# 前端视觉与交互设计规范

> 让视觉与交互先完成表达，把文字留给内容、操作和必要决策。

既有界面随实际改动逐步落实视觉与交互要求，避免为统一样式进行无关重写。

## 一、让界面能够直接被理解

用户应当通过布局、信息层级、控件形态与状态变化，识别当前位置、可用操作及操作结果。实现前先确定主要任务、主要操作和反馈位置，再决定是否需要说明。

- 主要操作具有明确的视觉优先级，相关内容与操作在空间上形成关系。
- 选中、禁用、等待、成功与失败应有明确且一致的表现，不能只靠一段文字解释状态。
- 优先改善控件、默认行为和操作路径。图标含义不明确时，保留简短、准确的操作名称，不能把理解负担转移给悬浮提示或用户猜测。

例如，保存操作通过按钮的等待状态和结果反馈表达进展，通常无需再写“点击保存后将保存您的设置”。

## 二、每一段界面文案都应有明确用途

操作名称、真实内容、关键限制和影响用户决策的信息应当保留。帮助说明、提示段落和注意事项不能作为填补设计缺口的默认手段。

新增解释性文案前，开发者应能回答：

1. 这段文字帮助用户完成哪个具体决策？
2. 更清晰的控件、布局、默认值或反馈能否解决同一个问题？
3. 信息应在当前画面常驻，还是在用户需要时展开？

无法说明用途的解释文案默认不加入界面。技术实现过程、内部模块名称和开发者的推理不应直接成为页面内容。必要的业务说明可以保留，并应简短、准确、贴近实际操作。

## 三、简洁的界面仍应有完整设计

删去说明后，应通过比例、间距、对齐、视觉重心和状态反馈建立秩序。大片空白配一个默认加载图标，不能代替完整设计。

- 使用现有品牌、字体、图标体系、颜色与布局角色，使界面属于同一产品。
- 主要内容有明确重心，相关元素紧密组织，次要信息安静但可发现。
- 精简装饰的同时保留真实内容、关键操作和必要的信息密度。
- 具体样式遵守 [CSS 与设计系统约定](./css-design.md)。沿用现有框架与设计令牌，不为视觉调整堆叠动画库或套用统一装饰风格。

设计选择应服务当前功能和品牌，不应把某一种配色、圆角、动效或页面构图机械推广到所有场景。

## 四、动效应承担明确的交互职责

动效应表达进入、退出、关联、等待、完成或状态变化，具有清楚的起点、终点和节奏。

- 高频反馈应短、轻、及时；品牌启动可以保留一个明确的视觉记忆点。
- 避免无目的的整页漂移、连续弹跳、过量缩放，以及多个元素同时争夺注意力。
- 不为播放完整动画而强制等待，不以动画完成事件代替真实业务就绪。
- 时长与缓动依据操作目的选择；启动衔接中的约 200ms 线性淡出是具体场景的实现，不是所有交互的统一模板。
- 优先采用开销可控的动画方式，避免因动画引起布局抖动或操作受阻，并提供减弱动态效果的完整使用路径。

## 五、把状态切换设计成连续过程

加载、首页、弹窗和内容切换应作为完整流程设计。上一状态应持续到下一状态具备可展示条件，再自然交接。

- 区分模块载入、数据准备和实际可见内容就绪，不能用其中一个事实替代另一个。
- 保持主题、背景、页面位置与主要布局稳定，避免中途露出空白、临时引导页或另一层加载状态。
- 保留真实的无项目引导、空状态和异常恢复；它们应在确认对应状态后展示。
- 初始过渡期间发生页面或任务切换时，重新核对实际目的内容，不能沿用过期的就绪结果。
- 达到当前界面的可用条件即可交接，不必等待所有后台请求或非关键内容全部完成。

启动案例：加载层覆盖设置、项目与初始页面的准备过程；实际页面完成所需绘制后，加载层退去，页面本身保持完整显示。具体提交标记、遮罩与错误边界见 [启动技术契约](./daemon-bootstrap.md)。

验收对象是用户实际看到的连续画面。

## 六、正常过程安静，异常状态明确且可操作

正常工作过程优先通过视觉反馈传达。确需用户处理时，提供简短、准确的说明和直接可执行的操作。

- 错误码、堆栈、内部阶段和命令标识等诊断信息按需展开，默认不占据主要界面。
- 精简展示不能删除恢复入口、原始诊断或必要的操作结果；未确认的结果不能显示为成功。
- 可恢复的异常应提供对应恢复动作，操作失败后仍保留可用界面，避免空白或永久加载。
- 真实但不阻断操作的提示，可以采用可发现的次要入口并按需展开；不能只对视觉用户隐藏信息。
- 权限、数据丢失风险、不可逆操作及其他影响当前决策的重要信息，应在用户做决定前明确呈现，不能为了视觉简洁而隐藏。

## 七、状态表达必须真实

动画可以表达“仍在处理”。进度条、百分比、完成或成功状态必须有实际依据，不使用假进度掩盖等待。

加载、空状态、失败、禁用和成功都属于正式设计范围，应各有清楚的表现和对应行为。不能把未知结果表现为空数据，不能在内容尚不具备展示条件时先宣布完成。

## 八、视觉优先与可访问性同时成立

- 视觉用户通过画面理解状态，屏幕阅读器仍应获得准确的状态描述。
- 控件具有可识别的名称，键盘操作有清晰焦点，反馈不只依赖颜色。
- 需要保留加载语义时，避免把实时播报放进会延迟播报的持续忙碌区域。
- 系统开启“减弱动态效果”时，内容与操作仍完整可用，不依赖移动或动画结束才能继续。
- 加载层覆盖内容时，避免焦点与操作落入被遮住的界面；交接后恢复可操作性，不无故抢夺焦点。

这些能力应内建于组件，不能靠增加说明段落补救。

## 九、在真实流程里验收设计

查看实际页面、交互过程和过渡录像；静态截图只能验证其中一部分。

- 覆盖不同主题、适用的窗口尺寸、慢加载、空状态、失败与恢复路径。
- 涉及异步交接时，使用真实组件和实际加载层级，刻意延迟数据或模块，检查是否暴露临时界面、闪屏或跳动。
- 对组件预览、隔离数据、原生运行和打包环境的验证范围分别说明，不把简化预览的成功扩大为完整产品验收。
- 根据实际视觉与交互问题调整实现，不能只凭“代码中写了动画”就认定体验顺畅。
- 按改动风险选择有意义的验证；文案与局部样式调整不必新增测试或运行整套构建。

## 常见选择与验收标准

| 场景 | 应采用的表达 | 需要核对的结果 |
| --- | --- | --- |
| 普通等待 | 清楚的活动状态，必要的无障碍播报 | 能感知仍在处理，无假百分比或常驻技术说明 |
| 保存与提交 | 明确的操作名称、等待与结果反馈 | 重复操作受控，成功与失败都有实际依据 |
| 初始页面交接 | 真实就绪条件、稳定画面与连续退场 | 不露出临时引导页或空白，不强制延时 |
| 可恢复错误 | 简短说明、恢复操作、按需诊断 | 能恢复或退出，失败后仍有可用界面 |
| 重要风险或权限 | 决策前明确提示及真实选项 | 关键信息可见，不能为简洁而省略 |
| 空状态 | 准确说明当前状态及有意义的下一步 | 已确认为空，不混淆加载中、失败与未知 |

开发与审查时统一使用下面的标准：

> 当一个界面需要不断增加文字，才能说明它如何工作时，先重新检查信息层级、控件表达、默认行为和状态反馈。
