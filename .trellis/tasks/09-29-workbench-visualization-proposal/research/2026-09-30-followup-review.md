# 2026-09-30 追加产品与交互评审

## 范围与结论

评审对象为用户与 GLM 多轮讨论后的任务设计，重点是 `06-触达优先与透视方案.md`，并对照 `00`—`05`、任务 PRD/design/implement、当前面板源码、本机 Trellis 0.6.17 CLI 与官方资料。

**建议通过“阅读体验 + 快速触达”的产品方向；暂不将 06 整体作为可直接实施的路线图。** 首版范围仍偏大，任务流和上下文透视存在具体的能力误判，派单层需要独立的执行合同。以下是评审建议，不覆盖文档中用户已确认的决策，也没有修改应用代码。

与上轮相比，最有价值的变化是从用户“复制任务目录到 Typora”和“打开应用再找任务”的日常成本出发。主从阅读、接着读、热键打开指定任务、材料间连续阅读，都有明确的使用场景。05 对工作树身份、稳定任务地址、读取错误和能力式连接的要求仍应保留。

## 1. 派单台属于新增执行范围，须与阅读首版分开验收

**位置**：[06 支柱三](../../../../docs/proposals/2026-09-28-workbench-optimization/06-触达优先与透视方案.md)、06 §4；00 产品决策；任务 PRD。

面板调用官方脚本或启动 worker 后，即使面板进程没有亲自写 `task.json`，仍然是用户在面板发起任务生命周期动作。例如用户在 TP 点“检查”，worker 修改源码并运行验证；用户点“归档”，脚本移动目录、更新状态并可能提交。这些操作需要面板承担目标绑定、权限、重复提交、取消、失败结果和操作记录的职责。

这条路线可以作为后续产品选择，但“进程不直写 task.json”不是充分边界。当前 00/PRD 仍把生命周期操作移出主界面，06 又在 P2/P3 加回；06 的 P0 还写“归档走官方脚本”，而 P3 才设计三段式归档，阶段承诺不一致。用户对 AGENTS.md、workflow.md、spec/skills 等文件的写入限制，也应明确是否约束面板发起的 worker，不能只约束面板进程而留下派单绕行。

**建议**：首版明确为阅读与触达；派单作为单独可选扩展。P0 对归档的处理写清是停用旧面板入口，还是保留并改造；不能同时沿用两种说法。元数据代跑也要按具体字段列权限与回执，不能以“等脚本”泛化。

## 2. 任务流图不能把文件存在和修改时间画成实际执行位置

**位置**：06 §3.1，尤其第 80、83—86 行。

场景：任务已实施完成，正在检查。`task.json.status` 仍是 `in_progress`，`implement.md` 昨天修改过。图中把它标成“实施进行中”会让用户误读，即使旁边附有“推断”二字。另一种情况是 `implement.md` 仅为实施计划，代码还没开始做；文件存在也不能证明实施产出已经生成。

本仓 `.trellis/workflow.md:123-133` 明确：`planning` 覆盖整个规划阶段，`in_progress` 覆盖执行、检查、规范更新及提交步骤。设计、实施、检查不是三个可由该状态字段区分的运行时状态。`[workflow-state:*]` 标签块是每轮提醒文本，包含 no_task、task_error、inline 变体等；标签完整性 INVARIANT 不等于定义了一个可执行节点图或完整转移关系。

**建议**：图可保留为“项目流程参考”，另用文件事实展示“PRD 已找到 / 设计文件已找到 / 未找到检查材料 / 位于归档目录”。取消由 status+mtime 推断的具体执行位置，以及按推断阶段把全部任务布到总览图的首版承诺。只有实际步骤事件出现后再加入执行点亮；未知项目流程降级为原文，不自动套固定五节点。

## 3. 面包屑沙盘可以做，但现有 hook 不是接收任意状态的纯函数

**位置**：06 §3.2 第 105 行。

输入 `{"cwd":"..."}` 并得到输出，只证明脚本能在那个目录和进程环境下解析一次上下文。它不能证明任意选择任务与状态就能模拟同一个 AI 会话的结果。

`.codex/hooks/inject-workflow-state.py:420-472` 的主入口读取 cwd、环境开关、prompt、平台、配置和活动任务；`:161-195` 从目标会话指针定位 task.json 再读状态。`.trellis/scripts/common/active_task.py:646` 的解析还取决于会话身份和环境。主入口不消费一个可覆盖实际任务状态的模拟 `status` 参数。

**建议**：拆成两个可理解的操作：

- “规则预览”：只解析 workflow.md 标签块，用户选择块，显示该块原文；不运行项目脚本，不改会话指针，不声称就是某个真实会话实际看到的全部提示。
- “当前会话诊断”：用户选择可核实的会话，展示平台、任务绑定、配置和读取结果；如果要运行 hook，显示运行条件与输出，不能用面板自身环境冒充外部宿主。

技能 description 也是可供模型选择的说明，不能画成“某句话必定触发技能”的确定性路由。显示“声明的适用条件”即可。

## 4. 上下文超限提示目前描述错了机制，也不能解释所有不遵守规范的情况

**位置**：06 §3.2 第 98、106 行。

本机和本仓已有两条不同的上下文装配链：

| 装配链 | 核对到的行为 |
| --- | --- |
| `.codex/hooks/inject-subagent-context.py` | 单文件/任务产物超上限时截断正文并提示去读原文件；总预算不足时才降为路径、理由和大小索引。内容顺序、标题与说明也消耗预算。配置中的 0 表示关闭相应上限。 |
| Trellis Channel `context-loader.js` | 本机 0.6.17 使用另一套限制：单文件 1,000,000 字节硬上限，200,000 字节告警，合计 500,000 字节告警；不能直接套 hook 的 32K/64K/128K 三条默认值。 |

例如 40KB 的 spec 可能已经注入了前 32KB，并留下完整路径让代理继续读取；“AI 实际读不到正文”是错误结论。即便未内联，worker 仍可能通过文件工具读取；缺内联也不能直接归因为“AI 不遵守 spec”。

**建议**：按平台、分派方式和实际配置展示“预期完整内联 / 预期截断 / 仅索引 / 跳过 / 无法估算”，提供截断位置及原件。措辞限定为预期注入行为，不能推断模型实际读过、理解或遵守。

## 5. Channel 不是现成的权限与人机确认层

**位置**：06 §2 支柱三、第 150—152 行。

本机 `trellis channel spawn --help` 明确 `--sandbox` **codex-only**。`.trellis/agents/check.md` 默认 `provider: claude`，职责包含修复小问题和运行验证；已安装 Claude adapter 构建参数时采用 `bypassPermissions` 和 `--dangerously-skip-permissions`。因此默认 check worker 不能因面板传入 read-only 字样就成为受限的只读审阅者。

Codex 的 read-only/workspace-write/danger-full-access 也不是“只准写 .trellis/tasks/”的任意路径白名单。起草任务需要写任务材料，不能单纯采用 read-only 后承诺建任务。现有 check 模板不要求稳定的 check-report 文件作为机器门禁；planner 员工档案也不是当前项目现成文件。

官方脚本执行与 worker 审阅之间，需要明确的回执格式、人类待确认问题入口、目标目录、取消、断联和失败收敛。Channel 官方文档也要求显式发送至 worker 并等待运行时事件；`spawn` 不等于任务已接单。归档的“Git 干净/所有子任务闭环”门禁应来自目标项目规则，不能作为全体 Trellis 项目的统一强制条件；如果 check 会自修源码，前置 Git 干净检查后仍可能产生新改动，收尾流程也必须说明如何处理。

**建议**：先做一个范围明确的能力验证：给一个指定任务执行只读审阅，产出可解析报告，并核验不能写源码、待确认问题能回到人。通过后再分别评估 planner、修复型 check 和归档；不要直接把当前默认 check 用成产品门禁。

## 6. 只设置 worker 的 --cwd 还不够防止频道串项目

**位置**：06 第 150—151 行的两条“铁律”。

本机 0.6.17 `channelSpawn` 调用频道解析器时只传 `scope`，而 worker 的 cwd 单独传入。频道 project bucket 默认由 CLI 进程 cwd 或 `TRELLIS_CHANNEL_PROJECT` 得到；不是仅由 `spawn --cwd` 决定，也不是 task metadata 中的 project slug。

场景：TP 子进程从项目 A 启动，给 worker 传 `--cwd B`。worker 会在 B 工作，频道查找仍可能属于 A。流程中的 create/send/wait/interrupt/kill 若身份不一致，同名频道会把结果带错地方。

**建议**：所有 channel 子进程的工作目录、worker cwd、scope、目标工作树身份与环境覆盖一起绑定并验证。读写 channel bucket 复用官方解析方式；把设计中的“项目 slug”改成“官方项目 bucket”，不自行用项目显示名拼路径。

## 7. events.jsonl 有审计价值，但不是完整注入回放

**位置**：06 第 91、112—114 行。

本机 supervisor 的 `spawned` 事件记录 provider、worker、pid、已装配文件路径与 manifest 路径。它不在该事件中保存所有文件的原始字节、内容哈希、每次 hook 输出和技能读取结果。worker 配置中可以有启动 system prompt 的快照，但仍不能把全部 events.jsonl 宣称为每轮完整注入回执。

**建议**：区分“运行时事件”“启动上下文快照”“实际逐轮注入回执”。能读到哪个就展示哪个；缺证据时不提供历史 X 光回放。任务绑定与最后记录可先独立浏览，不必等面板能够启动 worker；同时不能把 last_seen_at 当在线心跳。

## 8. 触达机制值得做，但要先定义不打扰与定位合同

**位置**：06 §2 支柱一、P1 三件快赢。

场景：AI 两分钟内多次保存 prd.md、design.md 和研究文件。当前 watcher 的文件事件不防抖直接透传；每次保存直接弹通知会把“阅读入口”变成打扰。热键默认打开最近文件，也可能把用户昨晚尚未读完的正文换掉。

建议首版交互：

- 热键先恢复上次阅读位置；通过明确的“打开剪贴板路径”动作定位新任务。也可以提供用户设置的优先策略，但不能在刷新或重复唤起时自动切换任务。
- 通知以被用户关注的任务和核心材料为范围，等待文件稳定后按任务合并；当前正在阅读的材料只给轻量更新提示；首次扫描不发“新生成”通知。
- TP 在托盘运行且目标项目受到监听时才承诺通知。退出应用后没有常驻服务就不能收到事件；自启动是独立选择，不能把它隐去。
- 深链必须携带能定位到工作树、任务、文件的身份。`tp://task/xxx#验收标准` 只含任务名时，在两个 clone/worktree 里会产生歧义；重复标题、文件重命名、归档后的锚点失效要有回退。
- 现有 scheme 是 `trellis-panel://`，并带每安装 token。只读导航链接、用户可复制链接和有权限的操作入口需要区分；不能把旧桥接完全等同于可分享段落深链。
- 第一版锚点以标题/文件为单位，未定位到标题时展示原文件并提示失效；“任意段落稳定链接”放后续，避免正文一编辑就定位错。

## 9. 首版包含太多不同产品，现成组件不等于近零成本

P1 同时包含多项目触达、系统右键、深链、独立速读窗、主从阅读、阅读恢复、jsonl 渲染和任务图，P1.5 又加入整个透视中心。它们还依赖工作区身份、错误态和稳定地址；无法以复制速记窗和几条监听代码估计整体成本。

`FlowStudio.tsx:522` 的 FlowVisual 目前是按阶段渲染的嵌套卡片列表，不是通用节点/连线画布。`watcher.ts:18-45` 提供文件路径和 add/change 事件，不直接提供 mtime/size 差异；需要 reader/index 另行取值。先复用样式与读取能力，再估算新交互；删除“全套现成”“近零代码”“碾压通用阅读器”等不能验收的承诺。

建议首个可交付版本只含：可信读取、稳定任务地址、单项目主从阅读、热键唤起、指定文件/目录路径打开、记住阅读位置。加一项合并的材料更新提醒验证真实价值。右键菜单、任意段落分享、多项目常驻、两张图和派单层分别进入后续独立条目。

00 指向 02 为实施依据，05 声明待确认，06 声明已确认但混合新旧 P/R 编号；任务 PRD 和 implement 还基本保留最初五份文件改写范围，jsonl 也未包含新的评审和方向文档。
