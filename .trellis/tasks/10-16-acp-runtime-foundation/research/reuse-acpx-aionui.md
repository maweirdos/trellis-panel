# Research: Reusing acpx and AionUi for the ACP foundation

Clean-room note (TPD-009): This report is independently written architecture and dependency analysis. It contains no copied upstream implementation, documentation paragraphs or patches. No package was installed, repository cloned, model prompt run or credential read. Only this research file was written.

- Query: Which existing integration can own ACP runtime work instead of rebuilding it around the SDK, and how do openclaw/acpx and iOfficeAI/AionUi fit an Electron/TypeScript app requiring Codex + Claude Code?
- Scope: Mixed; primary public package manifests, published declarations, architecture docs, selected source boundaries and test/workflow declarations. Source presence is not production verification.
- Date: 2026-10-16

## Findings

**Verdict: prioritize an isolated validation of the published `acpx/runtime` library before designing a new supervisor.** It already exposes an application runtime, GUI permission callbacks, session storage, controls and lifecycle work. AionUi is a valuable complete-product reference, but its current execution foundation is a separate Rust backend with broader application ownership. Neither candidate has been run or production-verified here. The previous SDK-plus-custom-supervisor selection should remain reopened pending this validation and the coordinator's other candidates.

### acpx: directly reusable application runtime

It is an ACP **client** that launches external ACP agents, not another coding/model loop and not the `openclaw acp` agent/server bridge. The npm package is independently usable; embedding it does not require adopting the OpenClaw Gateway. Its declared protocol dependency is `@agentclientprotocol/sdk ^1.5.0`. [Published package](https://registry.npmjs.org/acpx/0.19.5), [connection implementation boundary](https://github.com/openclaw/acpx/blob/95adbc569fb6aa2e8c021c4f352ffee05cc835ad/src/acp/client.ts).

The following APIs were verified in the **published 0.19.5 declarations**, rather than inferred solely from main:

- `createAcpRuntime`, `createFileSessionStore`/`createRuntimeStore`, and `createAgentRegistry` provide in-process runtime, persistence and launch-registry seams.
- `ensureSession` retains local/backend/agent IDs; `startTurn` returns `promptStarted`, an async event stream, final result, targeted `cancel`, and stream detachment. It accepts `signal`, `assertActive`, per-turn `onPermissionRequest` and `onElicitation` callbacks.
- `getStatus`, `getCapabilities`, `setMode`, `setModel`, `setConfigOption`, `close`, `prepareFreshSession`, `doctor` and `shutdown` are exposed. Status/events carry tool updates, model/config information, plans and reported usage rather than requiring terminal scraping.
- Host options include a custom load/save session store, child-only environment overlay, per-session MCP resolution/permission policies, lifecycle hooks, and explicit fs/terminal capability switches.

These are API facts from [published runtime declarations](https://unpkg.com/acpx@0.19.5/dist/runtime.d.ts), [published registry declarations](https://unpkg.com/acpx@0.19.5/dist/agent-registry.d.ts), and [runtime façade source](https://github.com/openclaw/acpx/blob/95adbc569fb6aa2e8c021c4f352ffee05cc835ad/src/runtime.ts). They establish a significantly larger reuse surface than the bare protocol SDK.

#### Material acpx adoption constraints

1. **Use the published in-process runtime first for this GUI.** `createSharedAcpRuntime` shares the CLI queue owner and supports independent session watching, but does not serialize per-turn GUI permission/elicitation callbacks, custom stores, environment overlays or lifecycle callbacks. Its shutdown detaches the app; accepted work/owner can continue. That conflicts with simply assuming app quit means all work stopped. Shared owner is a separate future topology, not an interchangeable constructor. [Shared-session contract](https://github.com/openclaw/acpx/blob/95adbc569fb6aa2e8c021c4f352ffee05cc835ad/docs/shared-sessions.md).

2. **Exact option selection needs a compatibility gate.** Published `AcpPermissionDecision` returns allow_once/allow_always/reject_once/reject_always/cancel. Upstream chooses a supplied option of the corresponding kind, with fallback ordering. It does preserve the chosen upstream option ID on the wire, but a GUI cannot express “the second distinct option with this same kind” through that public callback. Test whether the chosen Codex/Claude versions only offer one option per kind. If not, seek a supported upstream extension or another public boundary; do not silently claim the old original-optionId acceptance contract is fully satisfied. [Published types](https://unpkg.com/acpx@0.19.5/dist/session-options-CkcvthCv.d.ts), [selection mapping, source 446-464](https://github.com/openclaw/acpx/blob/95adbc569fb6aa2e8c021c4f352ffee05cc835ad/src/permissions.ts).

3. **Override automatic acquisition.** Published registry defaults use `npx -y` adapter ranges, including Codex `^1.1.5` and Claude `^0.81.2`; availability of newer adapters does not mean these defaults use them. Pass an explicit registry resolving the app's separately installed/pinned adapter entrypoints and selected Node path. Otherwise Start/probes may acquire software and violate the proposed separate-Setup contract. This is a concrete default-policy mismatch, not a reason to rebuild the runtime. [Pinned registry source](https://github.com/openclaw/acpx/blob/95adbc569fb6aa2e8c021c4f352ffee05cc835ad/src/agent-registry.ts).

4. **Respect pre-1.0 and platform evidence limits.** Public docs label interfaces evolving. The inspected CI has Ubuntu jobs across Node versions; Windows-specific test modules exist, but their presence is not evidence of a real Windows CI pass or a packaged Electron run. Pin exactly, use public exports, retain our real-vendor/native gates and examine transitive package licenses before dependency introduction. Do not import undocumented internal modules to evade the callback boundary. [CI](https://github.com/openclaw/acpx/blob/95adbc569fb6aa2e8c021c4f352ffee05cc835ad/.github/workflows/ci.yml), [Windows tests](https://github.com/openclaw/acpx/blob/95adbc569fb6aa2e8c021c4f352ffee05cc835ad/test/windows-batch-cwd.test.ts), [cleanup tests](https://github.com/openclaw/acpx/blob/95adbc569fb6aa2e8c021c4f352ffee05cc835ad/test/client-process-cleanup.test.ts).

### AionUi: broad product reference; official sidecar boundary is AionCore

The present app no longer supplies its main agent engine as a small TypeScript ACP component. Its documented development topology is Electron AionUi launching `aioncore`/`aioncore.exe`, a separately built Rust service exposing HTTP REST and WebSocket APIs with its own SQLite/app domains. Reusing the service would be a sidecar/API integration and deployment choice. Copying historical app-internal ACP classes is neither the supported current boundary nor permitted by TPD-009. [Pinned development guide](https://github.com/iOfficeAI/AionUi/blob/c140550d04e44f3d6f8a9830b40ae56e4689a977/docs/contributing/development.md), [AionCore architecture](https://github.com/iOfficeAI/AionCore/blob/503a87199eb978790ca77675b39c84b241535bf3/ARCHITECTURE.md).

Relevant verified module boundaries:

- AionUi root declares TypeScript ACP SDK `^0.18.2`, but this alone does not establish the active runtime. AionCore's `crates/aionui-ai-agent/Cargo.toml` depends on the Rust `agent-client-protocol` crate **2.0.0**, plus Aion-specific auth, DB, realtime, runtime, process and session crates. The crate version is a library version, not proof that the application uses “ACP v2”. [Rust agent manifest](https://github.com/iOfficeAI/AionCore/blob/503a87199eb978790ca77675b39c84b241535bf3/crates/aionui-ai-agent/Cargo.toml).
- ACP compatibility/connection work is under `crates/aionui-ai-agent/src/protocol/acp.rs`, `acp_dialect.rs`, `acp_init_budget.rs` and associated protocol modules. Session synchronization is `src/persistence/acp_session_sync.rs`; HTTP-facing agent routes live under `src/routes/agent.rs`; terminal integration has `src/terminal.rs`. They are application-internal Rust modules, not published npm exports. [Protocol modules](https://github.com/iOfficeAI/AionCore/tree/503a87199eb978790ca77675b39c84b241535bf3/crates/aionui-ai-agent/src/protocol), [persistence](https://github.com/iOfficeAI/AionCore/tree/503a87199eb978790ca77675b39c84b241535bf3/crates/aionui-ai-agent/src/persistence), [routes](https://github.com/iOfficeAI/AionCore/tree/503a87199eb978790ca77675b39c84b241535bf3/crates/aionui-ai-agent/src/routes).
- Backend architecture owns managed Node resources and startup PATH enhancement, process construction, unified session capabilities/events and SQLite message projection. Native/direct CLI and ACP paths coexist; `aionui-session` even documents a direct Claude stream-json seam, so the entire product feature set cannot be attributed to ACP alone. [Runtime infrastructure](https://github.com/iOfficeAI/AionCore/blob/503a87199eb978790ca77675b39c84b241535bf3/ARCHITECTURE.md), [session manifest](https://github.com/iOfficeAI/AionCore/blob/503a87199eb978790ca77675b39c84b241535bf3/crates/aionui-session/Cargo.toml).
- Official setup documentation includes external Codex and Claude Code, with vendor CLI configuration/authentication and differing adapter capability coverage. This makes AionUi a relevant UX/compatibility reference, not proof that all permissions, resume/config/fs/terminal semantics match our contracts. [Official ACP setup](https://github.com/iOfficeAI/AionUi/wiki/ACP-Setup).

**Coverage assessment:** launch/resources, application auth, vendor integration, permissions/cancel, session/history synchronization, model/config controls and terminal handling all have app/backend ownership boundaries. A reusable minimal service contract specifically preserving our exact optionId choices, same-session resume, directory lease rules and tool callbacks has **not** been established by this bounded review. If shortlisted as a sidecar, validate its official REST/WS contract and artifact distribution rather than extracting those modules. Its broad DB/conversation/user/runtime ownership could duplicate Trellis state and materially enlarge the scope.

**Windows/maintenance evidence:** AionUi provides Windows build/distribution scripts and a public 2.2.2 release; its development guide covers Rust MSVC and Windows executable discovery. Backend and UI repositories contain integration/contract/E2E test infrastructure, including ACP integration tests. These are positive maintenance/engineering signals, not observed test success on our machine or both vendors. Public releases are more meaningful here than stars; no popularity count is used in this assessment. [Windows/development guide](https://github.com/iOfficeAI/AionUi/blob/c140550d04e44f3d6f8a9830b40ae56e4689a977/docs/contributing/development.md), [ACP integration tests](https://github.com/iOfficeAI/AionCore/blob/503a87199eb978790ca77675b39c84b241535bf3/crates/aionui-ai-agent/tests/acp_agent_integration.rs), [release](https://github.com/iOfficeAI/AionUi/releases/tag/v2.2.2).

### Recommended validation and delegated ownership

1. Evaluate exact published acpx 0.19.5 through `acpx/runtime`, using separately pinned Codex/Claude adapters and a custom registry; no implicit npx acquisition. Confirm Electron bundling or an external-Node host boundary before committing the integration topology.
2. Delegate existing ACP protocol/client/session/turn/process/fs/terminal/reconnect work to acpx where it passes the contract. Trellis retains profiles/UI, task/material association, IPC ownership, legacy history compatibility, explicit setup and the application-wide directory policy. Do not reimplement satisfied runtime responsibilities under a new “supervisor” label.
3. Gate on real GUI approval callback semantics (including duplicate-kind option choices), cancellation/cleanup, auth-required behavior, two turns, controlled file/tool work, native resume and Windows packaged restricted-PATH operation for **each** vendor. Validate unknown metadata and lifecycle hook timing before promising every current UI phase.
4. If a public API gap prevents our acceptance, record the specific unsupported boundary and compare the coordinator's other published daemon/client option before falling back to a custom runtime. AionCore is a larger sidecar alternative, not the default way to obtain TypeScript ACP lifecycle helpers.

## Caveats / Not Found

- No candidate or upstream test was installed/executed. “Ready to validate” is the conclusion; “production verified” is not.
- GitHub API requests were rate-limited; pinned OIDs were obtained from public repository/tag page metadata. Individual public files and npm declarations were inspected without cloning or saving upstream source into the workspace.
- AionCore was inspected only far enough to establish the official backend/package boundary and application ownership. Exact exported REST/WS approval/resume behavior and the license metadata inconsistency remain to verify if it reaches the shortlist.
- Published package and main snapshots differ. No capability seen only on main may be assumed present in 0.19.5; key embedding/permission/options APIs were checked against published declarations and the tagged source.
- This report reopens technical selection. It does not approve implementation or modify existing PRD/design/implementation documents.
