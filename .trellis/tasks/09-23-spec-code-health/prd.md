# 规范与实现一致性健康检查

## 当前复核状态（2026-09-23）

用户复核后认为手动维护代码关联和人工验证记录缺少直接价值，要求撤回对应实现。关联 UI、人工验证记录、Git 健康扫描及其 IPC、类型和产品文档现已从应用代码中撤回。下方验收与手工记录是撤回前的历史验证，不代表当前版本仍包含这些功能。本任务文档仅保留为决策记录，未来是否改为自动推荐相关规范和复核项另行决定。

## 目标

在现有规范页中建立规范文档与受管代码文件的可维护关联，依据 Git 历史提示“代码变更后需要复核规范”，并为人工行为验证保存可追溯的场景与证据。本任务不新增自动测试运行器。

## 用户需求

- 用户可在 `.trellis/spec/**/*.md` 中声明规范关联的项目相对代码路径。
- 用户能在规范页查看和维护关联路径，并查看相关 Git 变更与手工复核线索。
- 用户能为规范记录人工验证场景、预期结果、实际结果、通过/失败状态、可选项目内证据路径和对应 Git commit；每次验证保留为独立历史记录。
- 规范文件之后代码有提交时，提示“需要复核”；工作区未提交变更单独显示。
- 无 Git 历史、worktree、无效路径或 front matter 格式错误时，仍能正常使用面板并看到可理解状态。
- 这是只读健康分析；除用户明确添加/移除关联时更新规范文档外，不修改代码、不自动改写规范、不阻断提交。

## 约束

- `.trellis/spec` 继续作为规范的唯一来源，不新增平行 `.spec` 树或数据库表。
- 验证历史写入独立的 Git 跟踪 JSONL sidecar（`.trellis/spec-evals/`），不混入规范 front matter。
- front matter 可选；无 front matter 的已有文档行为保持不变。
- 按文件关联，不处理函数锚点、自动评估 DSL/runner、CI 门禁或 agent/worktree 调度。
- Git 分析按需异步执行，不进入启动时同步项目扫描。
- 验证范围保持小而针对：类型检查、构建、少量 Git 历史场景；不引入大规模测试套件。

## 验收标准

- [x] Markdown front matter 的 `code` 路径能被解析、规范化及安全校验；非法 YAML 或越界路径不会崩溃（小型 fixture 已覆盖）。
- [x] Git 能区分同步、已提交代码变更、未提交代码变更、未追踪/缺失路径和无法判断。
- [x] 规范页显示关联路径与健康状态，支持通过文件选择器添加路径并移除已有路径（隔离 fixture 手工核验）。
- [x] 规范页可追加人工验证记录；两条历史记录均保留并显示，证据文件链接可用，路径 containment 有针对性 fixture 核验。
- [x] 添加/移除关联复用规范编辑的冲突检测；外部改动后移除关联显示冲突并保留原关联；正文渲染不显示 YAML front matter，编辑器保留原始内容。
- [x] 非 Git 与 linked worktree 的健康状态由小型 fixture 核验；扫描使用按需异步 IPC，不进入启动同步扫描（未做大规模性能基准）。
- [x] `npm run typecheck` 与 `npm run build` 通过，并完成针对性手工验证。
