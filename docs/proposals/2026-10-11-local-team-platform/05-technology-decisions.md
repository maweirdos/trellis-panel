# 05 · 技术选型与反向论证

## 1. 结论与证据强度

初选：**扩展当前项目的可复用能力，建立薄的团队协作服务；员工端保持本地，开源基础组件按模块接入。** 不把整套 Paperclip/OpenHands 作为当前首选，也不把 Electron 全部改成 Tauri 作为首个工程目标。

这不是部署对比测试的结论。事实来自本项目静态代码、上游官方文档/代码与许可证；适配成本、路线优先级是基于当前约束的工程判断。没有实测吞吐、安装包新体积或全部企业版功能。来源在第 08 章。

## 2. 四条路线的多维比较

表格是定性判断，不是产品评分或基准测试。

| 维度 | A 当前项目抽能力+团队服务 | B Paperclip 二次开发 | C OpenHands 为底座 | D 参考 等项目管理底座 |
| --- | --- | --- | --- | --- |
| 真人接单、本机自主执行 | 与现有本地能力接近；需补团队数据 | 可实现，但需约束既有 Agent 派发模型 | 支持本地运行；团队业务职责需补 | 真人指派自然；本机工程需另建 |
| 无代码的产品需求阶段 | 新建小范围简报与反馈模块 | 需重新安排任务、助手、审批入口 | 要在对话/执行主线前增加业务阶段 | 文档与需求功能有基础 |
| Trellis 文件与规范 | 现有读取、编辑、交接可抽取 | 需要插件/适配器和文件同步层 | 同样要新增 Trellis 语义 | 同样要新增 Trellis 语义 |
| Jira 持续作为业务系统 | 可围绕 Jira 缩小自建范围 | 三套对象关系需认真约束 | 需要自建可靠同步 | 与自身完整项目管理功能重叠 |
| 成员/讨论/版本基础 | 需要组合现成组件与业务表 | 已有相当部分，优势明显 | 不等于现成完整团队权限系统 | 最成熟的方向，但范围较重 |
| ACP 与本机 Agent | 现有实现可迁 SDK，真实兼容需验证 | 已有适配器与部分 ACP 路径 | 原生适合多 Agent 交互 | 需另接 |
| 改造/维护代价 | 自己维护小业务内核；责任清晰 | 除扩展还需持续跟进 alpha 插件和上游变动 | 要跟随执行平台架构与运行依赖 | 接受额外技术栈、数据模型及许可边界 |
| 与当前技能栈匹配 | React/TypeScript，较高 | Node/React，较高 | 前端可复用，执行服务有额外运行栈 | 前后端体系差异更大 |
| 可逆性 | JSON/Markdown/标准协议边界可替换 | 扩展独立时较好；深度 fork 后下降 | 仅接执行服务时较好，整站改造后下降 | 把业务数据放进其系统后迁移成本上升 |

### 为什么调整上一轮对 Paperclip 的推荐

Paperclip 的[产品定义](https://github.com/paperclipai/paperclip/blob/master/doc/PRODUCT.md)强调自主 Agent 组织、任务与执行协调。它并非只能云端运行，也不是没有真人功能；问题是本产品现在把“产品无代码、真人本机接单、团队端不启动编码”作为核心边界。

如果只借其成员、评论和审批，却要改写主要任务/执行体验并新增 Trellis 本地协议，复用收益可能被领域适配与上游跟随成本抵消。因此降为候选与交互参照，不先 fork。插件能力有真实实现，但官方仍标为 alpha。[插件指南](https://github.com/paperclipai/paperclip/blob/master/doc/plugins/PLUGIN_AUTHORING_GUIDE.md)

### 为什么不直接用 OpenHands

[Agent Canvas](https://github.com/OpenHands/OpenHands)适合多 Agent 和多执行环境，有价值；本项目首版最缺的是业务需求到本地工程的交接、材料发布和 Jira 一致性。这些不会因为换一个 Agent 控制台而消失。执行服务可作为未来可选适配，但不需要将整个产品建立在它的运行栈上。

### 为什么不把 参考 当“省掉团队系统”的捷径

[参考](https://github.com/make参考/参考)有完整任务与文档管理，但 Jira 仍是用户既定入口；把两套项目管理体系都当主系统，会增加字段与状态协调。借鉴收件箱、任务视图、讨论方式，暂不搬入其整个数据体系。

## 3. 自建范围受到限制

值得自己做的四块：

1. 需求简报、开发澄清和工程绑定之间的关联。
2. 真实 Trellis 文档、阶段、规范回执的可视化。
3. 从员工本机选择并发布团队可读成果的流程。
4. Jira 与交付状态的可靠映射。

不自建通用聊天平台、模型代理、向量数据库、用户密码算法、通用任务调度器、云开发沙箱和任意流程设计器。看板与 Markdown 阅读继续使用现有组件；冲刺和复杂排期尽量复用 Jira。

## 4. 模块级开源选择

| 模块 | 初选与复用方式 | 替代与退出条件 | 首轮验证 |
| --- | --- | --- | --- |
| Web | 现有 React + TypeScript + Vite，抽掉 Electron API 依赖 | 无需为内部工具改成 SSR 框架；明确出现需求再评估 | 同一文档组件在 Web 与本地壳可读 |
| 服务端 | [Fastify](https://github.com/fastify/fastify)，MIT；模块化单体 | 团队已有成熟 Node 服务框架则优先一致性 | 权限、schema 校验、错误与事件契约 |
| 身份 | 公司现有 IdP 优先；无现成服务时验证 [Better Auth](https://github.com/better-auth/better-auth)，MIT | OIDC/成员管理不符合环境时对接现有身份网关 | 入组、离组、项目授权、会话撤销；不能只测登录 |
| 可靠后台任务 | [pg-boss](https://github.com/timgit/pg-boss)，MIT，使用已有 PostgreSQL | 跨系统长流程运维复杂后再比较 Temporal，不先引进两套队列 | 重启、重试、唯一意图和失败可见性 |
| ACP | [官方 TypeScript SDK](https://github.com/agentclientprotocol/typescript-sdk)，Apache-2.0 | 非 ACP Agent 使用明确的专用适配或复制交接材料 | 实际两种常用 Agent、Windows、取消、权限、MCP |
| 文档 | 现有 Markdown 阅读器；编辑体验不足时引入 [Milkdown](https://github.com/Milkdown/milkdown)，MIT | 首版版本化编辑足够则不引入多人实时共编 | Markdown 往返不破坏内容；评论针对版本 |
| 流程图 | [React Flow](https://github.com/xyflow/xyflow)，MIT | 简单阶段列表足够则暂缓 | 点击节点能看到真实输入、结果和等待原因 |
| 知识库 | 现有自建 MCP / WeKnora，通过接口集成 | 无需强迫更换公司现有 KB | 用户范围、来源引用、失效资料、离线降级 |
| 模型网关 | 已有网关优先；新建时先试 [Bifrost](https://github.com/maximhq/bifrost)，Apache-2.0 | 公司已有 LiteLLM 则继续用；适配失败再比较 | 所需模型、流式、工具调用、密钥隔离、预算归属 |
| MCP 网关 | 首版少量来源直连 | 多工具、多认证来源时再评估 [ContextForge](https://github.com/IBM/mcp-context-forge) | 身份能否到达下游，不能只测工具列举 |
| 本地通信参照 | [Happy](https://github.com/slopus/happy)，MIT | 借鉴本地 CLI/设备与会话连接边界，不直接接入其远程控制流程 | 仅参考公开设计；本产品不授予产品经理远程控制 |

WeKnora 的主项目条款为 MIT，LICENSE 同时包含其他第三方组件条款；以所部署版本的完整声明为准，不能将整个镜像笼统视为只有一种许可。[许可证原文](https://github.com/Tencent/WeKnora/blob/main/LICENSE)

“模块首选”不意味着本轮安装。最小部署仅团队服务和 PostgreSQL；其余优先复用公司已有服务。

## 5. ACP 的投入应该到哪里为止

只实现用户真正能感知的统一面：启动前的能力检查、任务材料传递、流式回复、工具/权限事件、取消、可支持的恢复。优先两种员工实际使用的 Agent；其余不以 logo 形式提前承诺兼容。

当前官方 SDK 稳定入口仍针对 v1，v2 是实验草案。首版固定已验证版本，协议变动隐藏在适配器后面。ACP 不负责业务审批、团队调度或决定谁可以读源码；这些仍在本地与平台边界实现。[SDK 说明](https://github.com/agentclientprotocol/typescript-sdk)

## 6. Electron、无壳与 Tauri

| 路线 | 好处 | 成本/限制 | 次序 |
| --- | --- | --- | --- |
| 暂保 Electron | 现有窗口、凭据、进程与深链可复用 | 运行时体积保留 | 首个真实闭环 |
| 浏览器+本地伴随程序 | 非开发成员零安装，开发端不必携带浏览器运行时 | 本地页面/配对/升级/端口处理仍需建设 | 抽离后优先实验 |
| Tauri 轻壳+伴随程序 | 可复用系统 WebView，保留桌面入口 | Rust/插件迁移、Windows WebView2、Node sidecar 体积仍存在 | 有桌面能力需求后再比较 |

现存产物测量：安装包 80.61 MiB、主 exe 180.04 MiB、app.asar 29.77 MiB。这不是新架构体积预测。减重验收必须分别测安装包、安装后磁盘、Node/Agent 依赖、首次下载及离线安装；禁止只报一个小壳 exe 的大小。[Tauri Windows 安装说明](https://v2.tauri.app/distribute/windows-installer/)

## 7. 必须能推翻当前建议

| 触发条件 | 如何调整 |
| --- | --- |
| 业务用户试用后只愿意留在 Jira，不愿维护简报 | 减薄 Web，转为 Jira 内入口+本地工作台，保留版本与交付关联 |
| Paperclip 小样能通过全部本地边界验收且明显省去团队基础工作 | 重新提高其优先级；要求无需深改执行内核，数据仍可导出 |
| 某 Agent 的 ACP 缺关键能力 | 使用其受支持的专用入口，保留通用任务材料，不被 ACP 卡死 |
| 本地伴随程序安装/升级成本高于现有客户端 | 延后无壳/Tauri，先交付团队协作价值 |
| 工程材料无法安全共享且业务摘要仍无用 | 重新研究共享内容，不靠自动全量上传“解决” |
| 公司知识库权限无法可靠继承 | 先使用按项目隔离的只读端点，不接全部公司知识 |
| 需求非常复杂、同步协调超过团队可维护能力 | 缩小首版范围或接成熟连接/流程服务，不继续扩大自写框架 |

## 8. 未来容易走偏的地方

把“引入 ACP”当成产品目标；把“规范文件被读过”画成绿色合规；把员工使用不同 Agent 当成必须统一替换；为了多 Agent 演示牺牲真人控制；为减安装包而先重写所有后端；为省开发工作而 fork 一个领域模型不合适的大系统。

每引入一个组件，必须写清：它替掉哪段自建能力、增加什么运行负担、数据能否带走、失败时如何退回。没有具体答案就不加入首版。
