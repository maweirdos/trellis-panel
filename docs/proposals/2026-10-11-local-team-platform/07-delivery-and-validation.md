# 07 · 交付路线与验收

## 1. 本轮与正式实施的区别

本轮完成方案、静态交互原型和可检查的行为说明。下列阶段是建议实施顺序，不代表已经启动产品重构；时间与投入须结合团队人员、公司 Jira/登录/网络环境后估算。

## 2. 先做能否成立的验证

使用一个真实试点项目、产品/开发/测试三位参与者，以及两种员工实际使用的 Agent。不要先铺所有菜单或接十种模型。

| 验证 | 可检查的输出 | 失败时的选择 |
| --- | --- | --- |
| 无代码的需求澄清是否有用 | 一份真实简报，明确待开发确认项 | 改进项目能力卡；不假装能扫描代码 |
| 开发是否愿意接单并采用简报 | 一次本地绑定、一次反馈产品的闭环 | 优先编辑器交接，减少额外面板操作 |
| Trellis 流程能否真实展示 | 文件版本、阶段来源、一次上下文回执 | 降为只读观察，不伪造阶段自动化 |
| 文档共享是否能满足评审 | 产品和测试只看发布副本也能验收 | 调整共享摘要，不直接上传全部工程材料 |
| Jira 同步是否可靠 | 正常、超时后重试、重复事件三类样本 | 先人工预览回写，延迟自动流转 |

建议把首个验证限制在约 1–2 个工作周内，这是试验时间盒而非整体交付承诺。结束时决定继续、缩小、替换底座，而不是因为已经投入就扩大开发。

## 3. 四段交付

### M1 需求—本地评估闭环

公司登录、项目权限、简报草稿与发布、真人指派、开发领取、现有 Electron 打开任务、本机项目绑定、只读分析与澄清反馈、版本引用。先复用已有 Jira 工单，不急于自动创建复杂子任务。

验收：产品没有代码工具；开发本机能用真实项目反馈；双方知道采用的简报版本；领取不自动启动 Agent。

### M2 Trellis 工程工作台

按原生工作流创建或关联任务；PRD/design/实施计划查看；两种 Agent 的明确适配；规范选择与传递回执；开发确认后的本地执行；阶段事件回传；离线保存。

验收：开发在平台或既有编辑器工作均能继续同一任务；外部改文件不被覆盖；一个项目自定义状态也能正确显示。

### M3 交付—Jira—归档闭环

共享范围模板与发布预览、版本化成果、验收项、退回、Jira 单一写入口、重试与冲突、开发归档回执、经选择的知识沉淀。

验收：Jira 故障不丢交付；重复事件不重复操作；测试只能看授权材料；“已归档”来自实际操作。

### M4 规则治理与客户端减重

规则提案与评审、适用范围、引入本地、在途任务影响提示；抽取纯 Node 本地能力；实测无壳伴随程序和 Tauri 再决定客户端形态。

验收：规则能在下一次真实任务中采用；无需静默改仓库；非开发人员不用安装；减重报告包含所有运行依赖。

## 4. 建议代码边界（将来实施）

```text
apps/team-web        角色化业务 UI
apps/team-api        业务 API 与后台同步 worker
apps/local-client    先承接现有 Electron 壳
packages/trellis-core 文件读取、任务/规范解析、文档索引
packages/local-runtime 本机 Agent、工作区、私有日志
packages/contracts   设备、版本、发布与事件 schema
packages/connectors  Jira / KB / 模型配置适配
packages/ui          可跨 Web/桌面使用的现有展示组件
```

这是逻辑拆分建议，不要求第一天搬成完整 monorepo。先给 Electron API 加窄的适配边界，避免大范围移动与功能重构叠加。

## 5. 当前资产的迁移次序

| 当前资产 | 迁移处理 | 保护点 |
| --- | --- | --- |
| scan/watcher/handoff | 抽为与 Electron 无关的文件能力 | 未知字段、worktree 身份、实际文档存在性 |
| ArtifactViewer/Markdown | 作为共享 UI 组件 | 继续消毒、保留源码/渲染切换 |
| acp.ts | 用官方 SDK 替换协议细节，保留本地生命周期 | 不宣称“已支持任意 Agent” |
| plan/chat-context | 拆为需求助手与本地项目助手 | 产品侧不能意外继承项目上下文工具 |
| Jira IPC 自动动作 | 团队同步迁到统一后端，避免多个写者 | 旧模式按项目显式切换，防双写 |
| WeKnora 归档/spec 自动同步 | 改为发布策略与规范版本同步 | 不把工程全文当默认公司知识 |
| Flow/channel 派发 | 暂不扩为中央调度器；本机按原用途保留 | 新工作台任务关联优先，减少多套状态 |
| userData 设置与凭据 | 本机继续本机存储；公司连接另建 | 不上传用户全部 settings 文件 |

## 6. 关键验收矩阵

| 编号 | 场景 | 可观察结果 |
| --- | --- | --- |
| A01 | 产品创建需求 | 无仓库、终端、编码 Agent 入口；后端同样无执行权限 |
| A02 | 无项目上下文 | 明确待开发核实，不显示工程设计已完成 |
| A03 | 开发领取 | 更新领取状态；不 spawn Agent |
| A04 | 未绑定本地项目 | 无法开始项目分析；路径不提交团队后端 |
| A05 | 开发分析发现冲突 | 发布业务问题，源码证据保留本机 |
| A06 | Trellis task create 生成 PRD 骨架 | 显示规划中，不等于已确认计划 |
| A07 | 轻量任务 | 依项目工作流省略 design，不强迫空文档 |
| A08 | 自定义状态 | 原值可见，不写坏 task.json |
| A09 | JSON/Markdown 外部变化 | 重读版本与冲突，不覆盖最新内容 |
| A10 | 规范引用/加载/检查 | 分别显示，缺证据不升级状态 |
| A11 | 产品发布新版本 | 正在运行的版本不被悄悄替换 |
| A12 | 设备离线 | 显示陈旧时间；已获准本地执行可继续 |
| A13 | 恢复网络 | 补传事件，不自动开始新 Agent |
| A14 | 双设备或旧任期事件 | 拒绝旧端推进共享状态，显式处理交接 |
| A15 | 发布材料 | 上传正文与用户预览一致，默认没有源码与绝对路径 |
| A16 | PM/QA 请求本地文档 | 服务器没有私有内容可返回，而非仅前端隐藏 |
| A17 | 验收旧交付版本 | 提示版本已变化，拒绝错误确认 |
| A18 | 部分验收未通过 | 可退回；不可标记全部已通过 |
| A19 | Jira 超时后重试 | 查证原操作结果，避免重复评论/任务 |
| A20 | Jira 状态/字段改变 | 冲突可见，不无条件覆盖 |
| A21 | 同一 webhook 重复 | 入站去重，不形成同步循环 |
| A22 | 规则发布 | 新规则不自动覆盖本机；引入版本可查 |
| A23 | 公司库权限或可用性变化 | 无越权缓存；不可用来源如实显示 |
| A24 | Agent 不支持恢复/费用 | 使用可用交接，费用显示未知 |
| A25 | 转交员工 | 新员工重新绑定自己的项目，不搬运未提交代码 |
| A26 | 撤销需求或权限 | 不再受理新受管操作；离线进程状态如实未知 |

## 7. 值得记录的产品效果

先用 5–10 个真实需求记录当前基线，再比较：产品需要重复解释几次；开发找到已确认决定的时间；需求变更被发现的时间；测试能否只靠共享交付材料完成验收；Jira 同步失败恢复耗时。只做团队流程改进，不把它改造成个人代码量或 Agent 使用时长排名。

## 8. 回退与停止条件

新平台停用后，员工仍能用原编辑器和 Trellis 工作；代码与文档未被锁在平台数据库。共享内容可导出 Markdown/JSON；Jira 保持可访问；停止自动同步时显示最后确认位置。

若一轮试点表明“发布摘要比直接发文档更费力”“产品流程重复 Jira”“接单后仍得重新复制材料”，应先改流程或缩小平台范围。不要用增加更多 Agent、更多仪表盘解释失败。
