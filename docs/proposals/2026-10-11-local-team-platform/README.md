# Trellis 团队研发工作台 · 初版方案

版本：v0.1 · 2026-10-11 · 状态：供产品评审，尚未实施到正式产品。

后续讨论入口：[经过 GLM 回复与可行性审计的统一候选 v0.3](../2026-10-11-cockpit-convergence/README.md)。本目录保留为历史记录；当前流程、共享默认值、首发范围与分歧状态以统一候选为准，未获用户实施裁决。

这套方案围绕真实员工协作：产品经理与需求助手澄清业务，发布给开发；开发在自己的电脑上绑定项目、评估代码、决定如何使用 Agent，再进入 Trellis。团队平台保存共享的需求与交付记录，开发环境留在员工本机。

## 本版的明确建议

- 首选架构：团队 Web + 模块清晰的 Node/TypeScript 后端 + 员工本地伴随程序。
- 首版沿用现有 Electron 承载本地工作台；先分离业务能力，再比较无桌面壳与 Tauri。团队非开发成员无需安装。
- 开源按模块复用：ACP SDK、身份组件、PostgreSQL 队列、现有知识库、可选模型网关。第一版不整体 fork Paperclip 或 OpenHands。
- 需求助手没有仓库与本地终端能力；开发助手由开发在本机启动。
- 上游业务说明称为“需求简报”；Trellis 的 `prd.md` / `design.md` 是开发结合项目上下文后形成的工程材料。
- 平台不能远程替产品经理在员工电脑上启动编码 Agent；通知、领取、开始分析、开始实施是不同动作。
- 共享过程状态，按明确范围发布文档。完整代码、工具输出、终端和本机路径不作为默认同步内容。
- 模型使用边界已确认：员工继续按公司既有规则使用模型，包括允许的云模型调用；平台不额外上传、镜像或集中索引仓库，也不要求改用内网模型。

这些技术建议是可推翻的初选，不是因为已有代码就必须沿用。第 05 章明确列出改选条件。

## 本次建设范围

只新增本目录的文档、静态交互原型和原型检查资料；没有创建 Trellis 任务，没有接入真实 Jira、模型、MCP 或本地 Agent，没有修改现有产品代码与依赖。上一轮内联原型是早期讨论材料，本目录是纠正角色与执行边界后的新版。

原型中的“本机”“已加载”“测试通过”等均为带有演示标识的样例状态，不代表实际读取过员工项目。初版不提供真实账号、权限校验或设备配对。

## 初版评审顺序

先确认角色与工作流程，再用原型走一次真实任务；随后确定共享文档范围和 Jira 版本；最后通过小规模技术验证决定组件版本。不要先围绕框架名称争论，也不要把外观原型当成生产实现。
