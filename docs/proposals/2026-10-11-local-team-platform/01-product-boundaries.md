# 01 · 产品定位与角色边界

## 1. 产品要解决的具体问题

产品经理已经把需求说清楚，但开发打开本机项目后仍然发现旧接口、迁移成本、历史约定。现在这些差异往往散落在 Jira 评论、聊天记录和 AI 对话里，确认过的决定也不容易带到下一次执行。

工作台应把这一过程连起来：业务说明有版本，工程判断有依据，疑问能返回产品，开发有可用的 Trellis 上下文，测试能按验收项确认结果，规则能经过评审沉淀。

主要用户是使用 AI 的真实研发团队。Agent 是各角色使用的工具；人员组织、任务责任和授权不能被 Agent 名称取代。

## 2. 已确认的边界

| 决策 | 本版约束 | 来自哪里 |
| --- | --- | --- |
| D01 本地开发 | 代码与开发环境在员工电脑；不建设云端开发环境 | 用户本轮明确要求 |
| D02 产品权限 | 产品经理发布需求、与需求助手澄清；不指定员工使用哪一个编码 Agent | 用户本轮明确要求 |
| D03 项目上下文 | 通用流程必须允许开发结合代码再修订需求和设计 | 用户本轮明确要求 |
| D04 产品助手知识 | 使用获授权的已发布规范、知识库和需求材料；不直接读取代码 | 用户本轮明确要求 |
| D05 交付物 | 本轮建设初版文档、流程、设计和原型；不创建 Trellis 任务 | 用户本轮确认 |
| D06 模型使用 | 允许员工继续使用现有模型方式；平台不额外上传仓库 | 用户 2026-10-11 后续回复确认，原 Q01 |

“本地开发”不等于“模型必须离线”。用户已确认员工可以按公司既有规则使用模型，包括获准的云模型调用及其必要上下文传递；平台不额外上传、镜像或集中索引仓库。不要求迁移到内网模型，也不因为引入平台就强制所有员工经过新的模型网关。见第 08 章已解决的 Q01。

## 3. 两种助手，不同能力范围

### 需求助手：帮助人把事情说清楚

输入：用户描述、所选 Jira 工单、业务知识、已发布规则、研发维护的项目能力摘要。

输出：需求简报草稿、业务场景、验收标准草稿、问题清单、来源引用。

它可以说“已发布资料显示目前只支持单笔退款”，但不能声称“我检查了当前实现”。资料过期或无证据时，标为待开发核实。不得生成已确定的文件改动清单、技术工期承诺或伪造项目分析。

### 开发助手：由开发在本机使用

输入：指定版本的需求简报、开发选定的本地仓库与分支、项目 Trellis 工作流、适用规范、获授权的知识库。

输出：可行性判断、反馈产品的问题、Trellis PRD/design/实施计划、代码与测试、待共享的交付摘要。

“开始项目分析”默认仅允许读取项目和形成规划材料；进入实施由开发按项目流程确认。Agent 与模型选择属于开发环境配置，产品经理无此入口。

## 4. 权限表

| 动作 | 产品经理 | 被指派开发 | 测试/验收人 | 规范维护人 |
| --- | --- | --- | --- | --- |
| 创建、讨论需求简报 | 项目内允许 | 可评论/提修订 | 可评论/补场景 | 可评论 |
| 发布业务需求版本 | 有发布权限者 | 可建议，不替产品发布 | 可建议 | 不因维护规范而获得 |
| 分配给真人/团队 | 按 Jira/项目权限 | 可领取或申请转交 | 无默认权限 | 无默认权限 |
| 绑定本地仓库、选择 Agent | 无 | 仅自己的设备 | 无默认权限 | 无默认权限 |
| 在员工本机开始/暂停开发 | 无 | 本机开发本人 | 无 | 无 |
| 查看完整本地 PRD/design/代码 | 无默认权限 | 按本地仓库权限 | 按既有代码平台权限另行获得 | 无默认权限 |
| 查看已发布业务摘要、证据 | 按项目范围 | 按项目范围 | 按项目范围 | 按项目范围 |
| 批准交付 | 指定验收责任者 | 提交交付；不自动等于自验 | 指定验收责任者 | 无默认权限 |
| 发布公司规则 | 提议 | 提议 | 提议 | 按适用范围审批发布 |

管理员管理成员和连接；管理员身份本身不获得远程启动员工 Agent 的能力。UI 隐藏按钮之外，服务端权限与本地执行端也必须拒绝越权。

## 5. 产品信息结构

导航围绕人每天要做的事：

- **我的工作**：待领取、待回复、待验收、需处理的同步失败。
- **需求空间**：简报、业务讨论、需求版本、开发反馈、分工。
- **本地开发**：只对开发显示；仓库绑定、工程计划、规范加载、执行、发布交付。
- **交付与验收**：已共享证据、验收项、驳回原因、Jira 回写情况。
- **知识与规范**：搜索知识、查看发布规则、提出和审批规则提案。
- **连接设置**：管理员管理公司级连接；开发管理自己的设备与 Agent。

一个需求页面可跨角色打开，但返回的数据按角色裁剪。不能把完整本地文档发到浏览器后仅用 CSS 隐藏。

## 6. 边界并不意味着产品侧只能写空泛文字

研发可以发布“项目能力卡”：系统负责什么、已知业务限制、接口的业务含义、维护人、来源日期、有效期。产品助手用它提高澄清质量；它仍是经发布的资料，不等同实时源码。

开发发现简报有技术障碍时，提交业务可理解的反馈，例如“旧订单缺少重试标识，需要明确是否支持历史订单”。产品补充范围后生成新简报版本。这样的往返是正常流程，不应被视为 Agent 失败。

## 7. 不纳入首版

公司服务器拉仓库代开发、产品经理远程给员工运行命令、自动给 Agent 派活、按 token/代码行评价员工、所有聊天全文共享、每个需求强制生成完整 design、通用低代码流程编辑器、另建 Jira 同等规模的排期系统。

后续“平台内开发”指员工本机工作台中的 Agent 交互、文档与差异评审；不会自然扩展为云端 IDE。
