# 验收与实施顺序

## 设计验收

| 场景 | 通过条件 |
| --- | --- |
| 在项目中切工作项、迭代、团队、统计 | 模块同级、位置固定，项目选择器唯一，没有任务父级吞并其他模块 |
| 打开具体工作项 | 首屏能找到标题、项目、责任人、阶段、版本与下一步；中央没有无关仪表盘 |
| 产品确认需求 | 可读指定版本与未决问题，意见落到对应位置；后续只重新确认变化 |
| 开发开始实现 | 规划材料与既有 Trellis 授权要求明确；实际执行显示当前材料和环境 |
| 不使用 Agent | 产品、开发和测试仍能走完完整流程，不被模型配置向导拦住 |
| 进入团队页 | 找得到“等谁、缺什么、下一步”，点击回到同一工作项；不靠重复任务副本维护进度 |
| 找知识依据 | 搜索来源和权限明确，能打开原文与版本；引用和发送给模型是不同动作 |
| 进入项目文档与知识中心 | 同一材料的身份、来源和版本一致，没有两份相互覆盖的规范 |
| 查看会话 | 项目会话目录和任务入口指向同一记录；无项目归属的旧记录有明确兼容范围 |
| 改设置 | 个人、项目、资源、本次执行的生效范围清楚，不暗中改现有运行 |
| 在窄窗口阅读 | 中央仍有可读宽度，辅助区和导航可以收起；应用整体不出现横向溢出 |
| 没有项目或数据 | 显示正确引导和真实空态；演示有持续可见标识，没有虚构的在线和运行结果 |

## 视觉验收

比较同一视口、同一业务状态的设计稿与实现截图，检查标题层级、选中项、留白、文字密度、侧栏位置、阅读宽度和主动作。不能仅以有截图、能切页、构建通过作为体验合格。

单个导航区域只有一个明确当前项。范围选中与页面选中在不同区域用不同强度表达。状态有文字和图形，关键操作有可访问名称，键盘焦点可见。

核心验证宽度建议为 1920、1440、1280，并覆盖窄侧面板与高缩放。尺寸是验证样本；布局根据实际可用宽度响应，辅助栏不能把正文挤成窄条。

## 先后顺序

| 阶段 | 交付内容 | 前提与边界 |
| --- | --- | --- |
| 先定视觉目标 | 同一布局的任务列表、任务工作区和知识阅读状态 | 审查中心、导航层级、材料阅读和右栏使用，不修改业务代码 |
| 布局与入口收敛 | 范围栏、项目同级模块、设置分区、页面路由与来源提示 | 复用现有能力；每个保留入口有去向，不因改名假装新增后端能力 |
| 工作项连续处理 | 需求、决定、规划、执行、验证和交付在同一对象中展开 | 保留真实文件、版本、深链和返回位置；按 Trellis 合同设计阶段映射 |
| 真实跨人交接 | 共享版本、评审、待处理和团队队列 | 需要真实身份、共享材料与权限；本机派生视图不能代替跨电脑协作 |
| 知识与执行深化 | 权限内知识引用、材料集合、成熟运行层接入 | 运行层复用开源，跨厂商历史与外部写入单独验证 |
| 最后扩展自动档 | 稳定步骤的触发、等待、恢复与审计 | 先有可用手动流程和维护责任，不直接搭建自制通用编排平台 |

## 已有能力与需要补齐的能力

现有可复用基础包括：工作项与多布局、任务详情、文件阅读与版本比较、Jira 接入和来源去重、项目内会话记录、知识检索、规范读取、周迭代、个人偏好与部分本地执行能力。

现有 Team 页主要由任务、开发者记录和本机分析派生。真正的跨机器材料共享、评审通知、成员权限、并发编辑和在线状态，必须按真实支撑情况建设。原始业务说明到工程材料的确认链，也需要版本与责任记录，不能靠移动按钮自动获得。

知识中心沿用已有本地与公司来源，但统一检索、发布经验、个人资料权限和任务引用需要各自验收。当前通用 API 会话没有项目身份，不能直接换个标题就作为项目会话。

## 本轮没有改变的内容

本轮仅保存产品布局、边界、流程和验证方案，并制作设计示意。没有创建 Trellis 任务、修改运行中的 UI、调整全局主题令牌、接入新 Agent、配置自动化或写入外部系统。

此前的 roadmap 继续管理分期；本方案补充未来界面如何承载这些能力。实施时逐项核对正在推进的 UI、阅读、预览降级、迭代与 Agent 任务，沿用其已验证结果。
