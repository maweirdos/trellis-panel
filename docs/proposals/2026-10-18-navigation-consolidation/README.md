# 单项目团队协作：导航与页面收敛方案

状态：信息架构设计稿，尚未修改产品代码。2026-10-18；修订3。

## 1. 已确认的产品定位

用户确认当前主要围绕**单个项目进行团队协作**，团队需要更高权重。
顶栏继续选择当前项目，不增加组织或空间切换层。项目 root 仍是任务、成员记录、会话、资料和统计的上下文。

用户进一步明确：首页偏个人记录，现有会话能力的使用频率极高，希望提前其顺序。
用户指出“工作台、工作、工作项”词根近似，固定标题也不宜过长。
本次推荐 **首页、智能体、任务、团队、知识** 五个主入口，底部保留设置。
“智能体”突出当前 Agent 核心能力；模型问答保留为辅助工具，不将它表述成执行型 Agent。
本轮统一显示名称、导航归属和页面组织，内部会话、频道和控制器的含义不变。
团队保留独立入口与完整协作视图；AI 使用频率通过第二位入口体现。
工程能力归入任务模块的“工具”，仍能从二级导航直接进入。

本方案以 `docs/roadmap_v2.md` 的最新实施记录、场景方向及范围取舍为依据。
用户本轮对团队权重和单项目协作的明确说明，是导航设计的新输入。
组织权限、跨设备审批和更大规模自动化仍需实际需求与后端支持。

## 2. 一级入口的职责

| 一级入口 | 用户来这里做什么 | 默认内容 | 不重复承担的职责 |
| --- | --- | --- | --- |
| 首页 | 找回自己刚才在做的事 | 最近打开、最近阅读、最近 AI 会话、个人收藏 | 不放第二份全量任务表或团队统计面板 |
| 智能体 | 使用 Agent 和角色，查阅执行记录；按需使用问答工具 | 当前或最近的 Agent 对话 | 不代替任务管理，也不将个人历史改成项目共享记录 |
| 任务 | 按事项收集、组织并推进项目工作 | 全部 | 不建立第二套成员名册、团队负载或协作报表 |
| 团队 | 按成员与协作关系看项目运作 | 概况 | 不建立第二份任务表、迭代计划或任务状态编辑器 |
| 知识 | 查找、阅读和维护项目资料 | 项目资料 | 不另建任务材料副本或第二套阅读器 |
| 设置（底部） | 配置本机偏好、执行环境与外部连接 | 个人偏好 | 不承载日常 Git、运行日志或需求处理 |

首页围绕个人记录；任务围绕事项；团队围绕人与协作。
首页默认在当前项目内组织个人记录，不因此改写通用问答的本机跨项目历史。
当前首页的“最近更新”来自全项目文件更新时间，不能直接改名成“我的记录”。
记录归属必须有实际来源；缺少最近打开/阅读记录时，先补真实记录或隐藏该区，不推断操作者。
“我的待处理”可以保留为轻量摘要，完整任务集合与筛选留在任务模块。

### 任务与团队共享数据，但主操作只保留一份

| 场景 | 主要入口 | 团队或首页中的关联方式 |
| --- | --- | --- |
| 创建需求、建任务、设优先级、排自然周 | 任务 | 其他入口可发起明确动作，仍复用同一受控操作 |
| 修改某个任务的负责人 | 同一个任务详情 | 团队可打开该详情，不新增独立的负责人字段写入逻辑 |
| 查看某成员承担的工作与负载 | 团队 → 成员 | 展示按人聚合与任务摘要；查看全部时显式进入带负责人筛选的任务列表 |
| 查看某任务的变化与检查记录 | 任务 → 任务详情 | 团队中的记录可打开该任务预览并返回原位置 |
| 回顾本项目协作变化、效率与周报 | 团队 | 首页只展示与我相关的记录摘要 |
| 查看代码变化、启动脚本、阅读日志 | 任务 → 工具 | 不因为某成员是负责人就把工程执行复制到团队 |

团队可以按人投影任务信息，但不再复制全量列表、看板、任务编辑器或迭代编排。
同一个任务只有一份来源、一个受控修改路径和同一套事实口径。
成员记录、未来的项目成员关系和角色属于团队；任务的负责人字段仍属于任务。
这一区分既允许从成员视角分工，也防止两套分工结果互相覆盖。

│  ├─ 迭代
│  ├─ 接入
│  ├─ 归档
│  ├─ 工具
│  ├─ 视图（折叠分组）
│  └─ 收藏（折叠分组）

任务的状态、负责人和优先级进入正文筛选栏。
列表、看板、表格、甘特和日历继续作为同一集合的展示方式。
“迭代”打开相同任务集合的自然周视图，可选择其他周，不再占一级图标。
“工具”内部切换 Git、运行、架构、定制；这些工具按当前项目工作，不要求绑定具体任务。

建议图标沿用当前 Lucide：House、Bot、ListTodo、Users、BookOpen；底部 Settings2。
沿用全局 48px 栏宽、32px 按钮和18px图标。本轮重点是功能归属，不调整视觉尺寸。

## 4. 真正合并的页面与内容

### 工作项与迭代

共用任务集合、查询条件、详情面与布局控件。
当前 `workItemsView` 保留为视图状态，离开和返回时按项目记忆。
未开始、进行中等是筛选条件；自然周是排期维度，均不代表另一个工作模块。
需求草稿与正式工作项保留各自对象边界和显式转换动作。

### 团队与统计

合成一个团队工作区，内部按五个稳定视图组织内容：

| 团队视图 | 内容来源及合并方式 |
| --- | --- |
| 概况 | 谁需要协作、分工是否清楚、负载与接续是否存在问题；不再复制通用项目任务面板 |
| 成员 | 现有 Team 的负责人聚合与开发者记录，支持定位相关任务 |
| 动态 | 现有任务文件、开发者工作区与会话记录动态 |
| 统计 | 现有 Analytics 与 Team 的效率指标、流程分析；同类指标归到同一处 |
| 报告 | 现有站会和周报；在内容区选择报告类型与周期 |

统计页的工作项快照与 Team 效率页的 `getAnalytics()` 流转记录并非同一口径。
整合入口时保留来源、时间范围、是否含归档和无数据说明，不直接相加或删除不同口径的指标。
站会与周报收敛为报告视图内的类型选择，不再各占一层全局导航。

当前成员主要来自任务负责人和开发者记录。
页面使用“成员记录、负责人、最近记录”等准确标签。
用户确认面向团队，支持将团队放在一级，但并不代表当前已经有跨设备身份、在线状态或多人审批。

### 知识与规范

收成同一个资料浏览与阅读工作区。
项目资料、规范、公司库通过来源切换和目录区分。
规范编辑是选中文档后的操作，不再用另一套顶栏与二级导航重复组织内容。
沿用现有 DocumentReader、来源路径、显示版本、待更新提示与阅读位置。
公司库结果保留其独立范围说明。

### 智能体与辅助工具

将通用问答移入“问答”；内容说明仍明确它是模型问答与本机跨项目历史。
ACP、频道和通用问答可以共用外壳、导航位置及视觉控件，但继续使用各自的控制器与归属规则。
当前频道属于本机 Agent 协作记录，不改称已实现的成员群聊。
角色配置属于智能体模块；模型与执行引擎的全局配置属于设置。
会话仍可作为内部记录与生命周期的名称，不做代码标识、IPC或历史数据的全局重命名。

### 工程与设置

Git、运行与日志、架构和项目定制集中为“任务 → 工具”。
现有 DevTools 的 Git 与 Run 部分成为对应视图，保留只读 Git 和仅停止自有进程树的边界。
连接凭证、模型账号、执行引擎安装与 MCP 配置留在设置。
业务中的“配置连接”是明确标识的设置动作，不伪装成同级浏览项。

## 6. 防止再次出现导航相互跳转的规则

1. 每个页面有且仅有一个一级 owner。迭代、归档属于任务；统计属于团队；通用问答属于智能体模块的辅助工具。
2. 二级栏只展示该 owner 内的页面、视图和对象。团队栏不再列出工作项和频道作为目录。
3. 跨模块关联放在正文中，用“关联对话、查看任务”等明确动作表达。
4. 点击任务先打开原位置的详情或预览。展开、返回保留来源 owner、筛选和阅读位置。
5. 明确选择完整列表或另一个工作区时才改变 owner；此时目的地标题与一级选中态一起变化。
6. 顶栏项目是唯一项目上下文。切项目时按现有 root/代际规则清除旧项目对象，不新增独立团队上下文。
7. 首页不显示二级栏时，不覆盖用户保存的全局侧栏宽度和收起偏好。
8. 命令面板、侧栏、标题和旧路由映射读取同一份归属定义。搜索“统计”应定位到团队内的统计。

关系跳转本身是必要能力。应消除的是目录归属混乱和无提示的上下文替换。

## 7. 与 roadmap 的衔接

| 方向 | 稳定落点 | 本轮不据此扩张的能力 |
| --- | --- | --- |
| PF-01 / PF-02：项目连续性与阅读 | 全局项目上下文、任务详情、知识与智能体阅读面 | 不新增任务库和阅读器 |
| PF-06：现有 Agent 日常使用 | 第二位的智能体 | 不自建另一套 Agent 运行层 |
| PF-07 / PF-08：粗需求与旧任务接续 | 任务模块的接入、任务材料与接续交接 | 不建重复状态台账或通用关系图 |
| PF-09 / PF-10：Git、运行与日志 | 任务 → 工具 | 不默认增加 Git 写操作、云 IDE 或远程调度 |
| PF-11：检查与交接 | 工作项详情保留原记录；团队报告汇总适用结果 | 不将检查通过解释成业务验收通过 |
| 团队协作深化 | 团队的成员、分工、动态与报告 | 真实共享身份和访问能力未实现时不展示假在线或假审批 |
| 更多外部来源 | 设置管理连接；任务处理来源；智能体按需引用 | 不按厂商数量增加一级图标 |

近期首先改入口归属，再合并重复工作面。
后续协作能力优先扩展团队内部视图；没有明确独立对象和高频场景，不新增一级入口。
若将来发展为跨项目组织协作，再设计团队与项目的上层关系，不提前改变当前 root 合同。

## 10. 命名与顺序（修订3）

推荐排序：首页 → 智能体 → 任务 → 团队 → 知识；设置位于底部。
“工作台、工作、工作项”不再同时作为导航名称。
旧路由与数据对象保留，实施时只统一面向用户的固定名称。

| 原显示名称 | 建议短名 | 含义放在哪里 |
| --- | --- | --- |
| AI 工作台 | 智能体 | 当前以 Agent 使用和角色为核心；问答是辅助工具 |
| 工作 | 任务 | 项目事项管理；附属项目工具仍可在当前项目使用 |
| 工作项 | 全部 | 位于任务上下文，完整名称可用于可访问标签 |
| 本周计划 | 迭代 | 当前自然周及其他周在内容区选择 |
| 需求接入 | 接入 | 页面说明解释本地草稿与外部来源 |
| 项目工具 | 工具 | 内容区切换 Git、运行、架构、定制 |
| 保存的视图与收藏 | 视图 / 收藏 | 两个独立对象，分别作为折叠分组 |
| 成员与分工 | 成员 | 分工、负载在成员页面中呈现 |
| 协作动态 | 动态 | 当前团队协作记录，来源另行标注 |
| 统计与报告 | 统计 / 报告 | 指标分析与叙述报告分开，避免混称 |
| 规范与规则 | 规范 | 按目录和文档来源解释类型 |
| 模型与执行引擎 | 模型 / 引擎 | 配置对象分开，各有短名 |
| 外部应用连接与项目绑定 | 集成 | 本机连接与当前项目绑定用分区和范围标签说明 |

固定命名规则：

- 一级名称采用2–3个汉字；二级采用2–4个汉字。MCP、Git等必要缩写保留。
- 一个名称表达一个对象；不把两个目录拼成“某某与某某”。
- 父级已经明确范围时，子项不重复“项目、团队、个人、Agent”等前缀。
- 用说明、范围标签与内容分区补充含义，不把整段用途塞进标题。
- 任务名、文档名和用户自定义视图名保留真实内容，过长时截断并提供完整文本。
