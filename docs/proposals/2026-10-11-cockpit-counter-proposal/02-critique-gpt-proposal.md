# 02 · 对 GPT 方案的锐评

评审对象：`../2026-10-11-local-team-platform/`（G01–G09）。评审立场：以 01 章用户证词为准绳，从真实团队用户视角审判。GPT 方案可逐条回应；接受合理反驳，但反驳须给证据或指出本评审的证词依据错误。

## R0 应得的信用（三点，辩论中不重复争论）

1. **防伪纪律值钱**（G02/G03/G04）：文件被读过 ≠ 规范已遵守；Agent 自述 ≠ 测试通过；Jira 超时先查证再重发；设备离线 ≠ 任务失败。这层反作弊条款应全盘保留，贯穿后续一切方案。
2. **边界判断正确**（G01/G04）：产品经理不能远程启动员工机器上的 agent；平台不镜像仓库；ACP 不当沙箱用；Jira 继续作为工单字段最终依据。这些是产品在公司环境存活的前提，不是保守。
3. **开源调研诚实**（G05/G08）：不整体 fork Paperclip / OpenHands / 参考，按模块复用（Fastify、Better Auth、pg-boss、ACP 官方 SDK）；证据链区分"查过"与"猜的"；G05 写明自我推翻条件。该调研结论可采信。

## R1 主路修给了 20% 的场景

G02 的重头流程是"简报 v1 → 只读分析 → 反馈 → 简报 v2 → 工程规划 → 确认 → 实施 → 策展发布 → 验收 → Jira 回写"，这是大需求的完美流程。但真实团队 80% 的工作量是小修小补（对应 P05：bug/优化/小需求），G02 第 6 节对这类的全部回答只有一句"轻量任务可省略 design"。一个工具若让最频繁的任务多三步操作，开发会绕开它，数据链断裂，PM 看到的一切随之过期。这是协作工具死亡第一死因，GPT 方案未正面处理（其 G07 第 8 节仅在"停止条件"里隐含承认）。

## R2 Brief 与 Jira 双写，且自我矛盾

G05 拒绝 参考 的理由是"两套项目管理体系都当主系统会增加字段与状态协调"，但 G04 的领域模型（Requirement / BriefRevision / Clarification + 业务状态 + 工程状态 + 同步状态 + 设备在线）正是在 Jira 旁立了一套带版本化发布流程的小 Jira。PM 的真实反应会是"我为什么要在两个地方写需求"。GPT 方案的回答是"简报全文可用链接保留在 Jira"，等于让 Jira 用户点开一条内网链接。

对照证词 P05：用户的现实是"Jira 工单（粗）+ 飞书文档（细）+ 手动拷贝到本地 docs"，用户要的是把这个抽取动作自动化，而不是新增第三个书写面。方向应反转：**Jira 工单是输入入口，平台是增强层**，而非把 Jira 降级为回写目标。

## R3 共享默认值装反，掐死了核心卖点

用户核心诉求（原始畅想 + P01）："实时展示 trellis 创建的任务 prd、design 以及进程相关文档或状态展示"。G02/G03 的做法是开发手动勾选、编辑摘要、预览受众、再发布——这是要求开发持续做数据录入，而开发对额外录入零容忍。且 G04 把 `.trellis` 过程文档当潜在敏感物默认不共享：该判断对代码、终端日志、私有会话成立，对过程 markdown 不成立——这些文档本就在公司 Git 仓库里（P07：任务本来就要提交基座仓库），PM 缺的是能看懂的结构和入口，不是权限。

正确默认值：**task 的 PRD/design/阶段事件自动同步只读快照 + 敏感路径黑名单**；代码 diff、终端日志、私有会话默认排除。GPT 方案恰好把这组默认值做反，于是"直播 trellis"变成"开发定期手写战报"。

## R4 ACP 投入未回答用户的灵魂拷问，且缺三个真实入口

用户原话："如果花费这么大力气引入 acp，最后只搞了一个基本对话，那为什么不在各个平台的 ai 编辑中直接操作？"G05 第 5 节给出的 ACP 产出是"统一启动、能力检查、流式、取消，支持两种 agent"——比基本对话强，但有限。真正让 ACP 值钱的团队场景（统一事件流喂规范回执、会话材料跨人交接、用量可归因）在 G04/G08 只有一句带过。用户在 P02/P03 要的"注入可视化、工作流可视化"没有成为 ACP 投入的主目的地。

三个缺口：
1. **无 MR/PR 对象**。现有代码 `src/main/services/gitlab.ts` 已实现 GitLab OAuth、建 MR、任务分支状态查询（已核实），而 G04 十三个领域对象无一 Git 托管概念；"合并确认"靠人肉点击。
2. **无 IM 通知**。PM 和测试不住在平台里，住在飞书/钉钉（P05 证词：需求细节本就在飞书）。没有机器人卡片推送"待澄清/待验收"，非开发角色第一次错过通知就回 Jira 去了。
3. **无跨任务检索**。"上次这类问题怎么解的"是沉淀层最值钱的查询（P04/P07），G06 只讲了知识权限与新鲜度，没讲检索入口。

## R5 交付顺序错位 + 为三人试点配三十人规模的严谨

G07 的 M1 是登录、权限、简报、领取——全方案唯一"没有它平台不成立"但也"没人会因它兴奋"的部分，还是 PM 弃用风险最高的部分（G05 第 7 节自己承认该失败模式）。同时 G04 的 bindingEpoch、任期、租约、outbox 事件信封、SyncIntent 幂等层，是为几百人多设备并发写的分布式严谨；首个试点是三人（G07 第 2 节），用"单设备假设 + 事件 ID 去重"足够。

### 场景对照（周三下午四点，PM 想知道 PAY-128 做到哪了）

- 现状：去问开发；细节在 AI 会话里，PM 看不懂也看不到。
- GPT 方案落地后：看到"开发中"+ 开发上次手动发布的摘要（大概率三天前）；想看细节——默认无权限，因为共享需开发策展。
- 用户想要的：PRD 现在长什么样、注入了哪几条规范、agent 跑到哪个阶段、MR 建没建、CI 绿没绿——只读直播，开发零额外操作。

## 结论

GPT 方案值得留档，身份是**边界与防伪的字典**，不是产品路线图。方向修正两句话：共享默认值从"开发手动策展"反转为"自动快照 + 黑名单"；Jira 从"回写目标"升回"需求入口"。两条不改，其余做得再严谨，也只是一个更好看的流程法庭。
