# 01 · 用户一手证词（痛点底座）

来源：用户 2026-10-11 的口述，经整理但保留原意与关键原话。**本文件是证据，不是方案；辩论双方可以引用，不得改写、不得替用户"优化"表述。**

用户的总立场：两份 AI 方案（GPT 方案与本反方案）此前都"想得太理想"，很多东西做不到那么完美；要以实际开发体验为准。用户自述脑子里设想过很多交互，"每个都比较难以落地"，因此需要 AI 帮忙构思完整产品。

## 痛点清单

### P01 文档阅读痛苦（本项目立项初衷）

> "生成 prd 与 design，我每次都要到文件生成的目录里面去用 Typora 打开阅读，因为各大 AI 编辑器都默认在右侧打开一个 md 阅读器，不仅格式显示还有预览大小都看着不舒服，所以我很不乐意阅读。还有 task.json、implement.jsonl 等文件，这种都没有一个可视化窗口显示。"

- 现状：trellis 产出的过程文件（prd/design/task.json/implement.jsonl/check.jsonl）在 AI 编辑器里阅读体验差或根本没有可视化。
- 立项初衷："我本质上还是对这些源文件阅读做一个视觉交互，这也是我这个项目建立的初衷，只不过我现在想更进一步做成一个团队产品。"
- 含义：本产品的第一性价值是"把 trellis 源文件读舒服"，任何团队化改造不能丢失或稀释这个初衷。

### P02 注入黑盒

- 现状：规范通过 hooks 注入，"在第三方窗口里面其实也观测不到到底注入了哪些规范给模型，这里其实就是一个黑盒"。
- 编码规范："我是想严格地每次编码都要注入，但是其实每次是否真的注入了，或者是否渐进式披露注入了我都是未知的，所以代码其实也不全是按照规范来的，很多时候还是要返工。"
- 业务规范："我也不知道模型处理任务的时候是否会路由到相关的业务规范。"
- 用户理想：至少能看见注入了什么；"当然这个注入逻辑如果能交互那就更好了。"

### P03 工作流黑盒

- 现状："主 agent 跑，然后可能派发子 agent 做前端，做后端，做测试等，这里都是工作流决定的，但是其实用户是感知不到工作流执行的。"
- 用户理想（自认大胆）："工作流可视化，执行到哪一步了都能显示，就像一个进度一样，那样我甚至可以观测到模型哪些工作流没有执行，或者遗漏了。"

### P04 交付迭代与断裂衔接

- 现状："复杂逻辑都是不能一次性完成的，一般都会出现各种各样的问题，有涉及的修复。"
- 既有做法："工作流我当初制定的方案是创建子任务挂载当前任务下面继续优化。"
- PRD 不齐的场景："有时候甚至是发现任务在最开始 prd 阶段就没有补齐，还要额外的补充。"典型例子：药品追溯码管理，一阶段由产品调研产出，功能属于迭代过程，优化完善很常见。
- 核心断裂："往往这个时候都是中间隔了好几个其他任务了，你如何衔接到前面做过的任务也是很重要的，不然整个优化任务又是相当于重新来。"

### P05 Jira 接入的现实与鸡肋感

- 团队模式："划分大版本的，每个大版本里面有各种 issue，可能是 bug 修复，可能是优化，可能是新增需求，基本都是产品提出来，然后分配到团队的开发人员，开发人员去开发认领。"
- 既有集成自评："接入 jira 做到的功能点也就几个，一个是查看自己的任务，一个是结合 trellis 变更任务状态，其他的就真的没啥用了……这个也比较鸡肋。"
- 需求细节的真实位置："产品又习惯在 jira 里面总结一下问题（一般是新功能新增；bug 一般就直接描述了），并不细致，然后挂一个飞书需求链接，所以更多细节反而在飞书里面。"
- 飞书文档的问题："飞书里面的需求文档又过于多，你即使进入这个链接，还要翻阅到对应的目录找到具体的需求，所以要想自动化也是难度很大。"
- 现实折衷："很多时候还是要提取到本地项目的 docs 目录，然后制定给 AI 读取。"

### P06 知识库的真实用法与黑盒

- 架构意图："我本地的 docs 中的需求文档是当前任务的具体流程，但是很有可能这个任务涉及面广，触及到了其他模块功能，所以知识库知识就能更全面地去分析这个需求，以确保任务的健壮性。"
- 黑盒现实："但是实际上 AI 是否是按照我的这个想法执行的吗？其实这也是一个黑盒状态，我不得而知。"
- 现有资产：知识库已 RAG 一部分需求文档（WeKnora 自建 MCP）。

### P07 团队文档沉淀（理想，未落地）

- 既有设计："相关的任务都是需要提交到我的基座仓库的，这样能追踪到每个员工的需求具体设计与迭代。"
- 理想："如果后续能基于这些文档再建立需求迭代知识库，那么这个 vibecoding 的项目质量就更有保障，至少能从文档了解出整个方向，从代码了解出具体细节。"
- 现状自评："其实这个也都是我的理想设计，具体也不知道怎么落地。"

### P08 工作空间进度线

- 观察：".trellis 工作空间这里有每个成员的任务会话进度记录，其实也是一个任务进度线。"
- 理想："这些后续也能做成团队展示的东西，开发记录表现图。"

### P09 为什么必须做 agent 产品（立项动机的自辩）

> "我自知现在每个 AI 厂商的编辑器平台很完善了，个人再出一个完全是没必要的，根本跑不过他们公司团队的产品。"

- 但任务流向决定了必须做："任务 prd、design 等制定都需要 ai，代码的编辑也需要 ai，任务的流转需要 ai……如果我不做 agent 到我们的项目中来，意味着这个永远只是一个 trellis 的面板查看，不会有任何的交互动作产生在这里。"
- 面板的天花板："面板的交互永远是外部的产品……你的工作流只是一个文档，你的规则注入只是一句话，你的产出也是源文件，你在会话窗口里面没有任何的视觉交互，都是黑盒无法把控，这不得不逼我来做这个 agent 产品。"

## 证词的归纳（供辩论引用）

用户所有痛点同构：**AI 在 trellis 里做的每件事（注入、规划、检索、派发、修复）对人都是黑盒，人只能看到落盘的文件结果，看不到过程，因此无法信任、无法纠偏、无法衔接。** 归为四黑盒（注入 P02 / 流程 P03 / 知识 P06 / 交付 P04）、一断裂（迭代衔接 P04）、一外循环（Jira+飞书+沉淀+进度线 P05/P07/P08），外加一个不可丢失的初衷（阅读体验 P01）和一条立项动机（P09）。
