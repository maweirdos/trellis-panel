## 一、面板现状盘点

### 1.1 一句话定位

Windows 桌面 Electron 面板，**单人用户通过「AI 频道 + 任务派发台」驱动多个 AI 代理干活**，本质是 `.trellis/` 工作流的可视化指挥台。核心用户问题永远是三个：**代理在干什么、什么卡住等我了、今天产出了什么**（[OSS 引言]）。

### 1.2 页面与视图地图

侧边栏四组 14 页（评审勘误：原文误作「15 页」，`Sidebar.tsx:26-61` 实数 14 项 = 工作台 3 + 知识 3 + 协作 3 + 系统 5，与调研笔记一致）+ 非导航视图 7 个，App.tsx 按需加载 17 个页面模块 [面板 一]：

| 分组 | 页面 | 承载 |
| --- | --- | --- |
| 工作台 | 概览（203 行）· 待办池（237 行）· 任务看板（1790 行） | 统计与当前任务；需求收集池（`.trellis/todos/`）；看板/阅读/列表/泳道四视图 + 拖拽 + DoD 门禁 + 归档 + AI 拆分/提交信息/PR 描述 |
| 知识 | 知识库（769 行，六库+公司库）· 规范文档（502 行）· 归档（59 行） | 联合检索 + AI 问答带引用；spec 目录树 + 在线编辑 + 引用统计识死规范；双布局只读归档浏览 |
| 协作 | AI 频道（429 行）· 团队协作（856 行）· Jira 任务（448 行） | channel 实时事件流 + 派发台 + worker 启停；动态流/效率分析/站会/周报 + AI 健康诊断；我的待办/冲刺/JQL/导入转任务/状态同步/评论回写/AI 规划 |
| 系统 | 架构图 · 定制中心（1335 行）· 模型管理（1134 行）· MCP 网关（914 行）· 设置（1077 行） | 三泳道工作流可视化；八个定制 section（含 FlowStudio）；多供应商模型配置；网关调试；主题/Jira/GitLab 连接/hooks |

非导航视图：AI 对话 Chat（769 行、14 个 IPC 通道，**入口仅 Ctrl+K**）、任务详情（24 字段编辑 + 暂存 Diff + GitLab MR，挂在 3 个页面）、胶囊模式、速记窗（全局热键 Alt+N）、命令面板（Ctrl+K，13 页 + 3 动作）、产物查看器、需求录入向导（直达 AI 规划）[面板 一]。

### 1.3 数据面

单一事实源：主进程 `project:snapshot` 全量推送 + watcher 防抖监听，渲染层 zustand 七切片 store，所有页面 `useApp` 读同一份 [面板 二]。跨页面共享能力 21 项（快照/待办/五库知识库/Flow/频道/应用内 AI/Chat/速记窗/胶囊/桥接/WeKnora/MCP 网关/访问令牌/Jira+GitLab/Git/报表/CLI 子进程/Web 看板/Shell/遗留收件箱）[面板 二]。

### 1.4 做对了什么（这些是资产，后续方案都挂在上面）

1. **单事实源数据面**：全部视图同源 `.trellis/` 扫描 + snapshot 推送，多视图天然一致 [OSS 2]。
2. **高频输入通道方向正确**：速记窗热键、胶囊模式、派发台一句话建任务、需求录入直通 AI 规划——「输入即结构化」的路线已经起步 [OSS 8]。
3. **诊断链路已有（修订表述）**：停滞判定是效率分析的**本地规则**（`report.ts:167`，updatedAt 差值 >3 天即计入阻塞段），团队页 AI 深度诊断是在其上做归因解读的**解读层**（`Team.tsx:301` 注释自证「把效率数据交给 AI 解读」）——数据与解读都在，缺的是可视化落点而非能力。
4. **看板反拥堵设计**：大列自动折叠（>8 条只留 5 条）[OSS 2]，已被成熟产品验证为正确分寸。
5. **通知通道现成**：托盘常驻 + tpanel notify 深链 + Toasts 组件 [OSS 6]，缺的是「通知策略」而非通道。

## 二、差距清单

分三组：A = 自身硬伤（文档与产品不符、前后端断链）；B = 对比参考项目（honsky-governance）的治理能力差距；C = 对比开源成熟交互的体验差距。**每条一句话讲透**；编号供 02 方案引用。

### A. 自身硬伤（证据最硬，属「还债」）

| # | 差距 | 一句话讲透 |
| --- | --- | --- |
| A1 | CLI 终端断链 | README 宣称的「CLI 终端」页面不存在——主进程 `cli:run/abort` + 事件流 + preload 四方法完整保留，但渲染层 api.ts 与所有 tsx 零调用，能力在、入口无、文档还在吹 [面板 三·1]。 |
| A2 | Chat 无入口 | 769 行、14 个 IPC 通道的重头 AI 对话页，侧边栏没有它，唯一入口是 Ctrl+K，新用户基本撞不上 [面板 三·2]。 |
| A3 | 命令面板太窄 | 页面清单 13 项缺「模型管理」「MCP 网关」，动作只有 3 个（新建待办/重扫描/切主题），与 21 项跨页能力、Flow 模板库、派发台完全不匹配 [面板 三·3-4]。 |
| A4 | inbox:new 死路径 | 主进程已无发送方、渲染层仍在订阅维护的半悬空事件路径，要么恢复发送方要么删干净 [面板 三·5]。 |
| A5 | README 落后代码 | services 清单缺 9+ 个文件与 2 个子目录，GitLab 集成（3 通道 + Settings + MR 按钮）全文只字未提——产品在长、说明书没跟上 [面板 三·6]。 |
| A6 | 概览页失职 | 203 行静态统计没回答「代理在干什么/什么等我/今天产出什么」，没承担工作台首页的聚合作用 [面板 三·7]。 |

### B. 对比参考项目 honsky-governance 的差距（治理能力）

参考项目与面板同用 Trellis 0.6.17，其定制全部核实过（模板哈希 + 双边 diff 实锤）[参考 workflow §1]。差距按「对面板价值」排序：

| # | 差距 | 一句话讲透 |
| --- | --- | --- |
| B1 | Jira 关联不入任务元数据 | 参考项目把工单号/IssueId/版本/链接写进 `task.json.meta` 随任务入库随 git 走 [参考 §1.2③]；面板侧**已核实为不写**（评审阶段补核代码）：`services/jira.ts`（182 行）是纯 HTTP 客户端、全文无任何 meta 写入，「加入待办池」只落 `.trellis/todos/` 待办（`Jira.tsx:133-143` 调 saveTodo，连任务都不建），「AI 规划」只把工单摘要预填规划弹窗文本、jiraKey 仅作 UI 徽章（`Jira.tsx:284`、`PlanningModal.tsx:134`）——关联信息活不过一次导入动作。 |
| B2 | 同步无回执无对账 | 参考项目每工单一份 `pending/synced/conflict` 三态回执 + `reconcile` 全量补偿 [参考 §1.2④、§1.1]，面板状态同步失败即静默丢失，没人知道 Jira 在撒谎。 |
| B3 | 同步靠手点非生命周期驱动 | 参考项目 after_start/after_archive 钩子自动推「开发中/开发完成」、失败不阻断本地流程 [参考 §1.1]，面板同步是页面上的一次性动作 [面板 一·Jira 行]，靠人记得点。 |
| B4 | 归档无机器预检 | 参考项目归档前跑交付门：逐条校验交付物路径/命名/单号/回执，FAIL 即阻断且每条带补救命令 [参考 §2.2④]——这套门就是被「AI 忘记上传、漏了靠用户追问」的真实事故逼出来的 [参考 §2.2⑥]；面板归档按钮没有等价预检。 |
| B5 | 无共享交付物登记 | 参考项目「唯一正本 + 共享登记（脚本 ID 回执）+ 机器校验」三件套管 SQL 交付 [参考 §2.4]，面板任何交付物（SQL/迁移/文档）都没有登记与校验链。 |
| B6 | spec 只是文档树 | 参考项目规范库有轨道（rules 严准入/business 登记制）、生命周期（status: verified/pending + 每月清账）、健康度（rules 30 天增长 >5 告警）[参考 §3.1、§3.5]，面板 Spec 页只有目录树 + 编辑 + 引用统计 [面板 一·规范文档行]。 |
| B7 | 任务上下文清单不可见 | 参考项目任务的 `implement.jsonl/check.jsonl` 每行 `{file, reason}` 记录「这任务读了哪些规范、为什么」[参考 §3.2③、§4.1]，面板未见解析透出（调研未发现），任务该配什么上下文全靠翻文件。 |
| B8 | 检查回执不可读 | 参考项目 check-report.md 是「规则→结论→依据」结构化回执、验证可复用 [参考 workflow §2.9]，面板没解析展示，AI 说「检查过了」人只能信或读原始 markdown。 |
| B9 | 团队约定不可视 | 参考项目 21 处团队约定插在 workflow.md 各步骤、随 workflow-state 逐轮注入 [参考 workflow §2.1]，面板用户只能读 700 行文档才知道本地规则改了什么。 |
| B10 | 模板改动无体检 | `.trellis/.template-hashes.json` 足以列出「哪些文件被本地改过、升级会不会丢」[参考 workflow §2.2]，面板不显示，`trellis update` 前心里没底。 |
| B11 | 无多仓工作区 | 参考项目 packages 双仓声明 + 命令安全转发（run_package_command.py，清单校验/防工作目录漂移）+ 边界校验 [参考 workflow §2.7]，面板按单仓假设设计，管多仓项目时无处落。 |

### C. 对比开源成熟交互的差距（体验）

| # | 差距 | 一句话讲透（参照产品） |
| --- | --- | --- |
| C1 | 无「等我处理」一等队列 | 代理等输入/门禁失败/卡住超时埋在频道事件流里，没有 Linear Inbox 式「需要我处理的事」的收口（Linear 的立场：Inbox 是要处理的，不是发生过的）[OSS 1、6]。 |
| C2 | 无保存视图 | 「卡住>N 小时/某频道全部/失败重试」这类高频横切视角每次手工筛，Linear 保存视图证明这是导航一等公民、实现成本几十行的事 [OSS 3]。 |
| C3 | 看板分组维度单一 | 只按状态分列；Linear 证明分组可以是任意字段——按频道分组时一列=一个代理的在制任务，看板同时变负载面板 [OSS 2]。 |
| C4 | 健康度无落点 | AI 诊断已有停滞归因/负载观察，却没有 GitLab epic 三档色点式「一屏扫全盘」的健康矩阵 [OSS 9]。 |
| C5 | 无吞吐趋势 | 效率分析是单点数值，缺 7/30 天完成速率/中位交付时长/卡住时长趋势线（Linear cycle 式），单点数看不出变好还是变坏 [OSS 9]。 |
| C6 | 动态流无降噪 | 没有 GitLab issue 时间线式两层结构：系统事件 diff 一行化、AI progress 折叠（「· · · 47 条进度消息」）、类型过滤——几百条 progress 不折叠，流就不可读 [OSS 5]。 |
| C7 | 无快捷指令 | 任务评论不能打 `/retry` `/reassign <频道>` `/done` 直接变动作（GitLab quick actions），人对代理的指令没有轻量下达通道 [OSS 4]。 |
| C8 | 无任务模板 | 速记/派发有「一句话」，但缺 GitLab 仓库模板式 PRD 骨架（bug/功能/调研三类，随 git 版本化共享），每次 AI 规划都从白纸开始 [OSS 8]。 |

### 明确不追的差距（写出来防止路线图跑偏）

甘特/时间线编辑器、传统燃尽图（AI 任务小时级、无排期概念 [OSS 2、9]）、OpenProject 式报表中心、多人指派与审批流、全量通知偏好矩阵——单人 + 多代理场景下这些是负资产，参考项目与开源调研均不支持投入。

## 三、差距的结构性判断

25 条差距不是并列的，有一个结构性结论：

1. **A 组是债**：文档与产品不符、能力在而入口无——不还会持续伤害信任（用户按 README 找功能找不到），且 A1（CLI 链路）是 B4/B8（命令回执、归档预检）的现成依赖，先还债等于给后面铺路。
2. **B 组是治理**：参考项目用「不改核心、只扩 meta + 钩子 + 声明层」的分寸感解决了外部系统对账、交付物漏交、规范失修、检查不可信四个治理问题 [参考 workflow §4]——面板作为这些数据的天然浏览器，是最合适的产品化载体；关键洞察是**回执文件驱动的状态机**（三态回执 + 失败不阻断 + 补偿命令）这个模式可以跨 Jira/门禁/规范复用。
3. **C 组是体验**：全部可以挂在面板已有能力上做增强（本地停滞规则与 AI 诊断解读、看板、事件流、命令面板），不新建数据面。

排序原则由此而来：**P0 还债 + 立起「等我处理」队列 + Jira 对账（最高频日常）；P1 治理三件套产品化（归档门/回执/规范）+ 视图增强；P2 健康度可视化 + 降噪 + 模板 + 多仓**。详见 02。
