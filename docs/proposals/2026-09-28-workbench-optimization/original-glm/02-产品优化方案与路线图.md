# 02 产品优化方案与路线图

> 日期：2026-09-29。作者：产品经理。
> 前置阅读：同目录 `01-现状盘点与差距分析.md`（差距编号 A1-A6 / B1-B11 / C1-C8 在本文直接引用）。
> 信息来源：research/ 下四份调研笔记（panel-current、ref-workflow、ref-features、oss-patterns）。本文只写方案，不含任何代码。

## 方案主线（一句话）

**把面板从「.trellis 的可视化浏览器」升级为「单人管 AI 代理的指挥台」：先还入口断链的债、立起「等我处理」这一等队列，再把参考项目验证过的治理能力（Jira 对账、归档门禁、检查回执、规范资产、交付物登记）产品化，最后补齐成熟工作台交互（保存视图、健康色点、动态流降噪、任务模板）。**

三条分期原则：

- **P0 = 还债 + 天天疼**：文档与产品不符的债、打开面板第一眼回答不了三件事（代理在干什么/什么等我/今天产出什么）、Jira 状态撒谎没人知道。
- **P1 = 治理能力产品化 + 视图增强**：参考项目用「回执文件驱动状态机 + 机器门禁 + 失败不阻断」解决了四个治理问题，面板是这些数据的天然浏览器。
- **P2 = 体验升级**：诊断结果可视化、事件流降噪、模板沉淀、多仓支持——挂在 P0/P1 立起的底座上择机做。

## 开源交互映射总览

本方案融入 11 类成熟工作台/团队协作交互（要求 ≥4 类，均注明出处产品）：

| # | 交互 | 取自哪个产品 | 用在哪个优化项 |
| --- | --- | --- | --- |
| 1 | 三段式今日视图（进行中/等我处理/今天完成） | Linear My Issues + Things 3 Today（「今天是我选的，不是系统排的」） | P0-1 |
| 2 | 「应收清单」语义（别人对我动作的清单） | GitLab To-Do | P0-1 |
| 3 | 命令面板动作化（导航+任务+动作混合排序、最近置顶） | Linear ⌘K / VS Code Ctrl+P | P0-2 |

## P0：立即做（一个版本内完成）

### P0-1 今日工作台：把概览页重构为「等我处理」指挥首页

**覆盖差距**：A6、C1（并为 A4 收尸）｜**交互来源**：Linear My Issues 三段式 + Things 3 Today 语义 + GitLab To-Do 应收清单

- **解决什么问题**：单人管 N 个 AI 代理，打开面板 10 秒内答不出三个问题——代理在干什么、什么卡住等我了、今天产出了什么（[OSS 1] 的核心判断）。现状 Dashboard 是静态统计墙 [A6]；代理等输入、门禁失败的请求埋在频道事件流里，用户要逐频道翻 [C1]。这直接影响每天的开工路径。
- **交互形态**：概览页重构为三段式：
  1. **进行中**——按频道/AI 代理分组的任务卡（不是按状态，见 [OSS 2]：按代理分组时一列=一个代理的在制任务）；
  2. **等我处理**——一等队列，聚合四类信号：代理在频道请求输入、门禁失败待确认、任务停滞超时（复用效率分析的**本地停滞规则**：`report.ts:167` 按 updatedAt 差值 >3 天判定——AI 深度诊断只是解读层不参与判定；阈值需在面板内做成可配，AI 任务小时级、3 天默认太迟）、失败/需重试；每条可就地动作（打开任务、回一句、重新派发）。
     **前置声明（评审补充）**：①②两类信号今天**没有结构化数据源**——channel 事件的 kind 是自由字符串透传（`channels.ts:29`），现存唯一日志 events.jsonl 里 kind 只有 create/message。P0-1 需先做一次跨组件前置：与 worker/代理端扩展事件协议（新增 kind 语义，首选），或在面板侧定义文本判定规则兜底（有漏识别风险，需在设置中声明）——见「风险与保守假设」第 7 条；
  3. **今天完成**——当天归档/完成的任务流（Things Logbook 语义，给正反馈），只收「今天到期的 + 手动拉进来的」，不自动塞全部活跃任务（[OSS 1]：今天是我选出来的）。
  「今天」语义抄 Things：手动拉焦点 + 到期，两种来源。
  顺手处置 A4：`inbox:new` 死事件路径 [A4] 在这次重构中二选一——要么由「等我处理」队列作为新发送方复活，要么删掉订阅与 reconcile 遗留代码，不允许继续半悬空。
- **依赖的现有能力**：`project:snapshot` 全量推送与 zustand store [面板 二·1]；频道事件流与 `channel:list/action` [面板 二·5]——注意事件 kind 为自由透传、现存仅 create/message，①②类信号依赖前述协议扩展/判定规则前置；效率分析本地停滞规则（`report.ts:167`）与团队页 AI 诊断（解读层）[面板 一·团队协作行]；InboxSlice + inbox-storage 的 reconcile 逻辑可改造复用 [面板 二·21]；Tasks 页任务数据。
- **为什么 P0**：这是日用频率的决胜项——其他一切能力都要从首页被看见；且它不新建存储面：③④类信号是纯已有数据重组，①②类信号需一次轻量的协议/规则前置（风险 7）——成本判断据此修正，**不再宣称「纯已有数据的重新组织」**。[OSS] 把它排在借鉴优先级第一的理由仍然成立（它是被看见的前提），但工期估算要把前置工作算进去。

### P0-2 入口还债：Chat 进侧边栏 + 命令面板扩容

**覆盖差距**：A2、A3、A5｜**交互来源**：Linear ⌘K / VS Code Ctrl+P（命令面板动作化）

- **解决什么问题**：769 行、14 个 IPC 通道的 AI 对话页没有侧边栏入口 [A2]；命令面板缺模型管理/MCP 网关两个页面、动作只有 3 个 [A3]；README 与产品不符伤害信任 [A5]。用户「知道功能存在却找不到入口」是最廉价的改进空间。
- **交互形态**：
  1. Chat 加入侧边栏工作台组（图标+快捷入口，Ctrl+K 保留）；
  2. 命令面板 pages 数组补齐全部页面（含模型管理、MCP 网关、Chat）；
  3. 动作组扩充：新建待办（已有）、**派发任务给频道**、**运行 Flow 模板**（模板库即动作源）、**跑一次健康诊断**、切换保存视图（P1-8 后生效）——两级轻参数化（选中任务 → 选频道）即可，不做命令行语法；最近使用置顶（[OSS 7] 三步补强全收）；
  4. README 同版本修正：services 清单补齐、补 GitLab 集成章节、删掉或兑现 CLI 终端宣称（与 P0-3 同批落地）[A5]。
- **依赖的现有能力**：CommandPalette 现有骨架（页面跳转+任务搜索+3 动作）[面板 一·命令面板行]；`channel:dispatch` [面板 二·5]；Flow 模板库与 `flow:*` 通道 [面板 二·4]；AI 诊断入口 [面板 一·团队协作行]。
- **为什么 P0**：纯还债，几乎零风险、零新数据面，却直接决定「面板能力被发现的比率」；且动作化命令面板是后续所有新功能的统一曝光位（[OSS 7] 原则：命令面板是加速器，新动作 UI 上仍要有出处）。

### P0-3 CLI 命令运行器：接回断链的命令执行能力

**覆盖差距**：A1（同时为 B4 归档预检、B8 命令回执铺路）

- **解决什么问题**：主进程 `cli:run/abort` + `cli:output/done` 事件流 + preload 四方法完整保留，渲染层零调用 [A1]——用户在面板里跑不了任何 trellis 命令，也看不到输出。P1 的归档预检门（B4）必须能「跑命令、拿退出码、展示输出」，这项是它的直接依赖。
- **交互形态**：**不做完整终端页**（README 宣称的那种），做轻量「命令运行抽屉」：任意页面 Alt+R（热键裁定见 03 §P0-3：Ctrl+R 与 Electron/Chromium 默认「重新加载窗口」冲突，本仓现有全局键仅 Ctrl+K/Ctrl+.）或命令面板动作唤出 → 命令输入框（带 trellis 命令历史与常用命令快选，读取 Settings 已有的 cliCommand 配置 [面板 三·1]）→ 实时输出流 + 可中止 + 退出码回显。退出码是关键：它让「命令跑过没有」从人眼判断变成机器可读。Settings 页保留一个入口按钮即可。
- **依赖的现有能力**：全部现成——`src/main/services/cli.ts`、`src/main/ipc/cli.ts`、ipc 注册表 cli 域、preload 的 runCli/abortCli/onCliOutput/onCliDone [面板 二·18]；只补渲染层消费方。
- **为什么 P0**：链路完整只差最后一米，是全场性价比最高的还债；且它排在 P1 归档门禁/回执中心之前做，后者直接复用。

### P0-4 Jira 同步中心：把参考项目的 Jira 桥产品化

**覆盖差距**：B1、B2、B3｜**交互来源**：参考项目 honsky-governance 的 Jira 双向桥全套设计 [参考 §1]

- **解决什么问题**：面板 Jira 页已有导入/状态同步/评论回写 [面板 一·Jira 行]，但三个结构性缺口：① 导入建立的关联没有作为任务元数据落进 `task.json.meta`——**已核实（评审阶段补核代码，不再是「待核实」）**：`services/jira.ts` 182 行纯 HTTP 客户端、全文无 meta 写入，「加入待办池」只落 `.trellis/todos/` 待办（连任务都不建），「AI 规划」只预填规划弹窗文本、jiraKey 仅 UI 徽章（`Jira.tsx:133-143、284`、`PlanningModal.tsx:134`），关联信息活不过一次导入 [B1]；② 同步失败静默丢失，没有三态回执、没有对账，Jira 状态在撒谎没人知道 [B2]；③ 同步靠手点，不是生命周期驱动 [B3]。
- **交互形态**（照参考项目的成熟设计逐条落地 [参考 §1.2、§1.4]）：
  1. **关联即元数据**：导入/关联工单时写 `task.json.meta`（工单 key、IssueId、Fix Version、链接、最后核对时间）；任务卡与任务详情直接读 meta 显示工单号徽章 + 版本 + 外链；写回前做防覆盖守卫（一工单一任务，工单已关联别的任务就拒绝）。
  2. **同步状态列**：任务列表/看板加同步状态灯——绿=已同步、黄=待同步、红=冲突+原因（回执文件驱动，每工单一份 JSON，先写 pending 再收敛 synced/conflict）。
  3. **生命周期自动同步**：面板的「开始任务 / 归档」动作内嵌自动推状态（对应参考项目 after_start→「开发中」、归档→「开发完成」），**失败不阻断本地流程**，落「待同步」回执。
  4. **预检 + 对账**：同步前先展示「远端当前态 → 将执行的流转」再执行（参考项目守卫显式化：允许起点白名单、不倒退、不覆盖人工改动 [参考 §1.2⑥]）；Jira 页加「对账」入口——扫全部关联任务，列出待同步/冲突清单，逐条或一键补偿重试。
  5. **凭据安全**：沿用参考项目模式——口令进操作系统凭据管理器、仓库零口令、面板 Settings 提供连接体检（doctor 式）入口；现有 Settings Jira 连接配置 [面板 一·设置行] 升级接入。
- **依赖的现有能力**：`jira:*` 5 个 IPC 通道（导入/同步/评论已有半成品）[面板 二·15]；Tasks 页归档动作与 DoD 门禁流程；TaskDetail 24 字段编辑（加 meta 展示）；Settings Jira 连接配置。
- **为什么 P0**：面板已有 Jira 页意味着这是三大参考能力里增量最小、见效最快的一个；而「状态可靠性」是每天高频痛点——同步失败无对账等于集成形同虚设。回执三态 + 失败不阻断 + 补偿命令这套模式也会被 P1-5/P1-6 复用，先在这里立标杆。

## P1：下一批（拆两批交付：治理三件套 → 视图与通知）

### P1-5 归档预检门：归档前的 dry-run 门禁 + 补救指引

**覆盖差距**：B4｜**交互来源**：参考项目 database_delivery_gate 的交互设计（dry-run 预检 + 每条 FAIL 带补救命令 + 分层容错）[参考 §2.2④]

- **解决什么问题**：参考项目的交付门是被真实事故逼出来的——门被误删后两单漏上传，靠用户追问才发现 [参考 §2.2⑥]。面板归档按钮没有机器预检，「交付物齐不齐、检查做没做」靠 AI 自觉。归档是 Trellis 流程里唯一不可逆的动作（移目录、置 completed、清指针），恰恰最需要门。
- **交互形态**：归档按钮改为两段式——点击先跑 **dry-run 预检**，弹出红绿灯清单：
  - 绿：全部通过，确认归档（可勾选记住结果，短期内不再预检同类项）；
  - 黄：警告不拦（如「盘上存在同单号但未登记的交付物」——参考项目同款分层容错：无交付物零打扰、未登记只 WARN、登记错误才 FAIL）；
  - 红：阻断 + **每条 FAIL 附补救指引 + 一键复制补救命令**（补救命令经 P0-3 命令运行器可直接执行）。
  预检项从参考项目的门逐条翻译：交付物存在性/路径命名/单号一致性/上传回执在文档中的登记（若 P1-9 交付物中心已上线则连它一起校验）、DoD 检查清单完成度、检查回执是否有效（连 P1-6）。
- **依赖的现有能力**：P0-3 命令运行器（跑预检命令拿退出码）；Tasks 页现有归档动作与 DoD 门禁（DoDModal）[面板 一·任务看板行]；`task.json.meta`（P0-4 落地后提供单号等校验基准）。
- **为什么 P1 且排 P1 首位**：它是治理三件套的地基——门禁交互（红绿灯+补救指引+分层容错）确立后，P1-6 回执与 P1-9 交付物都挂进这个门。**不改 Trellis 本体**：参考项目为实现阻断给 task_store.py 打了补丁 [参考 workflow §2.5]，面板不需要——预检发生在面板层（归档按钮先跑门再调 CLI），天然阻断；边界见「风险与保守假设」第 2 条。

### P1-6 检查回执中心：check-report 结构化展示 + 回执新鲜度

**覆盖差距**：B8（顺带 B7）｜**交互来源**：参考项目回执文化（规则逐条回执、验证回执可复用、未查必须显式标「未查」）[参考 workflow §2.9]

- **解决什么问题**：AI 代理说「检查过了、符合规范」，人只能选择信或去读原始 markdown。参考项目把检查做成「规则→结论→依据（行号引用）」的结构化回执，且实现阶段的验证回执在代码未变时可被检查阶段引用、不重跑 [参考 workflow §2.9]——这套「可验证的信任」正是单人管 AI 最缺的东西。
- **前置声明（评审补充）**：check-report.md 是参考项目**工作流定制的产物，本仓标准 Trellis 0.6.17 流程并不产出它**（本仓 `.trellis/tasks` 与 archive 下 find 零实例）。P1-6 的完整前置是把「检查逐条回执」约定移植进本仓工作流（check 阶段产出结构化报告）——这属流程约定工作而非面板代码；移植落地前，本功能在本仓将长期停留在「无回执态」（UI 设计已把它做成正常态而非报错），属于预期行为。
- **交互形态**：
  1. 任务详情页新增「检查回执」区块：解析任务目录 check-report.md，按规则逐条列出「已查（通过/发现问题）/未查」、每个检查点的依据引用、实际跑过的验证（命令、退出码、覆盖范围）、阻断项单独拎出；
  2. **回执新鲜度**：回执关联的代码文件在回执生成后有变更 → 回执标记失效（灰显+提示重新检查）——把参考项目「代码没变才可引用」的约定变成机器判定；
  3. 顺带透出 B7：任务的 implement.jsonl/check.jsonl 上下文清单解析成「这个任务读了哪些规范、为什么」列表（每行 `{file, reason}` 原样呈现），没配规范也能一眼看出。
- **依赖的现有能力**：project:snapshot 里的任务文件数据；ArtifactViewer 多标签查看器（Markdown/代码）[面板 一·产物查看器行]；P0-3 命令运行器（「重新验证」动作的出口）。
- **为什么 P1**：解决的是「AI 可信度」这个指挥台的根本问题，且直接增强 P1-5 归档门的预检项（回执有效=门放行条件之一）。排 P1 而非 P0，因为它的前置是把 check 回执约定移植进本仓工作流（见上，属流程约定非面板代码），且归档门先立框架它才有挂载点。

### P1-7 spec 规范资产页：从文档树到有生命周期、有路由的资产库

**覆盖差距**：B6、B7｜**交互来源**：参考项目规范双轨制全套（rules 严准入 / business 登记制 / index 路由表 / validate_spec 机械门 / 增长健康度）[参考 §3]

- **解决什么问题**：规范库现状只是「能看能编辑的目录树」[B6]。参考项目证明规范是**有准入轨道、有状态、有健康度的资产**：rules 严准入防污染、business 登记制防失修（每月清账）、index 是路由表而非目录页（基线必读 + 业务命中两层加载，未命中必须显式写「无命中」防糊弄）[参考 §3.1、§3.3]。面板用户看不到这些结构，规范库退化为「一堆 md」。
- **结构前提（评审补充）**：三轨（rules/business/guides）是参考项目的定制结构；**本仓 `.trellis/spec/` 现状是按包平铺的 md**（backend 下 15 个文件、无 rules/business 子目录，另有 frontend/shared/guides/big-question 目录）。面板按通用工具设计：按目录形态与 frontmatter 探测轨道——有轨道结构的项目按轨分组，无轨道结构的项目**降级为「按包平铺视图 + 轨道迁移引导」**，不能按参考项目结构硬套成空架子。
- **交互形态**：
  1. **按轨道分组**：spec 页目录树升级为 rules / business / guides 三轨分组（仅在探测到轨道结构时启用，见上「结构前提」），business 条目读 frontmatter 显示 `status: verified/pending`，pending 黄标；
  2. **路由表视图**：按「改动类型 → 必读清单」组织入口（解析 index.md 的路由表），替代平铺文件树作默认视图；
  3. **一键体检**：跑机械校验（frontmatter 必填字段、文件头元信息、business 必须有触发场景章节、index 链接可达——参考项目 validate_spec 的检查项 [参考 §3.3]），结果进红绿灯清单（复用 P1-5 的门禁组件）；
  4. **增长健康度**：rules 近 30 天变更 >5 个文件时告警「严准入在失效」（同参考项目算法）；business 每月清账提醒挂进 P0-1 的「等我处理」队列——治理待办进入日常循环，这是两个 P0/P1 项的漂亮联动；
  5. 收尾的规范沉淀入口：任务收尾时提示「有无长期约束要沉淀」，按轨道分流（rules 走严准入流程需用户独立确认，business 登记制直接提交）。
- **依赖的现有能力**：Spec 页现有目录树/渲染/在线编辑/引用统计 [面板 一·规范文档行]；`spec:backlinks` IPC [面板 二引]；P0-1 「等我处理」队列（清账提醒）；P1-5 门禁组件（体检红绿灯）。
- **为什么 P1**：规范失修是慢刀子（不像 Jira 撒谎天天疼），但规范库是 AI 输出质量的供给侧——规范的 routing 做对了，每次任务注入的上下文才对。它依赖 P1-5 的门禁组件与 P0-1 的队列挂载点，故排 P1 中段。

### P1-8 保存视图与频道分组看板

**覆盖差距**：C2、C3｜**交互来源**：Linear 保存视图 + Linear 任意字段分组看板 [OSS 2、3]

- **解决什么问题**：高频横切视角（「卡住>N 小时」「某频道的全部任务」「失败/需重试」「等我处理」）每次手工筛 [C2]；看板只按状态分组，回答不了「每个代理背了多少活」[C3]。
- **交互形态**：
  1. 可视化筛选器（字段+条件组合，不学裸搜索语法）→ **保存为侧栏入口**，可设默认分组排序；预置四个开箱视图：等我处理 / 卡住超时 / 按频道 / 失败重试（[OSS 3] 点名的四个）；
  2. 看板「分组依据」扩为任意字段：按状态（现状）、按优先级、**按频道/代理**——按频道分组时一列=一个代理的在制任务，看板同时成为负载面板，与团队页负载观察打通；
  3. 保存视图进命令面板动作（P0-2 的动作位预留在此生效）。
- **依赖的现有能力**：Tasks 页看板/列表/泳道多视图（同源数据已满足 [OSS 2] 关键原则）；zustand store 序列化；Sidebar 可折叠导航 [面板 一]。
- **为什么 P1**：[OSS] 优先级第二，但「等我处理」预置视图已被 P0-1 今日工作台覆盖了最痛的一个，此项边际收益后移半批；实现便宜（视图即配置），放 P1 后半批打头。

### P1-9 共享交付物中心一期：唯一正本 + 登记 + 校验

**覆盖差距**：B5｜**交互来源**：参考项目共享 SQL 脚本中心三件套（唯一正本路径 + 共享登记 ID + 机器校验）[参考 §2]

- **解决什么问题**：面板管理的项目产出的交付物（SQL 脚本、迁移文件、配置变更、发布说明）散落在任务目录和各处，没有「正本在哪、交没交、交给谁」的登记链 [B5]。参考项目的教训：靠 AI 记得交付，漏了要靠用户追问才发现 [参考 §2.2⑥]。
- **交互形态**：
  1. **交付物登记**：任务详情新增「交付物」区块——声明正本路径（约定唯一保存位置，如 SQL 在业务仓版本目录，不进任务目录 [参考 §2.2⑤]）、上传/提交后登记回执 ID、登记时间；一键校验「路径存在 / 命名合规 / 单号一致 / 回执已登记在文档」；
  2. **登记浏览器**：按版本/类别分组的交付物清单，条目详情含修订历史与 diff 视图（参照参考项目 list/show/history/diff/revise 的 CLI 面 [参考 §2.2③]，做成面板 UI）；
  3. **接入门禁**：有交付物声明的任务，归档预检（P1-5）自动校验登记完整性——无声明零打扰、有声明未登记才拦截（分层容错同参考项目）。
- **依赖的现有能力**：task.json.meta（登记元数据锚点，P0-4 建立）；P1-5 归档门；ArtifactViewer（diff/代码查看）；project:snapshot 文件扫描。
- **为什么 P1 且放批末**：**保守假设明说**——参考项目的共享中心是团队共享 PostgreSQL 服务 [参考 §2.1]；面板是单人桌面工具，一期按「仓库内登记文件（.trellis 下 JSON 清单）」做本地登记与校验，不引入数据库服务；二期若多仓/团队共享场景成立（P2-14 多仓支持上线后），再评估接共享服务。因此一期价值依赖归档门先立（P1-5），排 P1 收尾。

### P1-10 通知中心：两类通知、分组可处理

**覆盖差距**：C1 的 Inbox 形态（数据底座已由 P0-1 建立）｜**交互来源**：Linear Inbox + 飞书盒子（统一收口）[OSS 6]

- **解决什么问题**：P0-1 解决「打开面板看见什么」，但代理在后台等输入/门禁失败时用户不在面板前——需要主动通知；而 AI 代理一天几百条 progress，不克制的话用户会全局静音（[OSS 6]：绝不能让 progress 产生 toast）。
- **交互形态**：通知只留两类：
  1. **需要我动作**：代理等输入、门禁失败、卡住超时、任务失败——弹系统 toast + 托盘角标 + 进通知中心；**按任务分组合并**（同任务十条动态归一条）；每条可就地处理：打开任务、回一句、重新派发（动作化是 Linear Inbox 的精髓）；低价值类型支持自动归档规则；
  2. **摘要**：今日完成/失败汇总，定时一份，不弹。
  「等我处理」队列（P0-1）与通知中心是**同一份数据的两个视图**——队列是拉、通知是推。飞书式按应用分类的通知偏好矩阵不做，只做「这三类提醒 + 其余进流」的开关。
- **依赖的现有能力**：托盘常驻 + tpanel notify 深链 + Toasts [OSS 6 已核]；P0-1 的等我处理数据底座；channel 事件流。
- **为什么 P1 收尾**：通道全现成、缺的只是策略与形态；但它依赖 P0-1 先把「什么算需要我处理」的数据语义立稳，否则通知只会变成噪音源。

## P2：远期（底座稳了择机做）

### P2-11 健康色点矩阵 + 吞吐趋势

**覆盖差距**：C4、C5｜**交互来源**：GitLab epic 三档健康度 + Linear cycle 趋势 [OSS 9]

- **解决什么问题**：AI 诊断有停滞归因/负载观察的引擎，但没有「一屏扫全盘」的呈现 [C4]；效率分析是单点数值，看不出项目在变好还是变坏 [C5]。
- **交互形态**：健康矩阵（行=频道/代理，列=任务，格子里三档色点：正常/停滞/等输入/失败）挂团队页与概览；吞吐趋势三条小线（完成速率、中位交付时长、卡住时长分布的 7/30 天趋势）。燃尽图不做（[OSS 9]：对小时级 AI 任务是仪式感图表），唯一例外是 Jira 冲刺页可放一张只读的。
- **依赖的现有能力**：团队页 AI 深度诊断、效率分析（交付周期/流转热度/停滞预警）[面板 一·团队协作行]——数据源全有，纯可视化升级。
- **为什么 P2**：锦上添花——诊断数值已在，矩阵与趋势是呈现层升级；依赖 P1-8 保存视图先行验证「按频道」视角的真实使用率。若用户重度使用 Jira 冲刺，可提前。

### P2-12 动态流降噪 + 快捷指令

**覆盖差距**：C6、C7｜**交互来源**：GitLab issue 活动时间线两层结构 + GitLab quick actions + 飞书三角色语义翻译 [OSS 4、5]

- **解决什么问题**：AI 代理一天几百条 progress 淹没状态变更与关键事件，流不可读 [C6]；人对代理下指令要切到派发台，没有轻量通道 [C7]。
- **交互形态**：动态流两层化——系统事件压成灰字 diff 一行（「状态 planning→in_progress · 3 分钟前」，复用面板已有 Diff 语言 [OSS 5]）；连续 AI progress 自动折叠成「· · · 47 条进度消息」可展开；事件类型过滤器（只看：状态/门禁失败/等待输入）。评论即指令：任务评论框支持 `/retry`、`/reassign <频道>`、`/done`、`/拆分子任务`，面板翻译成动作执行并回帖确认（GitLab quick actions 的回执模式）——把派发台的结构化指令能力下沉到任意任务的评论区。指派语义按 [OSS 4] 翻译：执行代理 + 我（提出人兼默认关注人），到期/失败提醒我。
- **依赖的现有能力**：Channels 页事件流与 `channel:send/dispatch` [面板 二·5]；团队页动态流 [面板 一·团队协作行]；派发台结构化指令生成 [面板 一·AI 频道行]。
- **为什么 P2**：骨架已在（事件流、派发台），降噪与指令是「量大到受不了才疼」的优化——放 P2 等真实使用强度说话；若频道日消息量先爆，可提级。

### P2-13 PRD 模板库与五类信息标注

**覆盖差距**：C8｜**交互来源**：GitLab 仓库模板（模板即仓库文件）+ 参考项目 prd-writer 技能（五类信息区分）[OSS 8、参考 workflow §2.10]

- **解决什么问题**：每次 AI 规划都从白纸开始，没有 bug/功能/调研三类 PRD 骨架 [C8]；参考项目 prd-writer 强制区分「源事实/代码事实/用户决策/AI 推断/待确认」五类信息、不许把面向用户的 PRD 原文直接复制进任务 [参考 workflow §2.10]——这个纪律面板没有任何支撑。
- **交互形态**：模板文件放 `.trellis/templates/`（学 GitLab：随 git 版本化、随项目共享，不藏应用设置里）；PlanningModal/IntakeModal 建任务时下拉选模板套骨架，默认字段值预填；PRD 编辑器支持五类信息的字段化标注（段落在编辑器里标类别，渲染时按类别着色/过滤「待确认」清单）。克制点：常用模板三个以内，不做模板分类管理树（[OSS 8]：模板一多就没人用）。
- **依赖的现有能力**：PlanningModal/IntakeModal [面板 一·非导航视图表]；ArtifactViewer/MarkdownView；应用内 AI `ai:prdDraft` [面板 二·6]。
- **为什么 P2**：速记/一句话直通车的路线（[OSS 8] 判断「方向完全正确」）已覆盖 80% 场景，模板是长尾提效；五类标注依赖用户形成标注习惯，教育成本高，放远期。

### P2-14 多仓工作区支持

**覆盖差距**：B11｜**交互来源**：参考项目 packages 双仓声明 + run_package_command 安全转发 + 边界校验 [参考 workflow §2.7]

- **解决什么问题**：面板当前按单仓假设设计；若用户管理的项目像参考项目一样「治理仓 + 业务子仓」，任务的包归属、命令在哪个仓执行、各仓 branch/head/dirty 状态都无处落 [B11]。
- **交互形态**：读取 config.yaml 的 packages 声明 → 任务详情显示包归属与对应仓状态（branch/head/dirty）；P0-3 命令运行器支持「按包路由执行」（歧义时要求显式指定——照抄参考项目 run_package_command 的防漂移设计）；架构图页或设置页加多仓边界体检（治理仓不得 track 子仓路径、子仓必须有 .git）。
- **依赖的现有能力**：P0-3 命令运行器；config.yaml 读取（Dashboard 已展示 config 概览 [面板 一·概览行]）；Git 能力 `git:taskInfo` [面板 二·16]。
- **为什么 P2**：面板当前用户（本仓）是单仓项目，此项目化只有「面板被用于多仓项目」时才回本——明确写为条件触发项，不做投机投入。

### P2-15 工作流定制体检（挂 Studio 定制中心）

**覆盖差距**：B9、B10｜**交互来源**：参考项目「能用文档解决就不改代码」的声明层定制 + template-hashes 校验方法 [参考 workflow §2.1、§2.2]

- **解决什么问题**：`.trellis` 文件被本地改过多少、`trellis update` 会不会丢定制，用户心里没底 [B10]；workflow.md 里挂的团队约定/本地规则只能读 700 行文档 [B9]。参考项目两次跨版本升级没丢定制，靠的就是模板哈希清单 [参考 workflow §2.2]。
- **交互形态**：Studio 新增「工作流体检」section——对照 `.template-hashes.json` 列出「本地已修改 / 模板原样 / 本地新增」三类文件清单；升级前给 diff 预览与风险提示；workflow.md 等大文档提供「本地改动 vs 官方模板」的对照视图（团队约定一眼可见，覆盖 B9）。
- **依赖的现有能力**：Studio 八个 section 骨架 [面板 一·定制中心行]；ArtifactViewer diff 视图。
- **为什么 P2**：信息价值高但紧迫性低（升级是低频事件）；且依赖用户像参考项目那样真的做了本地定制才有内容可显——本仓面板项目自身是标准 0.6.17，属于「为未来定制铺路」项。

## 风险与保守假设（如实声明）

1. **静态盘点的边界**：面板调研未运行应用，所有「依赖的现有能力」基于代码链路存在 [面板 三]；每批实施前需先跑冒烟验证对应链路。
2. **归档门的边界**：P1-5 的阻断发生在面板层（归档按钮先预检再调 CLI），**用户绕过面板直接跑 trellis CLI 归档则门不在**——这是与参考项目（给 task_store.py 打补丁实现进程内阻断 [参考 workflow §2.5]）的明确取舍：不改 Trellis 本体、接受旁路风险；若实际使用中旁路频繁，再评估补丁方案。
