## 一、P0 优化项端到端流程

### P0-1 今日工作台：等我处理信号的聚合与就地处理

```
 信号源                            分类                       合并                    出口
┌─────────────────────┐   ┌──────────────────────┐   ┌──────────────────┐   ┌─────────────────────┐
│ 频道事件流            │   │ 信号分类器: 四类       │   │ 「等我处理」队列    │   │ 就地动作 (卡片上)     │

**设计要点**：①「等待输入」信号从频道事件流里提出来是一等队列，不再埋在流里 [01 C1]；②同任务多信号合并成一张卡，避免一天几百条把人训练成静音 [OSS 6]；③B/C 动作失败时**绝不能误删卡片**——队列是信任源；④A4 收尸：旧 `inbox:new` 死事件路径在本次重构中删除，语义由本队列接管 [01 A4]；⑤**①②类信号有跨组件前置**——channel 事件 kind 是自由字符串透传（`channels.ts:29`）、现存唯一日志 kind 仅 create/message，「等待输入/门禁失败」需先扩展事件协议（首选）或落面板侧文本判定规则（兜底），工期不能再按「纯重组」估 [02 P0-1 前置声明、风险 7]；⑥**③类信号是本地规则不是 AI 引擎**——停滞判定来自效率分析的本地计算（`report.ts:167`，updatedAt 差值 >3 天），团队页 AI 深度诊断只是解读层（`Team.tsx:301` 注释自证），本地计算不存在「引擎不可用」的降级问题；阈值需在面板内做成可配（AI 任务小时级，3 天默认太迟）。

        ├─② 任务 ──────────► [ 打开任务详情 ] ──────────────► ( 面板关闭 )
        └─③ 动作
             │
             < 需要参数? >
              ├─ 否 (新建待办 / 重扫描 / 切主题 / 健康诊断 / 运行命令)
              │     └──► [ 直接执行 ] ──► 成功: Toast 反馈 ──► ( 关闭 )

                          1/2 选任务 →(→) 2/2 选频道/模板 → Enter
                          （两级选完参数必然完整，无需再判完整性——原稿此处
                            有个多余的 <参数完整?> 判断框且只画了「是」分支，
                            评审指出后删除；Esc 随时可退，无断头路径）

                              ▼
                          [ 执行 ] ──► 成功: Toast「已派发到 worker-1」──► ( 关闭 )
                              │

### P0-4 Jira 同步中心：三条流程

**a. 导入/关联（防覆盖守卫）**：

```
( Jira 页选中工单 HONSKY-xxx ) ──► ( 导入转任务 )
        │
        ▼
   < 防覆盖守卫 · 写 meta 前逐项检查 >        [参考 bridge.py:198-228 的守卫语义]
        ├─① 工单已关联别的任务? ──是──► [ 拒绝导入·提示已关联 09-xx-yyy ]
        │                                  └► ( 打开那个任务 ) / (·强制切换·二次确认，即 --switch 语义 )
        ├─② 任务已关联别的工单? ──是──► [ 拒绝·提示先解除关联 ]
        └─③ 无冲突
             ▼
        [ 写 task.json.meta: 工单key / IssueId / Fix Version / 链接 / 最后核对时间 ]
             │
             ▼
        [ 任务卡与任务详情显示 [HONSKY-xxx] 徽章 + 版本 + 外链 ]
             │
             ▼
        ( 完成 · 关联随任务入库随 git 走 )
失败: Jira 不可达 ──► [ 提示连接失败 + ( 体检 ) ] ──► 停止，不建任务
       （导入是显式动作，失败即停；与生命周期同步的「不阻断」不同，两者刻意不一致）
```

**b. 生命周期自动同步（开始/归档时自动推状态）**：

```
   ( 任务看板: 开始任务 )              ( 任务看板: 归档 · P1-5 门全绿后确认 )
          │                                      │
          ▼                                      ▼
   ★ [ 本地动作先行执行并生效 ]           ★ [ 本地归档先行执行 ]
          │                                      │
          └──────────────┬───────────────────────┘
                         ▼
        [ 自动推送: 开始→「开发中」 · 归档→「开发完成」 ]
                         │
                         ▼
                  < 同步前预检 >
                   ├─① 任务未关联工单? ──是──► 静默跳过（零打扰）
                   ├─② 远端状态在允许起点白名单? ──否──► [ 落 conflict 回执+原因 ]
                   │                                         └► 今日工作台黄条 + 同步列红灯
                   ├─③ 目标流转唯一匹配? ──否──► [ 落 conflict 回执 ]
                   └─④ 通过 ──► [ 执行流转 → 回读确认 ]
                                    │
                                    ├─ 成功 ──► [ 落 synced 回执 · 同步列绿灯 ]
                                    └─ 网络/服务失败(失败路径) ──► [ 落 pending 回执 ]
                                                                    └► 对账可补偿，见 c
        ★ 同步永远不阻断本地流程——开始/归档已生效，失败只进回执与对账 [参考 §1.1]
```

**c. 对账补偿（reconcile）**：

```
( Jira 同步中心 · 对账 tab 打开 ) 或 ( 一键补偿重试全部待同步 )
        │
        ▼
[ 扫描全部关联任务的回执 · 每工单一份 JSON · 三态 ]
        │
        ▼
   < 回执状态? >
    ├─ synced   ──► 计入 ● 计数，不动
    ├─ pending  ──► ( 重试 ) / 批量一键补偿 ──► 逐单重走 b 的预检→执行
    └─ conflict ──► [ 展示原因（不在白名单 / 工单key变了 / 版本不再包含 / 人工动过） ]
                      │
                      └► ★ 只提供「打开工单核对」与「标记冲突留回执」，不自动补偿、不提供强推
                          人工在 Jira 处理后 → ( 重新同步 ) → 回执收敛 synced
失败: 扫描时 Jira 不可达 ──► [ 列表标注「远端不可达，仅展示本地回执」· ( 体检 ) ]
```

**设计要点**：①回执文件驱动状态机（pending → synced/conflict）是三条流程共用的底座，P1-5/P1-6 会复用这个模式 [01 三·2]；②「导入失败即停、同步失败不阻断」的分裂是刻意的：前者是用户显式动作（必须给结果），后者是后台自动化（不能挡干活）[02 P0-4]；③冲突永远走人工核对——守卫规则「不猜、不倒退、不覆盖人工改动」直接翻译成 UI 上「没有强推按钮」[参考 §1.2⑥]。

> 场景里的「团队」= 我（唯一人类）+ AI 代理。多人指派、审批流明确不做 [01 明确不追]。

  · 回一句发送失败 ──► Toast 报错·队列卡保留 ──► 重试

**解说**：这是面板的主循环——「输入即结构化」（一句话→指令）→ 代理干活 → 异常时找得到我 → 我的最小干预（回一句/重新派发）→ 双侧收尾（本地归档 + Jira 自动推）。三个关键节拍：**派发后不打扰**（progress 只进列表不弹 [OSS 6]）、**等输入必须找到我**（队列+toast 双保险）、**收尾自动对账**（失败不阻断，对账兜底）。

  · 门只黄不红（如「盘上存在未登记同号交付物」）──► 不拦截·确认按钮可用·可勾选记住 [参考 §2.2④]
  · 修复后回执又失效（代码再变）──► 循环回到「看回执」，直到回执有效且门全绿
  · 我不信任回执 ──► (· 查看原始 check-report.md ·) 全文可读 [02 P1-6]
  · 预检命令本身失败 ──► 门显示「预检不可用」+ 可跳过但记 journal [03 §P1-5]
  · ★ 绕过面板直接跑 CLI 归档则门不在——已知取舍 [02 风险 2]
```

**解说**：这个场景把「AI 说检查过了，人只能信」变成「机器可验证的信任链」：门（P1-5）发现回执失效 → 回执（P1-6）给出问题与依据（行号引用）→ 修复走正常派发 → 新回执生效 → 门放行。归档是 Trellis 里唯一不可逆的动作，恰好是被门保护的那个 [02 P1-5]。check 代理的边界（只修机械性问题、业务问题只报告 [参考 workflow §2.9]）在回执里体现为「发现问题」条目而不是自动改完。
