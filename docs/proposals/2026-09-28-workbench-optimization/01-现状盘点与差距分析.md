# 01 现状盘点与差距分析

> 修订：2026-09-29。依据现有提案调研与关键代码路径静态核对；未运行桌面应用。本文将“代码已存在”与“产品应保留”分开陈述。

## 一、用户实际在做什么

典型路径是：用户在 Codex、Claude Code 或其他运行 Trellis 的环境中讨论需求，按项目工作流创建任务、启动会话、实现、检查并归档。打开 trellis-panel 时，用户需要确认：

1. 哪些任务和材料已经写入 `.trellis/`，目前记录的阶段是什么；
2. 某个任务的 PRD、设计、实施计划、检查记录、规范引用和归档材料在哪里；
3. 最近观察到什么变化，有无读取失败、文件缺失或相互矛盾的记录；
4. 如何快速回到原始文件或外部工作环境继续处理。

面板不拥有外部代理的会话生命周期。任务标为 `in_progress` 只能说明任务记录如此，不能推断“代理正在工作”；目录修改时间也不是代理最后活动时间。

## 二、已经具备的基础

| 基础 | 已核对的实现 | 对当前定位的价值 |
| --- | --- | --- |
| 项目快照 | `src/main/services/scan.ts` 扫描任务、归档、规范和会话文件；渲染层共享 snapshot | 多个阅读视图可基于同一份本地事实 |
| 任务阅读 | `src/renderer/src/pages/Tasks.tsx` 有看板、阅读、列表、泳道；`TaskDetail.tsx` 显示字段与部分 Git 信息 | 可形成“概览 → 任务 → 原件”的查阅链 |
| 文件查看 | `ArtifactViewer`、规范文档页、归档页、知识库 | 可复用现有 Markdown、代码与归档阅读能力 |
| 外部关联 | Jira、GitLab、频道和 shell 打开能力 | 在有明确关联时提供跳转与来源说明 |
| 搜索入口 | 命令面板已有页面与任务搜索 | 补齐入口比另建一套导航成本低 |

这些是静态代码事实，不代表每条链路已经通过运行时验证。

## 三、必须先纠正的三个认识

### 1. AI 规划接口存在，但面板还不是 Trellis 规划平台

`src/main/services/plan.ts` 可以检索资料并调用配置的模型生成结构化计划；`PlanningModal.tsx` 允许人工修改后创建任务。但这是一次生成与确认流程，不是持续研讨、决策记录、上下文配置及代理接手的完整 Trellis 流程。`src/main/state.ts:createTaskRecord` 当前只创建目录和 `task.json`，并未在该路径写入 `prd.md`；规划弹窗的“PRD 已写入”成功文案不准确。这个现有问题值得单独修复，但不能成为本轮把面板扩为 agent 平台的理由。

### 2. 面板写状态和归档，与 Trellis 生命周期不同

`src/main/services/scan.ts:updateTaskRecordAt` 直接写 `task.json.status`；`src/renderer/src/pages/Tasks.tsx` 的拖拽和状态选择会调用它。Trellis 的 `task.py start` 还涉及上下文检查和当前 AI 会话的活动任务指针。`src/main/ipc/tasks.ts` 的面板归档直接移动目录；Trellis 自身归档还处理完成状态、会话、子任务与钩子。因此“面板点开始/归档”不能被设计为 Trellis 正式状态流转的同义词。

### 3. Jira 关联并非完全不落元数据

原稿 B1 只查 `src/main/services/jira.ts`，进而断言面板不写 `task.json.meta`，证据范围不够。`src/main/state.ts:createTaskRecord` 接收 Jira key 时会写 `meta.jiraKey/jiraUrl`，`src/renderer/src/pages/Jira.tsx:linkExisting` 也会通过任务更新写入这些字段。**“加入待办池只写待办文件”属实；“所有导入和关联都不持久化”不属实。** 未来若做 Jira 对账，应先逐条区分入口与数据形态，不沿用旧 B1 工作量估计。

## 四、按当前定位重排的问题

| 优先级 | 用户遇到的情况 | 设计要求 |
| --- | --- | --- |
| P0 | 看板状态、代理消息、Jira 状态混在一起，容易误以为整条流程已完成 | 区分任务记录、频道事件和外部系统；标明来源及读取时间 |
| P0 | 主界面提供创建任务、拖状态、完成与归档，容易把局部文件写入误认成 Trellis 正式动作 | 在目标设计中从任务主界面移除这些入口；保留清晰的外部继续工作路径 |
| P0 | 任务已有材料但需要在多个页面或目录间找，缺失材料也不醒目 | 任务详情集中展示已有文件、缺失与读取失败，并能打开原件 |
| P1 | Chat 等页面可达性弱，命令面板有漏页、名称不一致 | 补齐导航与搜索，统一“待办池”等术语 |
| P1 | 高频查阅角度需要重复筛选，列表信息密度不稳定 | 保存本地阅读视图、筛选与排序；不修改任务文件 |
| P1 | 概览页静态统计多，用户不能迅速找到最近有文件变化的任务 | 将首页改为可核实的项目快照与近期变化入口 |

## 五、原方案哪些需求暂不成立

- **“等我处理”代理请求队列**：当前频道事件缺稳定的结构化“等待输入/门禁失败”语义。关键词猜测不能作为可信收件箱；没有数据时不可显示“没有等你处理的事”。
- **按代理显示在制任务和用时**：现有任务、频道、worker 之间没有经过验证的稳定绑定；不能由 `task.json.status` 或任务目录 mtime 推算代理是否在线。
- **面板驱动的 Jira 生命周期同步**：任务正式 start/archive 并不由面板主界面执行；若需要自动化，应从实际 Trellis 生命周期机制设计，而不是在看板按钮上附加同步。
- **归档预检门、检查代理重派、交付物阻断**：它们需要外部工作流或定制协议产出权威结果。面板可阅读已存在的报告和回执，当前不承诺生成或执行门禁。
- **spec 三轨、SQL 登记、多人工作台范式**：这些是参考项目的本地约定，不能因参考项目有而列成本项目的缺口。

## 六、术语边界

| 词 | 本方案含义 |
| --- | --- |
| 待办池 | `.trellis/todos/` 中尚未成为正式 Trellis 任务的需求素材；不等于“代理等我回复” |
| 任务阶段 | 从任务文件读取的 `planning / in_progress / review / completed` 等值；不等于代理运行状态 |
| 已归档 | 扫描到任务位于归档目录；与“状态字段写成 completed”分别呈现 |
| 最近变化 | 观察到的文件变化及其时间；不推断谁改了、代理是否还在执行 |
| 资料缺失 | 期望文件不存在、尚未生成或扫描失败；三者应分别说明，不自动判任务失败 |

本轮方案据此转向“提高 Trellis 工作流的可见性、可追溯性和阅读效率”。原稿的产品类比与交互案例仍可作为灵感，不能替代上述边界。
