# 「工作台 + 团队协作」成熟交互模式清单（供 Trellis Panel 工作台优化借鉴）

- 调研对象：Linear、GitLab、OpenProject、Focalboard、AppFlowy、AFFiNE、飞书/Lark 套件；补充参考 Things 3、Todoist、GitHub Projects。
- 方法：基于产品公开使用知识整理，本任务未逐一打开产品实测；没把握的细节标「待核实」。
- 目标面板背景（引用自本仓库 README 与 git 记录）：Windows 桌面 Electron 面板、单人为主，通过「AI 频道 + 任务派发台」（README.md:28）驱动 AI worker 干活；已有看板/阅读/列表/泳道四视图（README.md:22）、任务详情 Diff（README.md:23）、团队页动态流/效率分析/AI 深度诊断（README.md:30）、Jira 冲刺（README.md:31）、托盘常驻（README.md:34）、Ctrl+K 命令面板（README.md:36）、速记窗 Alt+N（提交 cd02fa1）。
- 适配判断统一口径：单人 + 多 AI 代理。核心问题永远是三个——**代理在干什么、什么卡住等我了、今天产出了什么**。

## 1. 个人工作台 / 今日视图

**做得最好的：Linear。** 团队产品里没有比它更克制的「我的视角」；个人软件的金标准是 Things 3 的 Today（补充参考）。次选：GitLab To-Do 页、OpenProject「我的」页。

**交互长什么样：**
- Linear 打开先看侧栏三块：Inbox（要处理的通知）→ My Issues（预设分区：Todo / In Progress / Created…，还有「Active」聚焦进行中）→ 各团队视图。每个分区就是一个过滤好的清单，进去即干活，没有仪表盘装饰。
- Things 3 的 Today 只放两种东西：今天到期的、我手动扔进今天的；完成的自动进 Logbook，今天页永远干净。核心是「今天是我选出来的，不是系统排出来的」。
- OpenProject「我的」页相反：工时、我关注的、新闻、多个报表块拼成大仪表盘——信息全但无立场。

**适配判断：非常适合，且应是首页。** 单人管 AI 代理，打开面板第一眼要回答「哪些代理在干活 / 什么在等我 / 今天完成了什么」。建议结构直接抄 Linear My Issues 的三段式：
1. **进行中**（按频道/代理分组，替代「指派给我」）；
2. **等我处理**（代理请求输入、门禁失败、评审待定——这就是今日视图的灵魂）；
3. **今天完成**（Things 的 Logbook 语义，给正反馈）。
「今天」语义抄 Things：手动拉焦点 + 到期，不要自动把所有活跃任务塞进来。

**不适合的：** OpenProject 式通用仪表盘（概览统计本面板已有，README.md:21，不必重复）；「按团队/按人切换」的多视角——只有一个用户，浪费导航位。

## 2. 看板与多视图（列表 / 表格 / 时间线）

**做得最好的：分组看板 = Linear；「一份数据多个视图」= Focalboard；时间线/甘特 = OpenProject。** AppFlowy、AFFiNE 的「同源数据表格/看板/日历切换」与 Focalboard 同类。

**交互长什么样：**
- Linear 看板：列不是写死的「待办/进行/完成」，而是任意字段的分组（状态、优先级、指派人）；拖一张卡到「高优先级」列就是改优先级。卡面极简：ID、标题、头像、标签，hover 出快捷键。每个「分组×筛选×排序」组合可存成视图。
- Focalboard：一个板顶部可建多个视图 tab（看板/表格/画廊/日历），每个视图有独立的 group/filter/sort，切换不丢。它本质是「视图即配置」。注：项目已停止积极维护（Mattermost 约 2024 年起弃用 Boards，具体归档时间待核实），但交互模式仍是被验证过的。
- OpenProject 甘特：最强开源时间线，左表右图联动、拖动条改起止日期、依赖线（基线等高级能力是否企业版权限待核实）。
- GitLab issue boards 补充：支持按 epic 分泳道（swimlanes），本面板的泳道视图（README.md:22）即此类。

**适配判断：看板非常适合（已有），缺的是分组维度。** 现在按状态分，建议把「分组依据」扩成字段：**按频道/AI 代理分组时，一列 = 一个代理的在制任务，看板同时变成负载面板**，与团队页「负载观察」（README.md:30）打通。本面板的大列自动折叠（>8 条只留 5 条，README.md:22）已经是正确的反拥堵设计。
- **列表/表格**：适合批量扫 24 字段（README.md:23），保留。
- **时间线/甘特：不建议投入。** AI 任务周期常是小时级、无排期概念、并行度由代理数决定而非日历，甘特是超重武器。唯一例外：若深度使用 Jira 冲刺（README.md:31），给冲刺一个简单时间轴即可，别做编辑器。
- 关键原则（Focalboard/Linear 共同）：**多视图必须同源数据**。本面板全部来自 `.trellis/` 扫描（README.md:15），天然满足。

## 3. 筛选与保存视图

**做得最好的：Linear。** 次选：OpenProject 的「查询」（筛选+可见列+排序保存为个人/公共查询）；GitHub Projects 的 saved views 同类（补充参考）。

**交互长什么样：**
- Linear：点筛选器 → 按属性加条件（状态=进行中 AND 指派=我 AND 优先级≥高）→ 「Save view」存成侧栏入口，可再设默认分组排序。视图是导航的一等公民，不是搜索框的临时状态。
- OpenProject：查询下拉列出所有保存的查询，链接可直接分享复现同样过滤结果。

**适配判断：非常适合，实现成本低、收益最高。** 单人 + 多代理最大的痛点是横切视角，且都是重复性的：
- 「等我处理」（阻塞在人的任务）；
- 「卡住 >N 小时」（对应停滞预警，README.md:30）；
- 「某频道的全部任务」（盯一个代理的上下文）;
- 「失败/需重试」。
建议：可视化筛选器（字段+条件，不学 GitLab 的裸搜索语法）+ 保存为侧栏入口 + 预置上述四五个开箱视图。保存即序列化进 store，几十行的事，但直接决定面板日用频率。

## 4. 任务指派与 @ 提醒

**做得最好的：指派模型 = 飞书任务（Lark Tasks）；@与快捷指令 = GitLab。** Linear 的 subscribe（不指派也能收动态）是补充。

**交互长什么样：**
- 飞书任务：一个任务三种角色——**负责人**（唯一，对结果负责）、**协作人**（参与执行）、**关注人**（只收进度提醒）；到期对关注人也提醒；列表按「我负责的/我参与的/我关注的/我创建的」切。
- GitLab：评论里 @某人 自动生成对方的 To-Do 通知项；快捷指令（quick actions）在评论框里输入 `/assign @xxx`、`/due 2026-10-01`、`/close`，提交后系统执行并回帖确认执行结果。
- Linear：issue 上 subscribe，之后该 issue 所有动态进 Inbox，不必是负责人。

**适配判断：改造借鉴，语义要翻译。** 人只有一个（me），「指派给谁」=「派给哪个频道/代理」——任务派发台（README.md:28）已经在做这个映射。可借的三个点：
1. **三角色简化成两个**：执行代理 + 我（提出人兼默认关注人）。飞书的「关注人」提醒语义保留：任务到期/失败时提醒我。
2. **「@我」是一等事件**：代理在频道里请求人输入、门禁要人确认，应直接落进「等我处理」队列和通知中心（见模式 6），而不是埋在事件流里。
3. **GitLab 快捷指令模式非常适合 AI 指令场景**：在任务评论里打 `/retry`、`/reassign <频道>`、`/done`、`/拆分子任务`，面板翻译成动作执行——与派发台「结构化指令」思路（README.md:28）一脉相承，等于把派发台能力下沉到任意任务的评论区。

**不适合的：** 多人指派（GitLab 多指派人属付费档，且对单人是制造歧义）、飞书式审批流——跳过。

## 5. 动态流（活动 / 评论）

**做得最好的：任务级活动流 = GitLab issue 时间线。** 次选：Linear 的 issue 活动与团队活动；Focalboard 卡片历史是最小可行实现。

**交互长什么样：**
- GitLab issue：一条时间线混排两类内容——**系统事件**（「张三 把状态 open→closed · 3 小时前」，灰字单行、极紧凑）和**评论**（富文本、可 @、可快捷指令）。系统事件不抢视觉，评论是主角。
- Focalboard 卡片：属性每次变更记一行「谁在何时把什么从 A 改成 B」，纯 diff 式。
- Linear：issue 内活动与评论分区/混排（具体形态待核实），团队级有独立 Activity 页。

**适配判断：改造借鉴，且难点在降噪不在功能。** 本面板已有「动态流」标签（README.md:30）和频道事件流 create/message/progress/done（README.md:28），骨架是对的。要补的是 GitLab 式的两层结构：
1. **系统事件一行化**：状态变更、指派（派发）变更、优先级变更压成灰字 diff 行；本面板「修改暂存 + Diff 预览」（README.md:23）已有 diff 语言，复用即可。
2. **AI 消息必须分层折叠**：人类团队一天几十条活动，AI 代理一天几百条 progress——不做「事件类型过滤」（只看：状态/门禁失败/等待输入）和连续 progress 自动折叠（折叠成「· · · 47 条进度消息」），流就不可读。这是与人类协作产品最大的分叉点。
3. **评论与活动同层混排**：评论即「人对代理下的指令记录」，天然形成审计轨，配合快捷指令（模式 4）闭环。

## 6. 通知中心

**做得最好的：Linear Inbox。** 次选：GitLab To-Do；飞书「盒子」是全应用统一收口 + 稍后提醒的好参照。

**交互长什么样：**
- Linear Inbox：通知**按 issue 分组合并**（同一 issue 的十条动态归一条），每条可直接处理（接受/归档，全键盘），支持自动归档规则（低价值类型自动清掉）。设计立场明确：inbox 是「需要我处理的事」，不是「发生过的事」。
- GitLab To-Do：由 @提及、指派、评审请求等动作**自动生成**（完整触发清单待核实），可逐条或批量 Mark as done；本质是「别人对我动作的应收清单」。
- 飞书盒子：所有应用通知统一进一个收件箱，支持稍后提醒/置顶，避免通知散落。

**适配判断：非常需要，且要比 Linear 更克制。** 单人盯 N 个代理，通知只该有两类：
1. **需要我动作**：代理等输入、门禁失败、卡住超时、任务失败——弹系统 toast + 托盘角标 + 进 Inbox，每条通知可就地打开任务、回一句、重新派发（动作化是 Linear 的精髓）。
2. **摘要**：今日完成/失败汇总，定时一份，不弹。
**代理的 progress 消息绝不能产生 toast**（否则一天几百条直接把人训练成全局静音）。本面板已有托盘常驻（README.md:34）和 tpanel notify 深链（README.md:49），通知通道是现成的，缺的就是「分组 + 可处理 + 默认静默完成类」这套 Inbox 形态。「等我处理」队列（模式 1）与 Inbox 应是同一份数据的两个视图。

**不适合的：** 飞书式按应用分的 dozens 类通知偏好矩阵——单面板没有那么多源，做「只提醒这三类 + 其余进流」的开关就够。

## 7. 命令面板

**做得最好的：Linear ⌘K。** 桌面软件参照：VS Code / Obsidian 的 Ctrl+P（对 Windows 桌面面板更有参照意义）。GitLab 也已上线全局命令面板（17.x 起，GA 版本待核实）。

**交互长什么样：**
- Ctrl/Cmd+K 呼出，输入即搜——结果混合排序：导航目标、任务、可执行动作（新建/改状态/派发）。↑↓ 选择、Enter 执行；空格/→ 进入子选择（如选「改状态」后再选目标状态）。
- Linear 把命令面板当主交互：全键盘可完成建任务、改属性、跳转，UI 上大量入口只是命令面板的可视化冗余。
- VS Code 证明桌面常驻场景下命令面板是最高 ROI 的控件：所有长尾功能不必占 UI 空间。

**适配判断：已有底子，扩内容即可。** 本面板 Ctrl+K 已支持页面跳转/任务搜索/新建待办/重扫描/主题（README.md:36）。补强三步：
1. **动作清单扩充**：派发任务给频道、运行 Flow 模板（README.md:27 内置模板正好是动作源）、跑健康诊断、切换保存视图、打开某频道的最新消息——这些全是「高频但入口深」的动作。
2. **支持轻参数化**：选中任务后 →「派发到 dispatch/频道的子选择」两级即可，别做命令行语法。
3. **最近使用置顶**（Linear/VS Code 共同习惯）。
原则：命令面板是加速器不替代可见入口——新动作在 UI 仍要有出处，面板里可搜索的动作与按钮一一对应。

## 8. 模板与快速创建

**做得最好的：快速创建 = Linear；模板 = GitLab 仓库模板。** 补充参考：Todoist 的自然语言快速添加。

**交互长什么样：**
- Linear：任意页面按 C 弹出新建浮层，一个浮层里填完标题/状态/指派/优先级/描述，⌘Enter 保存，不打断上下文。issue 模板按团队定义，带默认字段值和结构化描述骨架（标题匹配到模板名时自动建议应用——匹配规则细节待核实）。
- GitLab：模板就是仓库里的文件（`.gitlab/issue_templates/*.md`），随代码版本化、可评审；新建 issue 时下拉选模板，骨架填入正文。
- Todoist（补充）：快速添加框输入「周五前 修登录bug p1」，自然语言解析出截止日期和优先级——输入即结构化。

**适配判断：面板已有速记窗（Alt+N，提交 cd02fa1）和派发台一句话建任务，方向完全正确，缺「模板」这一环。**
1. **任务模板 = PRD 骨架**：bug / 功能 / 调研 三类，各带 PRD 章节骨架 + 默认字段值。学 GitLab：模板文件放仓库里（如 `.trellis/templates/`）随项目共享、随 git 评审，而不是藏在应用设置里——这也符合面板「.trellis 的可视化浏览器」定位（README.md:15）。
2. **派发句式模板**：派发台已生成结构化指令（README.md:28），把常用的「一句话+目标频道+门禁要求」组合沉淀成可选模板。
3. **自然语言解析字段**可接已有 AI 能力（README.md:37）：速记/一句话里识别优先级、目标频道、截止，预填后让人确认——抄 Todoist 的体验，不必抄它的解析器。
克制点：常用模板三个以内，别做模板分类管理树——所有协作产品的教训是模板一多就没人用。

## 9. 进度可视化（燃尽 / 健康度）

**做得最好的：燃尽/燃起 = GitLab（里程碑与迭代同时提供 burndown/burnup，燃起图能看出范围膨胀）；健康度 = GitLab epic 的三档 health status（on track / needs attention / at risk，手选色点）；周期视图 = Linear cycle（剩余工作随周期推进的燃尽式小图，是否可切燃起待核实）。** OpenProject 是报表全家桶（工时/成本/燃尽），属重型企业路线。

**交互长什么样：**
- GitLab 燃尽图：横轴时间、纵轴剩余 issue/点数，理想线对照；燃起图叠加已完成与总量两条线，总量上翘即 scope creep。
- GitLab epic 健康度：epic 列表每行一个三态色点（绿/黄/红），点开手选，一屏扫全项目健康。注：epic 属付费档功能（具体档位待核实）。
- Linear 项目进度：由关联 issue 自动汇总成百分比 + 状态，不用人填。

**适配判断：燃尽不抄，健康度和趋势要抄。**
1. **传统燃尽/点数对单人 AI 任务几乎无意义**：没有固定冲刺、任务粒度不稳定、没有估点习惯，画出来是仪式感图表。唯一保留场景：若真用 Jira 冲刺（README.md:31），在冲刺视图里给一张即可，主界面不放。
2. **直接抄 GitLab 三档健康色点，但数据源换成 AI 诊断**：每任务/每频道一个色点——正常 / 停滞（超时未动）/ 等输入 / 失败。本面板 AI 深度诊断已有停滞归因、负载观察（README.md:30），缺的就是把诊断结果落成「一眼扫全盘」的健康矩阵（行=频道，列=任务，或看板卡角标）。
3. **用吞吐趋势替代燃尽趋势**：完成速率（任务/天）、中位交付时长、卡住时长分布三条小趋势线。效率分析已有交付周期/流转热度/停滞预警（README.md:30），从单点数值升级为 7/30 天趋势即可。
**不适合的：** OpenProject 式报表中心（多图表配置、导出、成本核算）——单人面板一张健康矩阵 + 两三条趋势线封顶。

## 综合借鉴优先级（建议路线）

按「收益 ÷ 成本」排序，前五均可挂在面板已有能力上，属增强而非新建：

1. **Linear Inbox 式通知中心 + 「等我处理」今日视图**（模式 1+6，同一份数据）：把「代理 @我 / 等输入」从事件流里提出来变成一等队列，这是单人管代理最痛的一刀。
2. **筛选与保存视图**（模式 3）：预置「等我处理 / 卡住超时 / 按频道 / 失败重试」+ 自定义，实现最便宜。
3. **看板分组维度扩展到频道/代理**（模式 2）：一列 = 一个代理的在制任务，看板即负载面板。
4. **健康色点矩阵 + 吞吐趋势**（模式 9）：AI 诊断结果的可视化落点，替代无意义的燃尽。
5. **命令面板动作化**（模式 7）：把派发、跑 Flow 模板、跑诊断变成 Ctrl+K 可搜动作。

明确不建议：甘特/时间线编辑器、OpenProject 式报表中心、多人指派与审批流、全量通知偏好矩阵。
