## 一、定位修订：从"要打开的应用"到"长在系统里的阅读层"

### 1.1 痛点自述（本方案的第一依据）

用户对产品起源与现状的自述，按疼痛频率排序：

1. **阅读体验（起家动机）**：各 AI 桌面端使用 Trellis 后，生成的文档无法好好阅读——只有简单链接或粗糙窄阅读区。用户曾长期"手动复制目录 → Typora 打开"。TP 因此诞生，"看的问题已解决，但还是差点意思"。
2. **打开成本（现状最痛）**：AI 生成任务文档后，阅读需"打开 TP → 进任务看板 → 找任务 → 查看"。用户自己是维护者尚且嫌重；普通用户不会为看一篇文档专门打开一个应用。
3. **流程交互缺位**：TP 无法决定任务规划、起草任务、任务流转；这些操作仍需回到 Codex/ZCode 等桌面端。

### 1.2 新定位一句话

> **TP = 长在操作系统里的 Trellis 阅读层 + 派单台：文档读得舒服且懂 Trellis 结构（展示），随叫随到不用找（触达），重操作走能力验证过的派单（交互）。**

核心反转：不是把应用做好看等用户来开，而是**应用去找用户**（通知/热键/深链把阅读送到手边）。

### 1.3 对 05 评审的配重

05 的 R0 数据纪律、克制清单、验收材料**原样保留**（R0 不动摇：假数据会让阅读也骗人）。配重两处：交接包从首版核心降半格（阅读与触达是每日痛点）；新增 ambient 触达层与阅读体验为主角。

## 二、三大支柱

### 支柱一：随叫随到（解"打开太重"）

目标交互：`打开 TP → 找任务 → 看文档` 变为 `点通知直达`。机制与**交互合同**：

1. **托盘常驻 + 文件监听通知**：TP 托盘盯 `.trellis/`，材料更新 → 系统通知 → 点击直达阅读。
   - **不打扰合同**：按任务合并（AI 两分钟内多次保存只弹一条）；等文件稳定（防抖）后再通知；正在阅读的材料只给轻量更新提示；首次扫描不发"新生成"通知；措辞只报文件事实，不推断代理状态。
   - **承诺边界**：仅当 TP 在托盘运行且目标项目受监听时才有通知；退出即无（无常驻服务）；开机自启动是独立选项，不隐含在通知功能里。多项目常驻监听为 T1 扩展，首版单项目。
2. **全局热键唤起**：任意位置按热键唤起阅读。**默认恢复上次阅读位置**（上次任务、文件、滚动点），不自动跳到最新文件——刷新或重复唤起不得切换正在读的任务。定位新任务走显式动作。
3. **显式"打开路径"**：用户粘贴/选择任务目录路径（衔接"从 AI 客户端复制路径"的既有习惯）→ 显式动作打开。不做打开即自动跳转剪贴板目标。
4. **资源管理器右键"用 TP 阅读"**（T1）：对标 Typora 习惯迁移。
5. **深链**（T1）：现有 scheme 为 `trellis-panel://` 且带每安装 token——区分三类链接：只读导航链接、用户可复制分享链接、有权限的操作入口，不复用旧桥接混淆分级。**链接身份必须含工作树 + 任务 + 文件**（仅任务名在两个 clone/worktree 间有歧义）；锚点首版做到标题/文件级，未定位到标题时展示原文件并提示失效，段落级稳定链接后置；重复标题、文件重命名、归档后失效要有回退。
   - TP 不改写 `AGENTS.md` 等 Trellis 托管文件去"教 AI 带链接"；用户想让 AI 附路径/链接，自行在提示词中要求。

**目标场景（生成即读闭环，验收用）**：Codex 里说"帮我规划登录超时修复" → brainstorm 写 prd.md → TP 合并通知"任务 XX 的 PRD 已更新 [阅读]" → 点击直达沉浸阅读 → 复制标题锚点贴回 Codex 说"改这一节" → 再合并通知。整个循环 TP 一次都没被"打开"，但无处不在。

### 支柱二：做懂 Trellis 结构的文档阅读器（解"还差点意思"）

差异化不是渲染速度，而是**懂 Trellis 文档结构**（验收措辞：Trellis 结构感知的阅读体验，不做通用阅读器对比承诺）：

1. **任务 = 小型文档站**：侧栏为该书目录（PRD/设计/实施/research/规范引用），正文区连续阅读，材料间跳转不弹窗。骨架复用 TaskWorkspace + ArtifactViewer（05 §9.1 已核实存在）。
2. **沉浸模式**：全屏、字号/主题/行距可调（"自定义显示效果"落点）。
3. **Trellis 特化渲染**：`implement.jsonl`/`check.jsonl` 渲染为"上下文引用清单"表格（文件+理由）；mermaid；代码高亮；PRD 章节大纲跳转；章节定位失败显示原文，不造假结构。
4. **接着读**：记住每任务最后打开文件与滚动位置。
5. **标题/文件级锚点引用**：复制引用链接（§支柱一第 5 条的分级链接之一）。

### 支柱三：派单式流程交互（能力验证优先，不随首版）

原则：**判断交给有工作流身份的 worker，执行交给官方脚本，授权留给人。面板进程不直写 task.json。**

**边界更正（v2，来自跟进评审）**："面板进程不直写"不是充分边界——用户在 TP 点"检查"而 worker 改源码，就是用户经面板发起的生命周期动作，TP 须承担目标绑定、权限、重复提交、取消、失败结果与操作记录的完整合同。因此派单整体是**新增执行范围，独立验收，不进首版**。

**能力事实（本机 0.6.17 核实）**：

- `--sandbox`（read-only/workspace-write/danger-full-access）**仅 codex worker 有效**；不是任意路径白名单（没有"只准写 .trellis/tasks/"）。
- `.trellis/agents/check.md` 默认 `provider: claude`，职责含自修复与跑验证；claude 适配器构建参数使用 `bypassPermissions`/`--dangerously-skip-permissions`——**给 claude worker 的提示词里写 "read-only" 不会让它变只读**。
- planner 员工档案**不存在**（现成只有 check.md、implement.md）。
- `spawn` ≠ 任务已接单：需显式 `send` 定向消息并等待运行时事件（turn_finished 等）。

**T4 路径 = 先窄验证，再逐项评估**：

1. **能力验证（第一个派单实验）**：对指定任务用 **codex + `--sandbox read-only`** 执行只读审阅，产出**可解析的固定格式报告**；核验：确实未写源码；待确认问题能回到人；报告可渲染留档。通过后再分别评估：
2. **起草任务（planner）**：需先补 planner 员工档案；沙箱需允许写任务材料（codex workspace-write，接受其范围语义），报告回 TP 通知"PRD 待审"。
3. **修复型 check 与归档三段式**：check 会自修源码——前置 Git 干净检查后仍可能产生新改动，收尾流程须处理；"Git 干净/子任务闭环"等门禁条件**来自目标项目规则**，不是全体 Trellis 项目的统一强制；check 模板当前不产出稳定的机器可读 check-report，作门禁前需定义回执格式。
4. **元数据代跑**：按具体字段列权限与回执（set-branch/set-scope/add-context 等），不泛化承诺。

**worker 写入边界**：worker 经官方流程可写任务目录材料（prd/research/jsonl 等）；但与面板进程同样**不得改写 `AGENTS.md`、`workflow.md`、spec/skills 等托管文件**（用户 09-30 边界的完整口径：约束面板进程，也约束面板派出的 worker）。

## 三、两个透视模块（T2，观察为主）

### 3.1 图1：流程参考 + 文件事实（v2 降级版）

**v1 的错误（已撤回）**：v1 曾按 `status + mtime` 推断"当前执行位置"并把全部任务布到总览图。经查 `workflow.md:123-133`：`planning` 覆盖整个规划阶段，`in_progress` 覆盖执行、检查、规范更新与提交——**状态字段不区分设计/实施/检查三段**；任务做完在检查、或 implement.md 仅为计划未动代码，都会误亮"实施中"。"推断"二字救不了误导。**推断位置点亮与总览布点撤回。**

v2 形态，两个分开的东西：

1. **项目流程参考图**：workflow.md 标签块的静态投影（只读参考，类似 GitHub Actions 的流水线说明页）。渲染用 stepper/卡片布局（复用 FlowVisual 的**样式**——它是按阶段渲染的嵌套卡片列表，不是通用节点连线画布）。未知项目流程降级为原文展示，不自动套固定五节点。点击 = 查看该阶段在 workflow.md 的原文摘录。
2. **文件事实面板**：每任务展示"PRD 已找到 / 设计文件已找到 / 未找到检查材料 / 位于归档目录"，全部为存在性事实，不推断执行进度。
3. **执行点亮（后置）**：仅当存在真实步骤事件（如 T4 派单产生的 channel 事件回执）后才点亮执行位置；没有事件就不亮。

### 3.2 图2：上下文透视（预演不回放）

**红线**：只做"预期注入行为"预演，不做"实际注入回放"——交互式会话注入无逐轮回执；即便 channel 的 events.jsonl，也只含运行事件与启动上下文快照（spawned 事件记录 provider/worker/pid/已装配文件与 manifest 路径），不含逐轮 hook 输出完整字节。三档分清：**运行时事件 / 启动上下文快照 / 逐轮回执（不存在）**。

四个视图（v2 拆分版）：

1. **规则预览**（替代 v1 的"面包屑沙盘状态模拟"——已证实 hook 主入口不接收模拟状态参数，它从会话指针→task.json 真实推导）：只**静态解析** workflow.md 标签块，用户选块看原文。不运行任何项目脚本、不碰会话指针、不声称等于真实会话看到的全部提示。纯 markdown 解析，无执行风险。
2. **会话诊断**：选择一个**真实存在的会话**，展示其平台、任务绑定（`.runtime/sessions/`）、配置与读取结果；如需运行 hook 展示运行条件与输出，不以面板自身环境冒充外部宿主。`last_seen_at` 显示"最后记录"，不当在线心跳。
3. **上下文预期诊断**（v2 机制更正）：**两条装配链数值不同**——hook 链（inject-subagent-context：单文件 32K/单产物 64K/总量 128K 默认；超限**先截断正文并留完整路径**让代理继续读，总预算不足才降为路径索引；配置 0=关闭上限）；channel 链（context-loader：单文件 1M 硬顶/200K 告警/合计 500K 告警）。按平台与派发方式展示五档：**预期完整内联 / 预期截断（附截断位置与原件入口）/ 仅索引 / 跳过 / 无法估算**。措辞限定"预期注入行为"，不推断模型实际读过、理解或遵守（缺内联 ≠ 不遵守 spec 的充分解释——代理仍可用文件工具读取）。
4. **技能与平台**：技能展示**声明的适用条件**（description 是匹配依据而非确定性路由，不画"某句话必触发"）；平台展示能力矩阵与接线状态（如 Codex 未开 `features.hooks` 标"未接线"）。

护栏：规则预览零执行；会话诊断如需运行脚本为点击触发的显式动作，只跑已知注入脚本、喂受控输入；所有预览标"预演"。

### 3.3 图3：会话/协作流（T5）

sessions 文件 + channel 运行事件/启动快照 → 谁在干活、启始上下文是什么。区分于"逐轮回执"（不存在）。依赖 T4 落地后才有稳定数据源，先以只读浏览（任务绑定 + 最后记录）独立提供。

**channel 绑定铁律（v2 升级）**：频道项目桶由 **CLI 进程自身 cwd（或 TRELLIS_CHANNEL_PROJECT 环境变量）**决定，与 `spawn --cwd` 无关。因此：**TP 起 trellis 子进程时，进程 cwd 必须就是目标项目根**（项目桶与 worker cwd 一次对齐）；必要时显式设置 `TRELLIS_CHANNEL_PROJECT`；读频道状态复用官方桶解析，不自拼项目路径；连同 scope、目标工作树身份一起绑定并验证——身份不一致时 create/send/wait/interrupt/kill 可能把结果带错项目。

**其他护栏**：面板偏好/日志不进任务权威字段；通知只报文件事实；TP 与 TP 派出的 worker 均不改写 `AGENTS.md`、`workflow.md`、spec/skills 等托管文件。
