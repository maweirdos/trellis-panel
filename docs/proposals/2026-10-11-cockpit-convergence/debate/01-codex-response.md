## 二、我不直接接受的技术假设

### T1 黑名单不是自动共享的完整边界

选择自动快照，不等于监控整个 `.trellis/` 后排除几个目录。建议：项目一次配置共享文件类型/路径白名单、受众与排除规则；内容检测命中疑似凭据时隔离该版本并提示；私有会话、源码、原始工具/终端日志默认不共享。例：PRD/design 通常可共享，PRD 中粘入凭据或生产数据则不因扩展名是 `.md` 被自动放行。

项目开启策略后，正常文档更新不要求开发反复点发布；共享的是“实时草稿”或“已确认版本”，不是手写战报。Git 仓库的存在也不自动证明所有 PM 有同样的文档访问范围。

### T2 hook 落账不等于模型实际收到并遵守

本地 `.codex/hooks/inject-subagent-context.py:964` 和 `:1190` 分别输出 `additionalContext` 与 `updatedInput`。在输出前写日志，只能证明组装/尝试提交；宿主是否接受、Agent 是否采用、压缩后是否仍在上下文，需要各自证据。

建议四层标签：已组装 → 已交给宿主/适配器 → 宿主接收已确认（仅支持时）→ 关联检查结果。记录文件 hash 与实际发送片段 hash、字节数、截断、目标会话/子 Agent。检索命中也不等于被选入。

F2 不应在 UI 上承诺“绿=规范已注入模型”，更不能把通过检查并入同一颗灯。

### T3 ACP 与内外部宿主不是观测能力的分界

ACP 提供 Agent 对外发出的消息/工具/权限事件，不保证完整内部子 Agent 树或供应商内部提示词。原生编辑器若安装兼容的 Trellis hooks，也能产生可靠回执；不应故意把它降成只有文件猜测。

建议逐项能力矩阵：文件观察、上下文回执、流程事件、子 Agent 事件、工具权限、恢复、运行中补充。舱内通常更容易统一操作，但 UI 只展示当前适配组合实际能证明的能力。没有证据时标“未知/未观察到”，不能据此断言没执行。

### T4 `task.py start` 目前不是审批强制门

`.trellis/scripts/task.py:171` 的 start 检查上下文清单、设置当前任务与阶段，没有校验用户批准的设计版本。当前前端加确认按钮，可以约束驾驶舱内的启动入口；外部直接调用仍可能绕过。

首版声明“受管启动门”：批准记录绑定具体计划/材料版本；驾驶舱执行入口检查；外部事件只能报告“未观察到对应批准”。不为了展示一个门去承诺控制所有编辑器。若以后统一改 Trellis 底层契约，要一起维护生成模板/升级兼容，而非私改各项目 hook 副本。

### T5 静态 CI 面板是阶段快照，不是实时直播

基座仓库 + CI 页面只能展示已经提交、推送、构建成功的内容，无法让 PM 看到尚在员工电脑上的 PRD 修改。建议同时给出两条明确能力：

- P0/P1 本地驾驶舱；可选基座文档站展示已归档/已提交快照，显示提交与构建时间。
- 第一次团队试点如果验收目标包括实时文档和在线澄清，就同步交付最小的授权接收/只读展示服务，不能等到很晚再用静态页冒充。

### T6 去重不够，最小持久化仍然需要

三人试点不需要分布式调度、任期协议和多设备自动接管，我接受删除这些首版施工项。但事件 ID 去重不能恢复断网时未送出的事件。最小方案是一个本地追加日志 + 已确认游标 + 有界重试；它可以复用本地事件日志，不需要单独建复杂 outbox 服务。

### T7 归档、提交、推送与合并分开

归档可以生成并排队一个限定文档范围的基座归档包。按项目一次授权的策略自动暂存/提交可选；不把 `git add .`、推送保护分支、合并 MR 隐藏在归档按钮后面。共享草稿更新与正式归档提交也不应产生同样的 Git 噪声。

## 三、补证结果

| 事实 | 核查结果 | 产品影响 |
| --- | --- | --- |
| GitLab 已有 MR/CI 能力 | `gitlabTaskStatus` 查询 opened MR 与分支最新 pipeline；`gitlabCreateMr` 已有 | 应复用，但还需稳定 MR ID、merged 查询与提交 SHA 对齐；不能直接把分支最新绿灯算本次交付通过 |
| 当前 ACP Trellis 事件关联 | `emitTrellisTimeline` 向同项目全部活跃会话追加事件；部分事件 taskDir 缺失 | 首发前需补 task/run/session 关联，不能把别的任务事件点亮当前流程 |
| 已有 native hooks | `.codex/hooks.json` 配置 UserPromptSubmit 与 SubagentStart | 外部宿主可能同样有强观测信号，不能一律降为 watcher 推断 |
| Trellis 清单有截断 | hook 有每文件、产物、总字节上限 | 回执必须显示缺失与裁剪，不能只列原始文件名 |
| 飞书文档抓取 | 存在官方文档 API，但公司应用授权、wiki/块类型、版本能力未实测 | 提前做一次权限与样本文档验证；保留章节选择、手动导入，移除八成匹配的承诺 |

## 五、请 GLM 反向攻击这版修订

请逐项回答：接受 / 反对 / 需补证，尤其 T1–T7；再指出下面路线仍可能失败的三处，并给可检验的替代方案：

1. 本地阅读 + 回执 + 工作流观察 + 一条轻任务执行路径。

4. 根据真实多人试点再加复杂治理、多人实时编辑或多设备调度。

不需要顺从，不能把“做不到完美”作为放弃明确验收的理由。请区分现有实现证据和新增设计，勿修改产品代码或原始证词。
