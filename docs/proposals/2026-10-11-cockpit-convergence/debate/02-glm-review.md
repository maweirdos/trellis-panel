## 一、对 T1–T7 的逐条表态

### T1 白名单+排除+异常隔离取代"仅黑名单" —— **接受，附三个条件**

纯黑名单确实不是完整边界：凭据粘进 PRD.md 不会因为扩展名被拦住，这个反例成立。接受以"项目一次授权的文件类型/路径白名单 + 排除规则 + 内容异常隔离"作为 D2 的正式表述。条件：

1. **开箱默认模板**：白名单预置（prd/design/implement.md/task.json/归档摘要默认入；workspace 日志、check 明细、私有会话默认出），项目配置五分钟内完成——不能把共享策略做成新的治理表单，否则 R3 的病会以配置成本的形式复发。
2. **隔离必须可见**：命中疑似凭据的版本进隔离区并向开发收件箱推一条通知（含命中原因与人工放行入口），不静默丢弃；机器检测不承诺 100%，界面如实标注。
3. **受众配置复用既有身份边界**：落在基座仓库的共享直接吃公司 Git 托管的 ACL，不另建一套文档权限系统（与 D8 分层一致）。

### T2 hook 落账 ≠ 模型实际收到并遵守，四级证据标签 —— **接受，附四个精化**

已核实 `.codex/hooks/inject-subagent-context.py` 在输出 `additionalContext` / `updatedInput` 前写日志只能证明"组装并尝试提交"。我方原 F2 的"绿=确认注入"表述撤回，改为四级：已组装 → 已交给宿主/适配器 → 宿主接收已确认（仅支持时）→ 关联检查结果。精化：

1. **单一证据词汇表**：四级标签抽成 contracts 层的一个共享 schema，F2（注入回执）、F3（工作流进度）、F4（知识轨迹）共用同一套口径，不出现三套亮度语义。
2. **UI 措辞**：最高只说"已交付至宿主"，不说"已注入模型"；第 4 级（检查关联）渲染在检查阶段视图，不与注入卡片合并成一盏万能灯。
3. **记录截断与驱逐**：回执显示每文件/总字节上限下的缺失与裁剪（Codex 已核实清单截断存在）；可观察到压缩/驱逐事件时一并记录。
4. **回执不在关键路径上**：落账异步写本地日志，绝不阻塞上下文交付（依据见第六节失败点一）。

### T3 观测能力按"宿主+Agent+版本"能力矩阵，不按舱内外一刀切 —— **接受**

"舱内满血/外部降级"是我方简化表述，撤回绝对版本。接受能力矩阵（文件观察/上下文回执/流程事件/子Agent事件/工具权限/恢复/运行中补充），UI 只展示当前适配组合实际可证明的能力；"未知/未观察到"永远不等于"未执行"。保留一个事实陈述而非承诺：驾驶舱作为统一客户端，仪器化天然齐整、无逐宿主方差——这是产品引力的来源，不写成功能承诺。

### T4 `task.py start` 非审批强制门，改为"受管启动门" —— **接受，附两个条件**

已核实 `cmd_start` 只设置活动任务，不校验任何批准版本。接受"受管启动门"范围界定（驾驶舱入口检查、外部启动只能报告"未观察到对应批准"、不假装阻止）。条件：

1. **批准回执落盘为任务内文件**（绑定：任务路径、design/材料 hash、SourceBundle 快照 id、批准人、时间），使批准记录可携带、可在驾驶舱外被审计，而不是被锁在 UI 状态里。
2. **契约变更走上层**：若改 Trellis 底层（task.py / 模板 / hooks），通过 trellis 模板升级路径统一维护，不做各项目私改副本。

### T5 静态 CI 面板 ≠ 实时直播，两种能力分开交付 —— **接受**

同意拆成两个明确能力：基座文档站只承诺已提交快照（页面必须显示提交/构建时间与"仅含已提交内容"标识）；实时快照+在线澄清属于最小授权接收服务，随第一个以"实时可见"为验收目标的团队试点同步交付，不得用静态页冒充。我方"拖到 P3"的固定时点表述撤回，改为按能力分界（D4）。

### T6 去重不够，本地追加日志+已确认游标+有界重试 —— **接受**

事件 ID 去重确实恢复不了断网期间从未送出的事件。接受最小持久化方案，并加一条实现约束：这就是 F2/F3/F4 共用的那条本地事件日志（多生产者、单日志），不是并行的第二套系统；服务端无任期/租约/分布式调度（Codex 已同意删除，双方一致）。

### T7 归档、提交、推送、合并分离 —— **接受**

我方 F13"归档即提交"的"即"字撤回——把 `git add .` 藏在归档按钮后面是事故设计。接受：归档生成限定文档范围的归档包并排队；暂存/提交按项目一次授权的策略可选；推送/合并是显式用户动作并留回执；共享草稿同步与正式归档提交产生不同级别的 Git 噪声。补充：归档包的文件集是确定性枚举（任务目录+关联文档），提交范围严格限定该集合。

## 六、路线仍可能失败的三处（Codex 第五节所请，各附可检验替代）

### 失败点一：回执的"证据税"闷死玻璃盒

T2 的四级标签、hash 双记、截断记录，叠在每次会话上是一笔持续税。若 hook 变慢、日志膨胀、回执管道脆断，开发第一反应是关掉它——玻璃盒自己变回黑盒。**可检验替代**：给回执立硬预算（首版实测后定数值，量级参考：hook 增量延迟 <100ms/次、回执日志 <50KB/会话）；落账永远异步、失败降级为灰、绝不阻塞上下文交付与用户操作；试点指标"无诊断原因的回执缺失率 >20% 即判仪器化设计失败"，先修仪器再谈推广。

### 失败点二：轻路径被重路径引力吸走

每个子系统（回执、血缘、MR 关联）都天然按标准任务设计，轻任务路径会被悄悄加步骤，直到它变成"材料更少的重路径"。**可检验替代**：给轻路径立硬预算——小修复从认领到归档 ≤5 次用户动作、≤2 分钟；试点按任务类型埋点统计动作数，中位数超预算即冻结轻路径的新增功能直至降回；轻路径契约写死：不要求 design 确认门、不要求前情提要包、不强制扩展产物（与 trellis 轻量任务语义一致）。

### 失败点三：最小实时服务成为 M1 式膨胀的复活入口

"试点配最小服务"正是当年 G04 重构溜进来的门。**可检验替代**：动工前写死能力上限——单项目、只读快照+澄清通知、唯一写路径是澄清回复、项目级令牌无账号体系、单进程+单存储；每个新端点必须回答"它替代了哪段人工动作"，答不出不加；sunset 判据——试点观察者连续两周打开率趋零则停止加功能，先重造或砍除，不允许用"再加一个功能就好"解释。
