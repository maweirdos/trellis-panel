## 2. 接受的附加条件，以及需要修正的实现词语

### T1：预置共享模板、隔离可见、尽量复用 Git 权限——接受

默认模板包括：PRD、design、implement.md、经字段筛选的 task 元数据、归档摘要。不是把未知字段很多的 task.json 原样外发。workspace 全文、私有会话、原始检查/终端日志默认排除；任务级检查摘要与回执摘要可以按项目策略单独选择。

正常更新不再逐次点发布；隔离必须可见，可查看命中原因并按项目权限处理。机器检测不能承诺 100%。“五分钟配置完成”可以作为已有身份/权限准备好的可用性目标，不能包含或替代公司审批耗时。

仓库和文档站尽量复用既有 ACL，但必须验证站点确实启用了访问控制。Git 私有仓库不自动意味着 Pages 私有；官方文档同时提供项目成员与 Everyone 等设置。[GitLab Pages 访问控制](https://docs.gitlab.com/user/project/pages/pages_access_control/)

### T2：统一词汇、分开检查、记录裁剪——接受；“永远异步、绝不阻塞”需改写

短生命周期 hook 中启动一个不等待的异步写，进程退出时可能丢回执。多个生产者直接追加一个文件，也不能默认在所有平台和写入长度下保持完整性。

建议约束：**遥测失败不使上下文交付失败，不在 hook 中等待网络或做重型扫描；本地记录使用有界、轻量的接收方式。** 可以向已有本地收集器提交，或写独立小片段供汇合；最终由一个逻辑日志出口顺序落账。超过预算则降级并留下可观察的缺口，不能把没有持久化成功的消息显示成已落账。

这保留了“共用一条本地事件日志”的产品语义，但不要求所有生产者直接并发写同一个文件，也不承诺物理意义上的零耗时。原始上下文已读入时复用内存数据计算摘要，避免为了回执重新扫文件。

必须区分遥测与控制记录：观测回执可以降级，受管操作所需的批准/来源版本记录则不能保存失败后继续假报成功。“不阻塞”不能成为绕过批准门的理由。

### T4：批准记录可携带——接受

在任务目录中使用有命名空间的扩展文件保存批准记录，例如 `.panel/approvals.jsonl`，不修改 task.py 的原生语义。记录稳定任务 ID、路径提示、材料 hash、SourceBundle ID、批准者来源与时间；路径只是提示，归档/重命名不令历史记录丢失。

首版本机记录不是不可伪造的企业签名，界面显示它真实的身份来源。外部启动仍只是报告缺少对应记录。未来若改 Trellis 原生门槛，统一维护模板与升级路径。

### T3 / T5 / T6 / T7：原方向接受

能力矩阵、静态/实时区分、本地持久日志与发送游标、归档/提交/推送/合并分离继续保留。统一客户端能减少一些集成差异，但不能再把“无逐宿主方差”写成事实；Agent、适配器和宿主版本仍会影响能力。

## 3. 对可行性审计的逐项表态

| 审计主张 | 结论 | 修改后的可执行规则 |
| --- | --- | --- |
| 按一名维护者+AI 的能力控制建设规模 | **接受为保守规划假设，不能当成已确认人员事实** | 当前没有核实用户投入时间、团队支持和运维资源；不从目录名推断“业余产能” |
| 所有前三阶段功能必须通过单人测试 | **修改后接受** | 个人核心必须独立有价值；低成本团队验证是另一条准入通道，不能因此删除用户明确的团队目标 |
| 不要求同事切换编辑器 | **接受** | 同事可只使用现有 hooks + 阅读视图；受管交互给自愿使用者 |
| 过程回执默认是开发者的工作证据 | **接受** | 团队默认看获准文档、任务状态与任务级摘要，不做人均违规率、员工行为排名 |
| 同事默认浏览器阅读已提交文档 | **条件接受** | 已有可访问的私有文档站时优先复用；只有提交后快照，不能代替本机未提交文档的舒适阅读 |
| PM 永远不用登录平台 | **改写** | 不要求新注册或迁移写作习惯；可复用现有身份/SSO。不能为了“永不登录”改为匿名公开私有材料 |
| 没有提到专职测试，因此不存在测试角色 | **反对该事实推断** | 角色尚未确认；首版不预设独立测试岗位，但质量检查与项目既有验收条件保留 |
| 平台内 Acceptance/验收流程移出前三阶段 | **接受为范围收缩建议** | 不自建验收工单引擎；接既有 Jira/MR/人工确认记录，不替团队宣布“关闭 Jira 就必然验收完” |
| 自定义机器人零审批、今天能上线 | **不接受普遍承诺** | 有权添加且公司允许时可低成本出站推送；仍需核实目标群权限、安全配置、触达范围 |
| 实时服务尽可能晚 | **接受按需求与运维承受力门控，不接受无限后移** | 确有未提交过程可见性需求、静态方案不能满足、有维护承诺时才做；实时验收没有服务就不能通过 |
| 静态站+推送覆盖 80% 团队需求 | **需测量，撤去数字** | 用真实问题完成率与滞后案例评价，不能把刚撤回的无依据比例换一个地方使用 |
| 一次适配修复超过一天就砍到一种 | **改成触发调查和缩范围的预算信号** | 先隔离坏掉的能力，保留还能工作的 hooks/文件观察，不因单一 ACP 回归丢掉所有强信号 |

## 4. D8 的更小且完整的替代方案

1. **文档仓库/静态站**：用既有 Git 身份和实际站点 ACL。明确读者是否能看该文档集合，不额外给源码权限。
2. **实时只读面**：优先现有 SSO/反向代理身份。如果只能用令牌，需经项目授权，限定项目/材料集合、只读、期限、撤销与传递方式；不能把一个无限期群共享密钥当成人的身份。
3. **设备上传**：单独的设备/写入凭据，限制到允许上传的任务和文档；读者令牌不能上传材料。
4. **澄清回复**：复用已验证的飞书用户事件或公司身份，并核验任务范围与文档版本。仅凭项目只读令牌不能匿名改写结论。
5. **新组织账号系统**：只有既有身份无法满足已明确的角色/审计/成员管理需要时才引入；“第二个非开发成员”与这个技术边界没有必然关系。

服务能力上限接受：一个试点项目、单进程/单存储、授权快照和有限澄清操作、不运行远程 Agent、不搬仓库、不建通用审批。准确地说，人类协作者的业务写入口仅限澄清；设备上传快照和系统同步回执本身仍是写入，不能用“唯一写路径是澄清”掩盖它们。

## 5. 预算应约束额外负担，而不是压缩真实工作

“领取到归档两分钟”混合了编码、模型响应、读计划、代码评审、CI 和人员等待，不是驾驶舱可控制的指标。要拆开测：

- 额外管理动作：相比原来的 Jira+编辑器路径，为驾驶舱新增的绑定、重复填写、再次确认。
- 人工主动耗时：操作与阅读，分别记录；必须的审阅不能靠少点按钮被省略。
- 外部等待：Agent、CI、Jira/飞书与人员等待，单列。
- 完成周期与返工：保留用于整体效果观察，不用“≤2分钟”硬压。

对“来源明确、已配置项目、无需额外组织审批”的轻任务，建议试点目标为**新增重复录入 0、同范围重复确认 0、新增管理动作不超过 2**；这些是候选目标，不是已测成绩。GLM 的 5 次/2 分钟可以保留作特定操作脚本的对照值，但不作为所有小修复的完成保证。

Jira issue 类型只能描述工单分类，不能证明工作量复杂度。两个版本的分类统计可作背景，还需抽样看实际影响范围与重复操作。

## 6. 飞书分档：接受降级思路，拆开三类能力

| 能力 | 最低可行路径 | 不能由它推导出的能力 |
| --- | --- | --- |
| 通知 | 在被允许的群中使用自定义机器人 webhook；无需自托管入站回调服务 | 不自动获得文档读取或可验证的任意回复能力 |
| 需求文档读取 | 被允许的应用/用户身份 + 对指定文档的访问权限 | 不因为能给群发消息就能读群里所有文档 |
| 交互回复 | 已验证身份的应用事件/卡片回调；目标 SDK 支持时可用长连接 | 不必一概要求公网回调，但也不能免除应用权限与运行环境维护 |

官方资料支持自定义机器人做群 webhook 推送，也说明添加机器人受群权限约束；知识库读取还涉及云文档 API 与文档/页面授权。[群机器人](https://www.feishu.cn/hc/zh-CN/articles/360024984973-在群组中使用机器人)、[知识库成员与应用权限](https://www.feishu.cn/hc/zh-CN/articles/530997871518-设置当前知识库管理员和成员)。官方也提供长连接接收事件路径；本轮未在公司环境验证特定卡片事件和 SDK 组合，因此不承诺已打通。[官方更新记录](https://open.feishu.cn/changelog?abilityType=Tool&lang=zh-CN)

推送不可用就复制授权链接/问题卡；文档读取不可用就人工导入；回复不可用就保留原工具讨论并由开发记录结论。三者分别降级，不把推送当成需求抓取的替代品。

## 7. 可行性预警的修正

不以“每天打开”“一个月没人主动问”“第二个成员”“一天没修完”单独裁决成败。先判断有没有适用任务、同事是否知道入口且有权限、是不是被首装或失效来源挡住、是否只需要少量低频查看。

回执的 <100ms、<50KB/会话、20% 缺失也尚无基线。保留“观测不能明显拖慢工作”作为硬约束，先测 p50/p95/最长值与故障降级。长会话与短会话不能用同一个 50KB 阈值。没有独立的预期事件分母时，不能报告回执缺失率；只能报告已观察的事件、错误和无法评估的范围。

可执行的首轮验证与建设范围已写入 [可行性与试点卡](../06-feasibility-and-pilot.md)。本轮保留团队目标，但停止把所有团队能力绑定到首发。
