# 第三轮 · GLM 可实施性审判（角色过堂 + 四维定级）

日期：2026-10-11。性质：GLM 独立发起的压力测试，**同时审判 GPT 方案与 GLM 反方案自身**，不受任何一方既有场景设定约束。目的：回答用户的问题——"不能做了一个完美的乌托邦，却根本无法实现"。

## 0. 审判方法

对每个能力问四个问题：①建造者产能够不够（见第 1 节的事实）；②组织环境放不放行；③目标角色有没有真实动机；④技术上有无硬阻断与持续维护税。全部通过"**单人测试**"：*如果这个功能永远只有建造者一个人用，它是否仍交付价值？* 通不过的功能不得进入前三阶段。

## 1. 两份方案共同回避的最大事实：建造者是谁

证据：本项目是个人项目（用户自述立项初衷、`D:\my_demo` 个人目录、基座仓库制度由用户个人制定）。**建造者 = 一名在职开发 + AI agent，业余产能。**

- 好消息：vibecoding 杠杆真实存在——本仓库 30+ 服务、20+ 页面就是一人+agent 的产出证明；P0/P1 的基体（scan/watcher/acp/jira/gitlab/知识库）已存在。
- 坏消息：**维护、跨机器差异、IT 审批流程不吃 vibecoding 这一套**。F1–F14 全集按收敛稿口径是多人季度工程；一人做，必须在每一阶段砍到通过单人测试为止。
- 结论：可实施性的第一约束不是技术，是产能。所有排期以"一人+agent"为分母；"团队平台"是产品被看见之后的**副产品**，不是前提。

## 2. 角色过堂（内心戏 + 判定）

### 2.1 开发同事（决定成败的采纳者）

内心戏："我为什么要装你 180MB 的客户端 / 放下我熟悉的编辑器？回执会不会变成查我没注入规范的证据？"

- 他们真实得到的益处：F1 阅读痛点（Typora 折腾是普遍痛点，非建造者独有）；F2 回执帮他们**自证**做对了；F9 血缘让接手旧模块不抓瞎。
- 他们真实的恐惧：监控感。若团队文化把回执读成"找茬雷达"，他们会用填满回执的方式游戏它，玻璃盒变成表演盒。
- 采纳的正确路径：trellis hooks 本就是团队流程强制项 → **回执在同事自己的编辑器里免费产生**（T3 能力矩阵的必然推论）；驾驶舱对同事首先是"读"和"看"，**永远不要求切换编辑器**；回执默认是开发者的私有视图，团队聚合面只到任务级状态，不到个人行为级。
- 分发渠道修正：阅读价值的默认载体是**浏览器**（基座仓库 CI 静态文档站渲染任务树/PRD/design），不是让同事装客户端。180MB 安装包是采纳杀手，静态站是零安装通道。
- 判定：**可实施**，前提是走"hooks 在编辑器内、面板只读优先、驾驶舱仅建造者与自愿者交互"路线。"舱内满血引力"是我方此前的乐观假设，降级为"存在即加分"。
- 早期信号：同事是否**主动问**"你那个视图怎么打开的"。一个月内零主动询问 → 停止推广投入，转为纯个人工具 + 静态站分享。

### 2.2 产品成员

现实行为（P05 证词）：Jira 写粗略总结 + 挂飞书文档链接，细节在飞书，从不写结构化需求。

- 对他们有效的：一个只读链接能看到任务 PRD 现状与阶段（他们现在**什么都看不到**）；澄清卡以飞书卡片形式到达，回复也在飞书里完成——**零新工具学习**。
- 对他们无效的：GPT 方案的"平台内撰写简报、平台内验收"——要求行为改变的工具会被飞书和 Jira 联手淘汰。
- 判定：**可实施，条件是"PM 永远不需要登录平台"**。全部交互发生在飞书卡片/只读链接/Jira 里。

### 2.3 测试/验收角色

事实核查：P05 证词中团队只有"产品提出→开发认领"，**从未出现专职测试**。GPT 方案的 Publication/Acceptance 验收机制在为一个可能不存在的角色建设。

- 现实中的验收 = PM 试用 + Jira 工单关闭。
- 判定：验收工作流（GPT 的 Acceptance 对象、验收版本冲突处理）**整体移出前三阶段**，归入"组织现实变化时再说"清单。这是本次审判砍掉的最大一块乌托邦。

### 2.4 建造者本人（流程 Owner）

诉求：vibecoding 质量管控、可追溯、迭代知识（P07/P08）。P0/P1 全部功能单人可用且直接服务此诉求。判定：**可实施且自我供养**——这是整个路线的地基。

### 2.5 IT / 公司环境

- Jira：已有集成在用，**已证实**。
- GitLab：OAuth/建 MR 代码已在，**已证实**（MR ID 稳定性与 merged 查询需补，Codex 已标注）。
- 飞书：**沼泽地**。分三档落地——Tier 1 群自定义机器人 webhook 推送（无需审批、无需服务器，今天就能做）；Tier 2 企业自建应用（需管理员审批 + 回调端点，D7 spike 定档）；Tier 3 放弃。抓取需求文档依赖 Tier 2。
- 服务器托管：内网 VM + 单人维护 = 真实运维税。判定：**实时服务尽可能晚**；静态 CI 站 + 推送覆盖 80% 团队可见性需求（与 D4 能力分界一致，但把"尽可能晚"升格为硬约束）。

## 3. 四维可行性定级

| 维度 | 定级 | 依据 |
| --- | --- | --- |
| 建造者产能 | P0/P1 **高**；P2 **中**；P3 **低**（除非出现团队自发拉力） | 单人测试；已有基体复用度 |
| 组织环境 | Jira/GitLab **已证实**；飞书 **中低**；服务器 **中** | 2.5 节 |
| 采纳激励 | 开发 **中高**（痛点真实+零成本获取）；PM **中**（零新工具原则下）；全员活跃 **低，不赌** | 2.1/2.2 节 |
| 技术与维护 | 无科幻项；**ACP/agent 版本漂移是持续税**；trellis 自有是护城河 | 第 4 节 |

维护税的具体形态：Claude Code / Gemini / Codex CLI 类工具月度级更新，每次可能破坏 ACP 适配与 hook 兼容。**预警规则：一次 agent 升级破坏适配超过一天修不完 → 适配面收缩到一种 agent，其余只走文件级观察。**

## 4. 功能级可行性（含砍单）

- **高（现在就做，单人安全）**：F1 阅读中枢、F2 注入回执（四级标签中第 1/2 级）、F7 钉规范、F8 澄清卡（本地）、F9 前情提要包、F10 子任务树、F11 的 Jira 部分、F13 的本地归档+摘要。
- **中**：F3 工作流进度（阶段级=高；步骤级"遗漏检测"受事件粒度限制，只能尽力而为+未知标注，不得承诺全知）；F4 知识轨迹（准备期=高；运行期仅 ACP 模式）；F5 受管启动门（防绕过不赌，外部启动如实报"未观察到批准"）；F6 权限卡（中等工作量 UI）；F11 的 MR/CI 对齐；F14 静态站。
- **低/后置/可能永不做**：F12 飞书抓取（组织门控，Tier 2 才有，Tier 1 替代覆盖推送）；实时快照服务（P3+ 且带能力上限）；GPT 治理层全部（平台内验收流、组织账号体系、多设备任期、Brief 强制写作面）。

## 5. 两份方案各自的乌托邦成分（自审）

- **GPT 的乌托邦：流程乌托邦**——假设多角色会因流程要求而改变行为（PM 维护简报、测试平台内验收、全员登录）。组织行为学上，被要求的采纳不是采纳。
- **GLM 的乌托邦：完备乌托邦**——假设建造者能撑起 F1–F14 交付且同事会为了"满血观测"选择驾驶舱。本节第 1、2.1 节已修正。
- **共同的更隐蔽风险：复杂度通胀**——两轮辩论每轮都在加精度（证据阶梯、能力矩阵、SyncIntent），没有一轮在做减法。收敛过程本身会产出"需要维护团队才能承载的系统"。解药就是单人测试 + 本节砍单 + 第 6 节预警信号。

## 6. 修正后的可实施路线与预警信号

**阶段 0（现在）**：F1 补全 + F2 回执（第 1/2 级）+ F3 阶段级进度，全本地零服务。同步做两个半天级测量：Jira 两个大版本的 issue 类型分布基线（为轻路径预算提供真数，兑现第四节撤回"80%"的承诺）；飞书 Tier 2 spike（D7 定档）。
**阶段 1**：建造者驾驶舱——F5/F6/F7/F9/F10 + F4 准备期留痕。
**阶段 2**：Jira 版本看板 + GitLab MR/CI 关联；飞书按 Tier 落地（Tier 1 群机器人推送零审批即可上线）。
**阶段 3（门控于自发拉力）**：基座 CI 静态文档站（同事的零安装阅读通道）+ 群推送；实时服务仅在"观察者真实存在且抱怨静态滞后"时立项，并带 02-glm-review 第六节失败点三的能力上限。

**预警信号（触发即调整，不解释）**：
1. 两周后建造者自己不再每天打开面板 → 阶段 0 方向错，回炉 F1。
2. 同事一个月零主动询问 → 停推广，转纯个人工具 + 静态站。
3. PM 从不点链接、只在群里问 → 推送即全部，砍只读站投入。
4. 无诊断回执缺失率 >20% → 修仪器（沿用失败点一）。
5. 一次 agent 升级适配修复超一天 → 适配面收缩到一种。

**永久不做清单（除非组织现实变化）**：平台内验收工作流、组织账号体系、多设备任期/租约、Brief 强制写作面、通用低代码流程编辑器（GPT 已列，此处确认）。
