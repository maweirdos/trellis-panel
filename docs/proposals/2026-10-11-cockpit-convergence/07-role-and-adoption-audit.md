# 07 · 从实际成员出发的产品与可实施性审查

日期：2026-10-11。此次审查不以既有页面、F 编号或演示流程为前提；先讨论谁获益、谁付出成本、什么条件会令产品被绕开，再决定建设范围。角色判断是有待验证的产品推演，不是已经做过的员工访谈。

## 1. 新确认的组织条件

| 条件 | 证据状态 | 对判断的影响 |
| --- | --- | --- |
| 团队约 12 人，其中 8 名开发 | 用户本轮直接确认 | 已具备有意义的跨人协作需求，不能继续默认只有个人偶尔使用 |
| 用户能推动整个团队 | 用户本轮直接确认 | 可以组织统一项目试点、约定资料范围与接入方式；不必只等待自然传播 |
| 每周五天使用 | 用户本轮直接确认 | 按工作日使用频率理解；不等同五天全职建设维护 |
| 当前 Trellis 实际使用人数 | 尚未确认 | 不能假定 8 名开发都已有一致工作流与 hooks |
| 专职产品、测试、运维各有几人 | 尚未确认 | 讨论工作职责，不虚构剩余 4 人的岗位分配 |
| 建设维护人力与公司部署权限 | 尚未确认 | 能推团队流程不自动等于有服务器、应用管理员权限或维护预算 |

**判断更新：团队能力应进入第一轮真实验证。** 个人核心仍先做出可用链路，但不能连续多个阶段只验证本人，最后才发现其他 11 人没有收益。单维护者预算可以继续作为资源保守假设，不能被当成组织事实。

## 2. 开发成员：省下自己的工作，才有理由长期使用

### 熟练使用 AI 的开发

他可能已经有成熟的编辑器、快捷键、提示词和会话恢复习惯。把同样的聊天能力搬进另一款工具，通常不足以补偿迁移成本。

真正值得交换的是：不用翻目录就能读到当前工程材料；知道此次到底带了哪些规范；发现缺项能有效补入；几周后接任务不用从零解释；交付状态不再靠手写同步。

需要验证的抵触点：重复登录/选模型、每次切换项目重新绑定、上下文与原编辑器不一致、正常修改也反复批准、两个窗口之间复制材料、适配器升级后突然不能工作。

**产品要求**：外部编辑器路径与驾驶舱路径共享同一任务材料与来源，允许只用其中一部分。先证明“这里多完成了一件原工具做不好的事”，再邀请进入受管 Agent 模式。

### 普通开发与不常用 AI 的开发

他可能并不关心 ACP、hook 或 token，只想知道自己需要改什么、参考哪个现有方案、怎样验证不会影响其他模块。

默认视图应回答任务问题：需求材料、当前决定、相关旧任务、待确认项。协议日志藏在可展开的诊断中；不能为了推进平台而先让全员学习新的 Agent 调度概念。

如果团队还没有共同采用 Trellis，推广成本包含工程习惯与材料责任的建立。安装了客户端、创建了规范目录，都不能算真正采用。

### 接手者、新人、临时支援者

他们的高价值入口可能不是“启动 Agent”，而是“上一次为什么这样设计、哪些问题已解决、哪些只是当时的假设”。

前情提要必须能回到确认过的文档、讨论与提交；过期结论显式标日期/版本。无法核实时显示未知，不能让一个流畅的 AI 摘要成为新的错误来源。

### 团队共同的信任条件

开发既生产大部分材料，也承担接入、更新和纠错成本。如果管理者只得到可视化监督，而开发只多了填表，强制推广也难获得可信数据。

详细回执先帮助本人检查；共享任务结果与必要过程摘要，不把工具调用次数、缺回执率、token 使用量转成人员绩效排名。允许说明合法例外和纠正错误归因，防止为凑齐绿灯而制造记录。

## 3. 产品成员：需要决策入口，不一定需要另一张仪表盘

产品通常关心：当前到底包含什么；刚改的要求是否被接受；哪里卡住且需要自己回答；能在何时看到可试用结果；哪些部分明确不在本次范围内。实际习惯仍需验证，不能声称每个产品都会每天读 design。

“正在检查”“Agent 调用了三次知识库”对这些问题帮助有限。默认团队视图应给出可追溯的变化与行动，例如“历史数据兼容未纳入本次，需要你确认范围”，并能展开对应 PRD/design。它不应要求开发另写同样内容，也不能由 AI 无证据推断交付承诺。

产品的贡献应当小而明确：在已有 Jira/飞书里提供原材料，回答一个具体问题，确认真正影响业务范围的改变。平台原创需求讨论可以有价值，但不作为导入现有工单的必经步骤。

不要预设产品一定拒绝新工具，也不要预设他愿意搬家。优先让他使用已有身份打开一个有用的任务链接；能在现有消息工具回复就保留该习惯。新平台账号/录入流程只有确实减少工作时才引入。

## 4. 技术负责人、评审者与质量职责

| 职责 | 真正可能的收益 | 容易造成的反效果 | 应验证的结果 |
| --- | --- | --- | --- |
| 技术负责人 | 找到反复返工的约定、检查规范是否过期、了解跨模块影响 | 把所有例外都当违规；把文档数当质量 | 能从一次真实问题回到规则、采用版本与检查依据 |
| 代码评审者 | 少问“为什么改、原需求是什么、是否考虑过旧行为” | 平台生成很长但不准确的说明；代码又变了一版 | MR 当前 SHA 与需求/设计/检查对应，旧证据不会误报 |
| 测试或承担验收的人 | 明确范围、验收条件、已测与未测部分 | 重建一套与现有工具重复的验收流程 | 用现有流程即可完成工作，平台提供材料和证据 |
| 规范/知识维护人 | 从真实任务提炼可复用规则 | 每次归档自动产生大量互相冲突的“规范” | 经验可检索；正式规则有维护人、范围、例外和弃用关系 |

这些是职责，不预设公司有独立岗位。同一个人可以承担多项。首版不建完整验收引擎，但不能因为角色未知就丢掉质量验证。

规范文本只能约束明确写出来的内容；代码执行行为还需测试/检查。检索与注入回执能够提高可解释性，但不能证明模型理解了全部业务或保证没有遗漏。

## 5. IT/运维与建设维护者

### IT 或公司工具管理

会关心安装权限、凭据放哪里、资料发到哪里、谁能看、软件怎么升级、出了问题能否撤销接入。用户能推动团队不自动授予这些权限。

对 8 名开发，当前现存安装包约 80.6 MiB、主 exe 约 180 MiB 值得优化，但不能直接称为“采纳杀手”。安装审批、签名与来源可信度、升级策略、重复运行环境和本机兼容更可能决定能否部署。以上体积为先前本地产物测量，未重新构建。

非开发成员用浏览器；开发先复用现有客户端验证价值。抽离 Electron API 后再比较浏览器本地工作台/轻壳，不能把“React 已有”理解成现在直接丢掉 exe 就变成 Web 产品。

### 建设维护者

长期成本主要是例外与兼容：某个 Agent 升级、hook 没触发、同事用不同分支/工作目录、公司接口授权变化、索引陈旧、断网重传、文档被并发改动。AI 能帮助写代码，但这些仍需要真实环境验证和明确责任人。

不承诺同时覆盖所有 Agent。先完整验证一个组合，后续扩展按团队实际使用量与维护成本排序；某一适配故障不能影响基本阅读和原编辑器开发。平台停用时任务材料仍可在 Git/Trellis 中使用。

## 6. 跳出原定顺序的压力场景

| 现实情况 | 产品应该怎样表现 | 由此能发现什么 |
| --- | --- | --- |
| 改一个很小的显示文字 | 不强制完整设计/新 Brief/团队审批 | 是否为了流程完整牺牲高频工作 |
| 紧急修复，来不及打开驾驶舱 | 员工可按现有应急规则继续；之后补关联，不伪造实时记录 | 平台会不会成为阻塞工作的依赖 |
| 同事不用受管 Agent，只用自己的编辑器 | 阅读仍有价值；兼容 hooks 可提供真实回执；未知部分如实显示 | 是否实际强迫统一工具 |
| 开发在多个任务和分支间切换 | 明确 repo/worktree/task/run 身份，不能串线 | 图表是否只是把同项目事件混在一起 |
| 产品在飞书改了范围，开发还在旧版 | 提示差异与当前采用版本，不静默覆盖执行输入 | 谁负责处理变更，是否需要再写一份需求 |
| 前任留下的设计与现代码不一致 | 显示历史版本，要求核对当前实现 | 前情提要是否会放大陈旧知识 |
| 开发电脑关机，产品要看进展 | 展示最近成功快照和时间，不显示持续运行 | “本地执行+团队可见”的真实边界 |
| 公司不允许加飞书应用 | 能人工导入/复制问题链接，核心任务仍可继续 | 是否把全部价值押在外部审批上 |
| 规范本身写错了 | 允许质疑、例外说明和修订，不鼓励为绿灯扭曲实现 | 是帮助工程判断，还是制造表演式合规 |
| 平台维护者请假或离职 | 既有任务材料可读、凭据可撤销、导出/备份可用 | 是否形成新的个人单点依赖 |

## 7. 当前技术可行性判断

以下“高/中”是基于代码与依赖面的工程判断，不是统计成功概率，也不代表已在公司部署验证。

| 能力 | 技术可行性 | 主要难点 | 当前证据 |
| --- | --- | --- | --- |
| 本地文档与任务结构化阅读 | 高 | 文件变更、未知字段、版本与阅读位置 | 已有 scan/watcher/文档组件 |
| 跨任务来源和前情接续 | 高 | 稳定关联、过期结论、当前代码核对 | 已有交接材料与 Trellis 任务基础；新关联还需实现 |
| 在可支持节点记录上下文回执 | 中高 | 宿主差异、截断、正确目标、性能与失败诊断 | 本地 hooks 可组装/输出上下文；完整接收证据并非都有 |
| 受管 Agent 交互和干预 | 中 | 能力协商、权限、恢复、外部宿主差异 | 已有 ACP 服务；MCP 下发等仍有缺口 |
| Jira/GitLab 的任务与交付关联 | 中高 | 实际版本/权限、分页、稳定 ID 与当前 SHA | 已有客户端，但有单页搜索、opened MR/分支最新流水线限制 |
| 12 人团队的文档/状态共享 | 技术上高，组织条件待验证 | 身份、可分享范围、版本/离线、部署维护 | 需新最小后端；当前团队页面主要是本地快照汇总 |
| 飞书资料读取与消息交互 | 条件性可行 | 应用/文档/群权限与真实样本支持 | 不能由公开 API 或“有代码”推定公司环境可用 |
| 全过程全知、强制模型遵守所有规范 | 不作承诺 | 模型内部与外部工具可见性边界 | 应降为可观察事实和明确范围的检查 |

本地证据：[ACP](../../../src/main/services/acp.ts)、[Jira](../../../src/main/services/jira.ts)、[GitLab](../../../src/main/services/gitlab.ts)、[Electron API 入口](../../../src/renderer/src/api.ts)、[task.py](../../../.trellis/scripts/task.py)。本轮只读核查，没有运行公司接口或完整集成测试。

## 8. 对这个 12 人团队的具体建议

推荐形态：**本地开发工作台 + 一个最小团队服务 + 既有 Jira/飞书/Git 平台。** 一份任务材料面向不同职责提供不同默认视图，源码和编码执行仍在员工本机。

团队服务只管：任务关联、获准文档快照、最后更新时间、需要人回复的问题、现有 MR/CI/Jira 的引用与回执。身份尽量复用既有系统；不先建完整组织架构、审批引擎、模型中台和全量会话仓库。

从第一轮试点就验证跨人链路，建议 2 名开发（至少 1 名不是平台建设者）与 1 名真实需求协作者。最小服务与本地核心组成同一个试点闭环，但不先为后台管理页面花掉全部时间。若公司部署条件暂不具备，用明确标注的已提交/导出快照验证阅读价值；实时目标仍记为未完成。

公司共识负责规定“什么材料需要留下、谁可读、哪些动作需确认”；员工仍可选择自己的编辑器和获准模型。推动全团队不应等于强制每天进一个新聊天界面。

这比等待个人版本全部成熟后才接触团队更适合当前已知条件，也比一次建设完整一站式系统更可控。

## 9. 投入收益要算净值

假设未来 8 名开发都实际使用，每人每工作日节省 5 分钟，五天合计是 200 分钟，约 3 小时 20 分钟/周；节省 10 分钟则约 6 小时 40 分钟/周。**这只是计算示例，不是已经测得的收益。**

如果每周维护适配和处理平台问题就耗掉更多时间，仅节省找文件时间不足以成立。还需观察是否减少重复澄清、交接困难和同类返工；不能把所有质量改善都归因于平台。

可持续投入和维护负责人仍未确认，所以现在不能给整体工期或断言收益已经为正。

## 10. 怎样让“可实施”变成证据

第一轮试点分别验证：

- 开发：完成真实任务没有重复写需求、重复上传文档；缺规范时能补入且有正确回执。
- 需求协作者：不用私聊开发，也能回答当前范围、最新变化、等待谁决定以及数据新鲜度；不能只看到“开发中”。
- 接手者：依据材料解释至少一个历史决定和遗留问题，并知道哪些需要核对当前代码。
- 运维：关机、断网、拒绝权限、接口失败和 Agent 升级时，原工作方式仍可继续，不出现假成功。
- 维护者：记录真实适配/故障处理时间，评估净收益；角色使用率按出现适用任务的次数衡量，不只看每日打开数。

技术闭环、角色收益和运行维护三项都成立，才扩到 8 名开发。组织推动力可以让试点发生，不能代替这些结果。

## 11. 当前结论

在约 12 人、8 名开发、能推动全团队的条件下，建设一个收敛的团队研发工作台具有现实可行性。最值得投入的是可追溯的任务材料、可核验的过程、可延续的决定与低成本协作。

现在不成立的承诺是：所有人都会因统一界面改变习惯、所有 Agent 内部过程都能观察、自动注入就能确保质量、没有明确维护投入也能长期稳定运行。保留这些边界，项目可以做；把它们当既定前提，才会走向无法实现的理想模型。
