# 02 · 产品蓝图与真实场景

本章描述目标体验，包含后续能力，不等于全部首发。v0.3 首发范围与可行性门槛见第 04、06 章；不预设公司有专职测试，也不要求产品迁移到新的验收系统。

## 1. 用户打开后的第一屏

默认是“我的版本工单 + 最近工程任务”。工单来自 Jira，按实际版本字段组织，支持 bug/优化/新需求过滤。最近任务包含本地任务、关联 MR 和未处理问题；不是全员统计仪表盘。

点进任务后始终留在同一个驾驶舱：

```text
Jira / 本地任务 / 当前分支          来源版本 · 文档修订 · 实际观测能力
阅读 | 上下文与规范 | 执行过程 | 需求来源 | 迭代脉络 | 交付
┌───────────────┬─────────────────────────┬──────────────────┐
│ 文档/章节目录  │ PRD / design 舒适阅读     │ 当前待处理问题     │
│ task 信息     │ 正文、差异、段落反馈       │ 规范与知识回执     │
│ context 清单  │ 可宽屏、可专注阅读         │ 下一步可操作动作   │
└───────────────┴─────────────────────────┴──────────────────┘
本地 Agent 对话可展开；它服务于当前任务，不取代正文阅读。
```

真实编辑/讨论围绕材料发生：选择 design 段落提出修改；看见遗漏规范后钉入；看到某个检查缺证据后要求补检查；在历史任务上发起后续优化。少用“去另一个页面再找同一任务”。

## 2. 阅读是首发功能，不是日志的附件

- PRD/design：正常文档排版、标题目录、阅读宽度、专注模式、原文切换、最近阅读位置。
- 文件变化：写入稳定后刷新；不在用户阅读时抢滚动和焦点。提示新修订，并可与已确认版本比较。
- task.json：结构化字段与原始未知字段并存，项目/worktree 标识清楚，不为美观丢字段。
- implement/check.jsonl：每条引用显示类别、路径、理由、是否存在、实际可读/裁剪情况；原始内容可检查。
- 有引用但没有读取证据、读失败、文件损坏、归档改路径，均有明确状态。

一份 Markdown 的源文件仍由 Trellis 和仓库管理。视觉批注生成任务内可追溯的反馈，不靠重写整篇文档保持“同步”。

## 3. 轻任务、标准任务、复杂任务

任务路径由修改影响和项目约定决定，不按标题长短判断。

| 路径 | 典型场景 | 开发必须看到什么 | 可以省什么 |
| --- | --- | --- | --- |
| 轻任务 | 描述明确、范围小、无数据迁移/权限变化的 bug | 原工单、最小处理计划、适用规范、检查结果 | 不强制新 Brief、额外 design、逐次共享发布 |
| 标准任务 | 单项目的常规优化 | 来源快照、工程 PRD、必要设计、步骤与检查 | 不强制跨角色审批链和复杂文档模板 |
| 复杂任务 | 跨模块/多仓/兼容或数据风险 | 来源与问题、工程设计、子任务/依赖、交接与回归 | 不省掉项目要求的关键确认 |

“准备任务”可以一次完成读取 Jira、定位已配置项目、整理来源候选和本地 Trellis 规划入口。它不能隐式从领取跳到改代码。已有对应任务时直接关联；项目变了或来源有歧义才额外确认。

## 4. 周三的小 bug：最短路径

小周打开 Jira 的本版本工单，“重复扫码时提示不明确”。描述足够，不挂飞书文档。

1. 点击“在本项目准备”，自动带入工单快照与项目约定，关联或创建本地任务。
2. Agent 在本机分析后呈现一页最小计划：影响位置、期望提示、两项检查。开发按原工作流确认后实施。
3. 驾驶舱显示必要的规范回执和检查依据。开发查看差异、创建或打开现有 MR。
4. 合并/验收达到项目条件后回写 Jira，任务材料按既定策略归档。

不要求产品再发布 Brief，不要求开发重新写一份战报，不要求每个小 bug 都有 design。具体人工步骤数与耗时在试点记录，不提前承诺“一分钟结束”。

## 5. 飞书里的复杂需求：减少复制粘贴，而非猜章节

Jira 概述“追溯码管理优化”，正文挂飞书链接。点击“准备需求资料”：

1. 展示工单描述和链接；已有精确章节锚点优先，否则列目录候选。
2. 用户选中需要的章节，预览正文、表格、图片/附件缺失提示。
3. 将授权读取的内容固化到项目允许的任务资料路径，并保留文档 ID、块/章节标识、版本或抓取时间与 hash。
4. Agent 使用该快照作为本次任务输入；飞书原文变更时展示差异，不悄悄换掉当前规划依据。
5. 权限不足时可粘贴/导入所需章节，保留来源链接和人工导入标识；不让使用流程完全失效。

检索出的业务知识用于补充影响范围；默认不把所有相关命中都注入。用户能看到查询、候选、选入、遗漏原因与实际传递。

## 6. 规范和知识如何“可干预”

“上下文”页显示四列关系：任务需要什么→找到什么→实际带了什么→检查如何验证。

用户可以钉入一条业务规范、取消过期候选、要求扩大知识检索、查看被裁剪内容。新增内容默认作用于下一个明确的上下文准备点；正在执行的轮次保留原材料版本，界面说明何时生效。

对“每次编码都应该带规范”的需求，首版提供阶段开始、包/层切换、子 Agent 启动等可观测点的上下文准备与核验。能否在每次写工具之前强制检查，取决于宿主能力；支持的组合明确验证，不支持的组合不声称已强制执行。

## 7. 工作流图的正确用途

它显示实际发生的事件和被支持工作流模板要求的步骤。阶段、子 Agent 泳道与检查记录关联同一任务和本次执行。灰色表示未知/未观察到，黄色表示部分/待处理，绿色只用于具体已完成的证据事件。

任意 workflow.md 的自然语言不能自动变成可靠的执行状态机。首版只为已支持的工作流版本提供观察映射；未支持的显示“原文步骤 + 观察时间线”，不自动判定遗漏。

使用外部编辑器的员工也可通过 hooks 提供回执。驾驶舱优势是材料、证据和操作集中；不靠故意降低外部观测来强迫迁移。

## 8. 两周后再优化：从前情继续

查找历史任务支持 Jira 号、名称、模块和全文；先按确定的关联关系定位，再用知识检索补充。用户选择“后续优化”“修复本次交付”或“替代旧方案”，关系与父子拆分分开。

“前情提要”确定性汇编：当时确认的 PRD/design、澄清结论、未解决项、相关规范版本、归档摘要、MR 与提交。原始聊天仅在本人有权限且明确选择时加入，不默认把整段会话带走。

提要明确“哪些仍需对当前代码重新核实”。用户检查来源和裁剪后作为新任务输入；它不会复制旧任务已完成状态，也不会自动执行历史命令。

## 9. 产品经理下午查看进展

初期优先利用既有私有文档站或限定导出，产品通过已有公司身份查看已经提交/导出的 PRD/design 与任务状态，页面显示来源版本和时间。不要求注册新平台账号，也不以免登录为由开放私有资料。

若后续已通过实时服务的准入验证，并配置自动共享范围，产品打开同一任务的只读页，才可看到最新同步的 PRD/design 草稿、当前阶段、待澄清卡、MR 和提交级 CI。详细个人回执和完整工具行为默认仍在开发本机，任务级摘要按项目策略展示。

每份材料显示修订与最近同步时间。开发离线后只展示最近快照，停止“直播中”提示。草稿不是已确认要求；需要业务决定时，通过飞书卡片/平台链接回应具体问题，反馈回到本地任务。

通知、文档读取和回复回填分别验证。只有 webhook 推送时，先提供原工具链接和人工记录结论，不能展示并未接通的自动回复回填。

产品经理无需安装本地客户端；不能从只读页面选择员工 Agent、执行终端命令或审批本机高权限工具请求。

## 10. 交付和沉淀

MR/CI 是第一方对象，不再靠按钮“我认为已合并”作为唯一证据。CI 必须对应当前交付提交；分支旧提交的绿灯仅作历史信息。

首版不另建平台验收引擎。使用团队已有的 Jira、MR 与业务确认规则，保留有来源的确认记录；不假设“没有独立测试岗位”或“关 Jira 就等于所有验收已结束”。

归档产生任务文档包与来源关系，按已有基座仓库制度提交选定材料。自动共享的过程快照不必每次都形成 Git 提交；正式归档版本与草稿快照分开保存。迭代知识库索引已发布/归档材料并反链任务树。

普通经验可以被检索；强制规范仍需要维护人评审并明确适用范围。规则发布不自动覆写所有员工本机项目。
